01

结论：作用有多大

「执行过程」回答的是一个很具体的问题：这一轮到底是怎么跑出来的？ 这个问题在不同人身上出现的频率完全不同。先按人群拆开看，再判断投入。

人群 / 场景什么时候会点开当前可用度优化后的价值
普通使用者 答案看起来不对、想确认「它到底查了什么」、或者一轮为什么跑了很久 低。首屏是一串 JSON，找不到「检索词 / 命中几段 / 时间花在哪」 高。一句话摘要 + 时间轴，3 秒能读懂这一轮
重度用户 / 开发者 工具失败、审批被挡、检索没命中、token 暴涨、回答变慢 中低。能查到事件，但没有筛选、搜索、失败定位与耗时分布 高。筛选 + 失败高亮 + 耗时/用量明细，可直接定位
运营 / 审计 复盘一次问题会话、把过程附到工单 低。没有导出，只能截图；审计另有 AuditLogPage，两边不打通 中。复制 Markdown / 导出 JSON 后够用
新用户 几乎不会主动点 无感。入口是标题栏一个 11px 的「过程」文字按钮 不必强推。等他在答案旁产生疑问时再给入口
VERDICT

有必要优化，但只做「让已有数据说人话」这一层

理由很直接：数据已经在库里了——工具、检索、用量、三张卡、产物、子智能体、失败与停止，账本都落过； 缺的不是采集，而是呈现与聚合。这意味着优化的边际成本很低：一个事件渲染器 + 一个时间轴，就能把「日志」变成「解释」。

但也要划边界：不要把它做成完整的 trace 平台。不做分布式链路追踪、不做实时直播时间轴、不做跨会话分析大屏—— 那是另一个产品，收益和成本都不匹配。这个面板的定位应该只有一句话： 「这一轮为什么是这么答的」的解释器。

  • 值得做的信号：「对照正文」是唯一能解释因果关系的能力，但目前两侧编号对不上；把它修好，价值立刻成立。
  • 值得做的信号：一次 103 秒的轮次，真正的故事是中间 89 秒的生成期；当前界面只把它表现为两行之间的空隙。
  • 不值得做的信号：面板没有搜索/筛选/导出时，排障者会直接放弃去翻服务器日志——说明它现在没有承担起排障入口的角色。
02

现状体检：六个具体问题

下面每一条都能在代码或你给的两张截图里对上号。按影响排序，前三条是「就算不改交互也必须先修」的。

ISSUE 01 · 数据缺口

账本里没有工具步，「对照正文」的编号对不上

账本只在 LEDGER_SSE_TYPES 白名单里的 SSE 事件入账，tool_status 不在其中； 主引擎路径也没有单独的 tool 入账调用。面板的「对照」却只对 type=tool 的事件编号， 两边编号天然对不齐，点击左侧步骤不会有右侧行被点亮。

ChatRunRuntime.java#L464-L467 · SessionEventsPanel.vue#L146-L157
ISSUE 02 · 原始 JSON

「用量」「检索」直接把 payload 当正文展示

读口只给 240 字摘要，前端把摘要原样铺在行里。于是用户看到的是 {"prompt":22315,"output":258,…}，而不是「输入 22.3k · 输出 258 · 缓存 8.4k」。 信息都在，只是没翻译。

ChatService.java#L1045-L1092 · SessionEventsPanel.vue#L78-L86
ISSUE 03 · 语义误读

累计快照被当成多次调用

一轮里 5 条 usage 是同一份累计用量的进度帧（prompt 22k→48k→63k→97k）， 4 条 retrieved 也是累计命中数的快照。折叠头却写成「检索×4 · 用量×5」， 读起来像发生了 4 次检索、5 次模型调用。

折叠头统计：SessionEventsPanel.vue#L233-L238
ISSUE 04 · 时间不可见

没有时间轴，耗时分布读不出来

截图那轮共 103 秒，其中 14:04:35 → 14:06:04 有 89 秒空档——那才是长回答的生成期。 当前只有首末时间和每行时刻，没有比例条，用户无法判断时间花在检索、生成还是等人。

SessionEventsPanel.vue#L51-L90
ISSUE 05 · 噪声淹信号

真正有价值的事件被用量行挤掉

9 条事件里 5 条是同一串用量 JSON，占了面板大部分视觉面积； 检索词、命中段数、失败与卡片反而被压到看不见。面板应该按「里程碑」呈现，而不是按「帧」呈现。

截图 2：9 条 = 5×用量 + 4×检索
ISSUE 06 · 入口与工具

入口深、没有筛选/搜索/导出

会话级入口是标题栏最右侧的纯文字按钮；单轮入口在消息的下拉菜单里。 面板内没有本地筛选、搜索、复制或导出，排障者只能靠肉眼滚 200 条。

2.2 一个容易忽略的事实

面板文案承诺「工具步与耗时」，但当前主引擎路径下账本通常只落检索/用量/卡片类事件。 因此这轮 103 秒里到底调了哪些工具、各花多久，账本回答不了——它只能回答「检索了几次、用量多少」。 这也解释了为什么「对照正文」看起来有按钮、却几乎没有可点的联动。

03

设计目标与原则

优化不是把面板做复杂，而是把同一份数据按「读者」重新分层：先给结论，再给证据，最后才给原始帧。

01
3 秒读懂一轮

折叠状态也要有：耗时、阶段比例、检索/工具/失败计数、一句话结论。不展开就能判断「正常 / 异常」。

02
一次点击定位

从最终答案的某一段，点到它对应的工具/检索/等待节点；反过来也成立。编号必须两侧同源。

03
快照不是事件

usage / retrieved 是累计状态，按「最新态 + 趋势」呈现；不要按帧铺行，更不要把快照数当成调用次数。

04
原始帧仍然可查

人话摘要默认，原始 payload 一次点击后可见。既不吓到普通用户，也不夺走排障者的原文。

04

优化方案：P0 兑现承诺，P1 给出洞察，P2 才谈导出

三档按「不做会失真 / 不做没洞察 / 不做也能用」划分。P0 与 P1 是建议范围；P2 视使用情况再定。

4.1 P0 · 先让面板说真话（必须做）

动作具体改法涉及位置验收
P0-1 补齐工具步 把 tool_status 的终态帧（done / error / denied + elapsedMs）并入账本；或在读口用消息里的 toolCalls 合成工时节点。二者择一，保证账本与消息同源。 ChatRunRuntime 入账白名单 / ChatService.eventItem 单轮面板能看到每一步工具、状态、耗时；与正文工具卡数量一致
P0-2 事件渲染器 前端按 type 提供「人话摘要」：usage → 输入/输出/缓存/上下文；retrieved → 检索词数/命中段数 + 词条 chips；tool → 工具名 + 参数摘要 + 状态 + 耗时；error → 原文；artifact → 文件名。禁止直接把 payload 铺行。 新增 process/presenter.js（或并入 projections） 面板中不再出现可见的 JSON 花括号
P0-3 快照合并 同一轮的 usage / retrieved 折叠为一个节点，展示最新态；展开才是逐帧明细。折叠头不再用「×N」统计这两类。 SessionEventsPanel.vue 的 group / summary 一轮 9 条 → 首屏 3~4 个里程碑节点；「检索×4」消失
P0-4 字段不再被截断 工具行的 name/status/elapsedMs 由后端结构化返回（已是现状），但需确保入账的 payload 截断不会切掉这些字段；检索/用量同理，不要靠 240 字摘要反解。 ChatService.eventItem · SessionEventService 任意长度 payload 下，工具编号与状态都正确
P0-5 单轮入口前移 在「已完成 · 用时 1 分 48 秒」这条状态行右侧加「过程 ›」文字链（保留消息下拉里的入口），让用户在产生疑问的原地就能点。 ChatPage.vue TurnBar / 消息操作 不经过菜单即可进入单轮过程

4.2 P1 · 让面板给出洞察（建议做）

动作具体改法验收
P1-1 时间轴 账本行改为纵向时间轴：时刻 + 类型节点 + 摘要 + 耗时；顶部一条阶段比例条（准备 / 生成 / 等待 / 收尾），把 89 秒的空档显性化。 不展开也能看出时间分布
P1-2 单轮指标条 总耗时 / 工具数 / 检索数 / 等待时长 / 失败数 / 最终用量，做成一行可点的筛选项。 点击「失败 1」只剩失败节点
P1-3 对照联动 两侧编号统一以消息 toolCalls 为源；账本工具节点带同一编号；点任一侧，另一侧高亮并滚到可见。 左侧第 3 步 ↔ 右侧第 3 个工具节点
P1-4 筛选与搜索 「全部 / 工具 / 检索 / 卡片 / 产物 / 失败」chips + 本地关键字过滤（不发请求）。 200 条内可秒级定位
P1-5 失败与等待突出 error / denied / stop / timeout 用红色节点与原文；「等待你 42s」单独成段，并说明它计入总耗时但不计入工具耗时。 一眼能回答「为什么慢 / 为什么错」

4.3 P2 · 可选项（先别做重）

动作具体改法建议
P2-1 导出 / 复制 「复制 Markdown」与「下载 JSON（最近 N 轮）」，用于工单与复盘。分享链接仍不包含账本（沿用 guest 过滤）。 使用率起来后再做
P2-2 跨轮对比 会话级总览加每轮耗时/用量的迷你条，看出哪轮变慢、变贵。 与 P1-1 同一套数据，增量小
P2-3 与使用统计打通 用量节点底部「查看使用统计 ›」跳到 StatsPage。 避免重复造统计
不做 全量 trace 平台 分布式 span 树、实时直播时间轴、跨会话分析大屏、采样与指标看板。 成本与定位都不匹配

06

落地与验收

P0 的改动集中在读口与渲染层，不新增表、不改 SSE 协议、不动消息表； P1 只替换账本的视觉结构。风险主要在「工具步与消息 toolCalls 的一致性」，需要一条对齐用例。

6.1 验收清单

  • 单轮面板能看到全部工具步，数量与正文工具卡一致
  • 面板首屏不再出现可见的 JSON 花括号
  • 一轮 9 条噪声事件折叠为 3~4 个里程碑节点
  • 折叠头不再出现「检索×4 / 用量×5」这类伪计数
  • 时间轴上能看出阶段比例，等待时长单独成段
  • 点左侧任一步，右侧对应节点高亮并滚动到可见
  • 失败节点默认可见且能展开完整输出
  • 移动端 sheet 与 PC 表现一致（除双栏折叠）

6.2 怎么判断「优化有没有用」

信号观察方式期望方向
入口点击率顶栏「过程」+ 状态行「过程 ›」的点击占比上升（说明入口位置对）
单轮对照使用率从消息进入且发生左右联动的事件数 / 进入次数上升（说明对照真的可用）
读懂率5 人小样本任务：找出「这一轮为什么慢」「哪一步失败」全部在 30 秒内答对
排障替代支持工单中附过程截图/导出的比例上升（说明进入了工作流）
噪声投诉「看不懂 / 全是代码」类反馈下降

6.3 风险与取舍

  • 工具步来源不一致：账本与消息 toolCalls 可能因并发/重试而数量不同。建议以消息为准做「权威步数」，账本只补充耗时与失败原文。
  • 历史数据：旧账本没有工具事件，也不能凭空补。面板对历史轮显示「本轮未记录工具步」，不要显示成 0。
  • 性能：一次最多 200 条，前端过滤足够；不要为此加分页或再开接口。
  • 隐私：分享链接继续走 answerOnly，账本不出现在访客视图；导出保留「仅本人」。
  • 定位：不做实时直播时间轴。跑动中的过程已经在正文过程簇里，账本只服务事后回看。
