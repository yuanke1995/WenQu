## 一、做成了基础版，需要补全的

### 1. 工具大输出留存（spill）——只救「给人看的那一份」

**现在的边界**：截断发生在 `SandboxTools.clip()`（2 万字符）与问答侧 8K 展示上限这两处，
超限时把**整份原文**落到 `data/tool-spill/<uid哈希>/`，工具卡片给「查看完整输出」按需读回，
保留期 `cleanup.toolSpillRetentionDays`（默认 7 天）+ 清理任务「工具外溢原文清理」，开关 `tool.spillEnabled`。

**没覆盖的三段**：

| 缺什么 | 为什么现在不做 | 补法 | 代价 |
|---|---|---|---|
| provisioner 侧 262144 字节帽 | 输出在进 Java 之前就被砍，Java 这层再留也留不到全文 | 改 `ProvisionerSandboxProvider` 的读回逻辑：分块读完再决定是否留存，或让 provisioner 只回传大小+前缀、原文走 `/v1/file` | 中；要动沙盒服务协议，注意别把上下文撑爆（帽子的存在就是为了这个） |

| **已经覆盖全部工具**（订正：`recordToolStatus` 是所有工具结果的统一收口，`instrumentTools` 逐个包装，所以 MCP / 技能 / 联网搜索超过 8K 的部分同样进留存；`SandboxTools.clip()` 只是沙盒那层多出的一个更早的 2 万字符口） | ~~残留的真实边界是磁盘配额~~ **2026-10-11 已补**：`tool.spillMaxMbPerUser`（默认 200MB，0=不限量）。写入后把该用户目录压回配额内，按落盘时间淘汰最旧的几份；刚写的那一份不参与淘汰（单份原文就可能大过整份配额，删掉等于这条能力对白开）。淘汰只影响「查看完整输出」能否读回，卡片预览与这一轮结论不受影响 → 见 §五 那三个既有缺陷的第 2 条 | 探针（真 `ToolSpillService` + 假配置源，24 条断言）覆盖：压回配额、留最新、0=不限、超配额大份保留、归属隔离、保留期清理照旧、孤儿元信息结清、关掉不落盘。真机验了设置项进快照且改值能回显 |

### 2. 会话过程回放——按轮定位已落地（PC），逐气泡入口只做了一半

**现在**：`GET /api/ai/session/{id}/events` 两种看法共用一个端点——不带 `turn` 按轮倒序列最近若干轮（头部「过程」按钮），
带 `turn=<turnId>` 只取那一轮、按发生顺序摊开（气泡「更多 → 看这一轮的过程」）。
`c_ai_message.turn_id` 已补列并在唯一写入口带上（一问一答共用一个 id，与账本同源），
Redis 降级缓存与补写路径同样带着，历史接口回传 `turnId`、`done` 与接流快照也回传（当轮不刷新就有入口）。

**没做**：

- **存量气泡没有这个入口**：`turn_id` 加列之前的消息为 NULL，前端按「本轮无过程记录」处理，不拿时间去猜轮次
  （一轮多问、重新生成都会撞在一起，猜错比不显示更坏）。要补只能按需回填，成本高于收益——**当前结论是不补**。
- **版本组的 turnId 归属要留意口径**：编辑重发/重新生成产生的每一行都带**自己那一轮**的 id（各版本本就是独立执行，
  回放各自的过程才如实）。切回旧版本时看到的「过程」是那次执行的账本，不是当前这轮的——不是 bug。
- **没建 `turn_id` 索引**：目前没有「按 turn_id 查消息」的读口（消息总是按会话整取）。
  P1 的「整轮重发 / `ChatCommand` 带轮次身份」真要用时再补 `KEY idx_turn_id`，代价小。
- **H5 端面板：2026-10-11 已补**。渲染与取数抽成两端共用的 `web/src/components/SessionEventsPanel.vue`
  （PC 的 a-modal 与移动壳的 `MobileEventsSheet` 各只是外壳），移动壳顶栏加「过程」入口、
  单轮 sheet（`MobileRoundSheet`）加「看这一轮的过程」；没有 turnId 的回答不露这个入口（按时间猜轮次比不显示更坏）。
  真机（触屏 390×844 + 本机 dev 5800）：顶栏开 sheet 列出 1 轮 8 条、展开看到事件行、按轮打开标题为
  「执行过程 · 这一轮」、打开后不横向溢出；PC 侧同一次重构回归通过（头部按钮 + 逐气泡按轮）。
  `scripts/check-h5.mjs` 加了第 ⑨ 段把「两端共用一份、移动壳不许没有、面板挂载即取数、失败要出声并给重试」钉住。
- **账本与消息的对照视图**：现在只列事件，不回答「这一轮为什么这么答」。要做成正文与事件并排对照才算完善。**代价偏大**，属质量治理线的活。

### 3. 断线重连——多端同看与「谁先看到」的语义没定口径

**现在**：一轮可挂多条通道（多标签/多设备），宽限 `chat.detachGraceMs` 默认 180 秒；提问/计划等待豁免宽限。

**没定/没做**：

- **审批卡挂到谁身上：2026-10-11 已做**。`c_ai_tool_approval` 补 `turn_id`（与 `c_ai_message.turn_id` 同源，
  三处落库点——工具审批 / 提问卡 / 计划卡——都带上本轮 id）；`/tool-approval/pending`、`/ask-user/pending`、
  `/plan-approval/pending` 出参加 `turnId`；前端 `useChatEngine.cardTargetFor()` 按它认气泡：
  这台设备手上的流要么没有轮身份（本轮助手消息还没落库）要么正是这一轮才挂它，明确不同轮就去找那一轮的气泡，
  找不到才补占位泡并盖上 turnId（存量 NULL 一律按原口径，不猜轮次）。
  真机对账（探针智能体 审批=ask 跑一整轮，用完删）：审批记录 turnId = 本轮用户消息 turnId = 落库回答 turnId 三者同一个；
  断线重载后卡片回来自如且**没有多出一颗进行中气泡**（2 行 / 重载前 2 行）。
  工作流画布的审批刻意留 NULL——那是 run 的身份，不是问答轮次。
- **游客分享会话不接**：`guestMode` 与收集型通道刻意不进总线（各有各的恢复语义）。要不要给分享页也做接流，是产品决定，不是遗漏——**当前结论是不做**。
- **工作流运行页不接**：`WorkflowRunStreamService` 有自己的快照回放，两套没统一。P1 seam 化时一起收（事件真源统一后再谈）。
- **进程重启后**：接流回 `running:false`，那半程正文是丢的（不落库）。与提问卡 `live=false` 同口径，接受。

## 三、已知小缺口（不影响主用法，看到了别当新 bug）

- 宽限中止与 `stopTurn` 都只解开审批的 future，**不**把 `c_ai_tool_approval` 那条记录写成终态，DB 会留 PENDING 直到超时路径把它落终态。审计口径问题，不是功能问题。
- 待答提问恢复时，若模型在同一轮问出第二张卡，只重建最新一张（`hydratePendingAsk` 取 `alive` 末条）。
- 接流的首帧快照与后续增量之间，靠事件序号 + 文本 `pos` 去重；非文本事件理论上仍可能重复一条（前端对 `tool_status start` 加了同名同参幂等，其余事件靠 `done` 的权威快照收口）。
- 接流来的那一轮如果收尾时带回没送达的插话（`pendingSteers`），**这台设备不代它续发**（那些插话是发起设备上的人说的）。发起设备若已经关掉，那几句就留在待插话列表里不再自动发出。
- ~~留存原文按 uid 哈希目录隔离 + meta 二次校验，但没有配额上限~~ 配额上限 2026-10-11 已补（`tool.spillMaxMbPerUser`，见 §一 第 1 条）；归属隔离与 meta 二次校验照旧。
- 配置布尔读取的默认值口径（2026-10-10 修）：`getBoolean(key, def)` 现在对**空值与缺键**都落到形参默认
  （此前 `Boolean.parseBoolean("")` 返回 false 且不抛异常，兜底链走不到第二级，「默认开的开关」在键未入库时静默变关）。
  但**一参形式 `getBoolean(key)` 对既无配置行、也未在 `ConfigService.defaults()` 登记的键仍然返回 false**——没有声明就没有默认，属预期。
  兜漏的是启动自检 `[Config][自检]`，而它只扫 schema 里 `type=switch` 且 `def=true` 的键：
  代码用 `getBoolean(key, true)` 读一个 schema 没声明默认开的键，自检管不到。

  历史接口回传 `turnId`，气泡「更多 → 看这一轮的过程」打开的是那一轮（11 条，标题「执行过程 · 这一轮」）、头部「过程」仍是会话级列表；

## 五、这三刀撞出来的四个既有缺陷（都已修，判据在此）

都不是新机制的欠账，是**早就在、静态检查全绿、只有真跑才露出来**的四条。按老规矩把判据与"为什么以前没发现"写清楚。

### 1. 审批=「每次问我」这一档自 P1 第一刀起整个是坏的（最严重）

`RagService.toolTurnContext(st)` 那个匿名 `ToolTurnContext` 里写的是：

```java
@Override public long approvalTimeoutMs() { return approvalTimeoutMs(); }   // 调的是自己
```

`ApprovalGate:50` 一读等待上限（`approver.approve(inv, turn.approvalTimeoutMs())`）就无限递归，
**StackOverflowError 直接把工具线程所在的 scheduler worker 打爆**，症状是：审批卡永远不出现、
这一轮停在"正在生成回答…"、屏幕上一点错都看不到。日志里是
`reactor.core.Exceptions : throwIfFatal detected a jvm fatal exception` 加一屏同名栈帧。

- 引入提交：`b377ccf`（P1 第一刀，守卫链接入 seam 骨架）。同文件里 `subCallTurnContext` 那一处写的是
  `return base.approvalTimeoutMs()`，是对的——只有主轮这一处漏了限定符。
- 为什么以前没发现：P1 的落地记录自己写了「审批闸只做了结构迁移，**沙盒默认关所以 ask 分支没在真机上跑到**」，
  后来又记「仍未真机验：审批闸的 ask 分支」。这次为了验刀3 才第一次把 审批=ask + 沙盒 组合真跑一轮。
- 修法：`return RagService.this.approvalTimeoutMs();`，并顺手全仓扫了同形态的自递归改写（命中 0 条）。
- 真机判据：探针智能体（审批=ask / 档位=standard）跑 `echo ping-cut3-live` → 审批卡出现 → 批准 → 回答带出输出。

### 2. 外溢原文的元信息一直没被删过（保留期清理留孤儿）

`ToolSpillService.purgeExpired()` 删 meta 时拼的是 `x.txt` + `.json` = **`x.txt.json`**，而写的时候落的是
`x.json`——所以保留期清理**只删正文、孤儿元信息永久留在盘上**，且下一轮扫描又跳过 `.json`，
它们连计数都进不去。配额淘汰复用同一个删除动作，会继承这个坑，所以一并修：
`metaOf()` 按 basename 换后缀，另在清理任务里把历史孤儿（没有对应正文的 `.json`）一次结清并打日志。
探针断言覆盖：淘汰不留孤儿、过期连 meta 一起删、扫孤儿不误伤在用原文。

### 3. 两项留存治理参数"改了看不出改过"

`tool.spillCleanupIntervalMs` 与 `cleanup.toolSpillRetentionDays` 在 `config-schema.json` 里有字段、
却没在 `ConfigService.defaults()` 登记，而 `snapshot()` **只回显 defaults() 里存在过的键**（见
`scripts/gen_config_schema.js` 开头那段说明）。症状：设置页把清理间隔改成 2 小时，重开页面又显示 3600000，
用户读成"没生效"（实际库里已经生效，跑的是新值）。这次补登记后真机复验：改成 7200000 / 3 天再取，
回显就是 7200000 / 3。新加的 `tool.spillMaxMbPerUser` 同步登记，未进漂移名单。

### 4. 占位泡的 `stage` 文案两端都没渲染（**未修，记录在案**）

`hydratePendingAsk / Plans / Approvals` 给占位气泡写了 `stage: '等你作答，回答才不会跑偏'` 之类的说明，
但 PC 模板与 `MobileMsgRow` 都不消费消息级 `stage`（grep 只有赋值点），所以那颗气泡在屏幕上就是一颗
转圈的空泡。本次没动它：改动面是"气泡头部要不要多一行状态"，属 UI 口径决定而不是归属判据，
而且我的验证断言已改成按可观测形态（末尾多一行空的 ai 气泡）而不是按文案。
