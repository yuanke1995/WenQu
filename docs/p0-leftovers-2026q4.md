# P0 收尾遗留清单（断线重连 · 大输出留存 · 过程回放）

日期：2026-10-10。配套 `docs/agent-runtime-gap-2026q4.md` 的 §三 P0（长任务可控性）。

P0 五项机制都已落地：**服务端停止本轮**、**运行中插话 steer**、**todo 逐步清单**、**会话事件账本双写**、**断线重连接流**。
这份文件只记一件事——**哪些是做成了基础版的、哪些还没做**，避免以后按「已经做完」的错觉去用它们。
代码侧的坑与判据写在项目记忆里（`project-detach-resume-run-bus`），这里只写功能缺口。

## 一、做成了基础版，需要补全的

### 1. 工具大输出留存（spill）——只救「给人看的那一份」

**现在的边界**：截断发生在 `SandboxTools.clip()`（2 万字符）与问答侧 8K 展示上限这两处，
超限时把**整份原文**落到 `data/tool-spill/<uid哈希>/`，工具卡片给「查看完整输出」按需读回，
保留期 `cleanup.toolSpillRetentionDays`（默认 7 天）+ 清理任务「工具外溢原文清理」，开关 `tool.spillEnabled`。

**没覆盖的三段**：

| 缺什么 | 为什么现在不做 | 补法 | 代价 |
|---|---|---|---|
| provisioner 侧 262144 字节帽 | 输出在进 Java 之前就被砍，Java 这层再留也留不到全文 | 改 `ProvisionerSandboxProvider` 的读回逻辑：分块读完再决定是否留存，或让 provisioner 只回传大小+前缀、原文走 `/v1/file` | 中；要动沙盒服务协议，注意别把上下文撑爆（帽子的存在就是为了这个） |
| 「可搜」只有前端按行筛 | 按行筛够用且零索引 | 服务端做检索（按 spillId 内查关键字、返回命中行号与上下文），或把原文塞进沙盒工作区让模型自己 `grep` | 小～中；后者会改变模型可见性，要先定权限档位（P2） |
| **已经覆盖全部工具**（订正：`recordToolStatus` 是所有工具结果的统一收口，`instrumentTools` 逐个包装，所以 MCP / 技能 / 联网搜索超过 8K 的部分同样进留存；`SandboxTools.clip()` 只是沙盒那层多出的一个更早的 2 万字符口） | 残留的真实边界是**磁盘配额**：只有保留期与单次 4M 字封顶，没有「每人/每会话最多留多少」的上限 | 与 P2 存储配额一起做（`ResourceVisibilityService` 那套归属已可复用） | 小到中；单独做不值，并到 P2 顺路 |

### 2. 会话过程回放——只有会话级面板，没有逐轮定位

**现在**：`GET /api/ai/session/{id}/events` 按轮倒序列最近若干轮，每条给 240 字摘要；入口是对话页头部「过程」按钮。

**没做**：

- **逐气泡入口**：`c_ai_message` 没有 `turn_id` 列，硬要靠时间对齐会错轮（一轮多问、重新生成都可能撞在一起）。补法：给消息表加 `turn_id`（`SessionService.appendToMysql` 的唯一写入口带上，SchemaMigrator 自动补列），之后每条回答下方直接给「看这一轮跑了什么」。**代价中等**：动主写入路径，要顺带决定版本组（重新生成多版）挂哪个 turnId。
- **H5 端面板**：只在 PC 做了。补法：`MobileChatPage` 头部动作行加入口，复用同一个端点与渲染（H5 用 sheet 而不是 modal）。**代价小**。
- **账本与消息的对照视图**：现在只列事件，不回答「这一轮为什么这么答」。要做成正文与事件并排对照才算完善。**代价偏大**，属质量治理线的活。

### 3. 断线重连——多端同看与「谁先看到」的语义没定口径

**现在**：一轮可挂多条通道（多标签/多设备），宽限 `chat.detachGraceMs` 默认 180 秒；提问/计划等待豁免宽限。

**没定/没做**：

- **审批卡挂到谁身上**：接流恢复的审批卡会挂到最后一条助手气泡；如果那一轮之后又有新轮（并发场景少见但可能），卡片归属会含糊。补法：审批记录带 turnId 并挂到对应气泡（依赖 §2 的 `turn_id` 列）。
- **游客分享会话不接**：`guestMode` 与收集型通道刻意不进总线（各有各的恢复语义）。要不要给分享页也做接流，是产品决定，不是遗漏——**当前结论是不做**。
- **工作流运行页不接**：`WorkflowRunStreamService` 有自己的快照回放，两套没统一。P1 seam 化时一起收（事件真源统一后再谈）。
- **进程重启后**：接流回 `running:false`，那半程正文是丢的（不落库）。与提问卡 `live=false` 同口径，接受。

## 二、明确没做的（P0 表里就没有，或排在后面）

1. **`c_ai_session_event` 的消费面只有一处**（过程面板）。事件真源统一、`deriveMessages()` 投影、历史投影切换（工具轨迹第一次回灌模型输入）都还没碰——那是路线里单列的 8–12 人日灰度项，动它要过评估集基线。
2. **P1 seam 化**（`ToolDescriptor` 单一真源 + 守卫链 + `ChatCommand`）未开工。顺带要说：本次给沙盒注入留存能力时特意走 `ToolContext` 而不是全局单例 setter，就是因为 `setSourceRegistrar/setSink` 那对单例的串号缺陷还在。
3. **P2 权限档位**（沙盒 3 档 × 审批 2 档）未开工。留存内容与「哪个用户能读哪份原文」在档位落地后要重新校核。
4. **P3a 子智能体真全循环 / P3b `run_code`** 未开工。P3b 的 spill 是「子调用结果不进上下文只回摘要」，与本文 §1 那份是两件事，别混。

## 三、已知小缺口（不影响主用法，看到了别当新 bug）

- 宽限中止与 `stopTurn` 都只解开审批的 future，**不**把 `c_ai_tool_approval` 那条记录写成终态，DB 会留 PENDING 直到超时路径把它落终态。审计口径问题，不是功能问题。
- 待答提问恢复时，若模型在同一轮问出第二张卡，只重建最新一张（`hydratePendingAsk` 取 `alive` 末条）。
- 接流的首帧快照与后续增量之间，靠事件序号 + 文本 `pos` 去重；非文本事件理论上仍可能重复一条（前端对 `tool_status start` 加了同名同参幂等，其余事件靠 `done` 的权威快照收口）。
- 接流来的那一轮如果收尾时带回没送达的插话（`pendingSteers`），**这台设备不代它续发**（那些插话是发起设备上的人说的）。发起设备若已经关掉，那几句就留在待插话列表里不再自动发出。
- 留存原文按 uid 哈希目录隔离 + meta 二次校验，但没有配额上限（只有保留期与单次 4M 字封顶）；P2 落地时应把它算进存储配额。

## 四、验证欠账（数据侧已验，手点没点到）

- 「查看完整输出」那颗按钮的实际点击（隐藏浏览器面板下工具卡折叠层级定位不稳，`.spill-btn` 未命中；原文落盘、`spillId` 进消息 JSON、端点与白名单都已实测通过）。
- `stopTurn` 收尾即时性、前端重试用例落空后的收尾——属「不再发生坏事」类，只做了代码级收口，没构造出可观测窗口。

要补验时最快的路径：新开一条会话 → 让智能体跑 `yes ABC | head -n 9000` → 展开工具卡 → 点「查看完整输出」→ 在弹窗里筛 `ABC`。
