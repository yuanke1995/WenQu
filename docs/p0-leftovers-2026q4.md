## 一、三项能力的真实边界（基础版已补全，剩下的是刻意不做）

### 1. 工具大输出留存（spill）——整份原文、可搜、可续读

**现在的形态**：截断发生在 `SandboxTools.clip()`（进模型 2 万字符）与卡片展示 8K 这两处；超限时整份原文落
`data/tool-spill/<uid哈希>/`，卡片「查看完整输出」按需读回。读回有三种看法（`GET /api/ai/tool-output/{id}`）：
不带参数=从头一段（512K 字符，响应里 `next` 是下一段起点）；带 `offset`=按字符续读；带 `line=`=按**行窗口**读
（自动给命中行留 20 行上文，一次最多 500 行）。找词走 `GET /tool-output/{id}/search?q=`——它扫的是盘上那份
**整份**原文，返回命中行号 + 字符偏移，前端点一行就跳到那一行。每人配额 `tool.spillMaxMbPerUser`（默认 200MB）、
保留期 `cleanup.toolSpillRetentionDays`（默认 7 天）、总开关 `tool.spillEnabled`。

**订正（2026-10-12 实测，原条目写的两处都不准）**：

| 原结论 | 实测 |
|---|---|
| 「输出在进 Java 之前就被 provisioner 砍到 262144 字节」 | 262144 那道帽**在 Java 侧**（`ProvisionerSandboxBackend` 同步路径留头、流式路径留尾）。镜像侧的帽是另一件事：`/v1/shell/exec` 只回**最后约 1 万行**（实测 5 万行只回 10,013 行 / 90,116 字节），响应里**没有任何"被砍"标记**，`truncate=false` 也一样 |
| 「要拿全文得改沙盒服务协议」 | 不用。问答走的流式路径读的是沙盒里的 **log 文件**（`/v1/file/read`），实测 10MB 单行、10 万行 11MB 都整份回传无帽——全文本来就在 JVM 手里，缺的只是别在截断时把它扔掉。这一刀改的就是：`ExecuteResponse` 多带一个 `fullOutput`（砍之前的整份，超 6M 字符不保留），`clip()` 把它交出去留存 |
| 「同步 exec 路径同样能拿全文」 | **不能**，而且是静默的：命令直接经 `/v1/shell/exec` 返回时，第 1 万零一行到第 5 万行在容器里就被丢了，Java 无从补。受影响的只有**没有输出回调**的调用方（子智能体分支、工作流代码节点、沙盒浏览面板跑脚本）；问答主链路必带回调，不受影响。要补得把同步路径也改成「输出重定向进文件再读回」，代价是每条命令多两次往返，本轮没做 |
| 「前端按行筛够用」 | 只对**已读回那一段**够用：一次读回上限 512K 字，一份 300 万字的日志里报错在第 280 万字处，前端筛什么都筛不到。故补服务端检索 + 行窗口跳读 |

**进模型的那一份刻意没动**：`clip()` 仍砍 2 万字符、`maxOutputBytes` 仍按字节挑一段——模型看到的形状一变，
token 预算、历史压缩口径、评估基线跟着漂移（路线文档 §风险 那条）。留存只管给人看的那一份。

### 2. 会话过程回放——按轮、两端、可对照正文

`GET /api/ai/session/{id}/events` 两种看法共用（不带 `turn`=按轮倒序最近几轮；带 `turn=`=那一轮正序摊开），
`c_ai_message.turn_id` 在一问一答两个行上都带（与账本同源），PC 头部「过程」+ 逐气泡入口，H5 顶栏 + 单轮 sheet，
两端共用 `web/src/components/SessionEventsPanel.vue`。

**2026-10-12 补的**：
- **对照正文**（回答「这一轮为什么这么答」）：按轮回放时面板默认左正文右账本，工具步与账本的终态工具行
  **按同一个编号**互相对应（第 i 个终态工具事件 ↔ 回答里第 i 个工具卡），点任一侧另一侧高亮；
  会话级列表没有「对着哪条回答」的问题，所以只有按轮模式才有这个开关。
  编号能对上靠的是新加的读口字段：`eventItem` 对 `type=tool` 的行解出 `name/status/elapsedMs`——
  原来只给 240 字摘要，摘要可能正好切在 `status` 之前，前端数不出第几步。
- **事件类型标签补齐**：`approval_required`、`steer`（中途插话）、`interrupted` 以前没进标签表，界面上显示成英文原名。
- **存量轮身份回填**（原结论「成本高于收益，不补」已翻案）：`SessionEventService.backfillTurnIds(dryRun, limit)`
  按「一轮时间窗里恰好只对上一个问题」这一条判据补，对不上就整窗跳过。**能补出来的量很小**：账本 2026-10-09 才开写、
  消息行的 turn_id 列 10-10 上线、账本还只保留 30 天——交集就那么几天。所以它是 `trace.turnIdBackfill`
  默认关的一次性补账开关（打开→重启跑一次→日志报「补了几行 / 因二义跳过几窗」→关回），不做一个长期任务。
  没补 `KEY idx_turn_id`：至今没有「按 turn_id 查消息」的读口，回填本身是按会话取再内存配对。

**仍然刻意不做**：猜轮次。账本上线之前的消息留着 NULL，前端按「本轮无过程记录」处理——一轮多问、重新生成
都会撞在一起，猜错是比缺失更坏的账本。

### 3. 断线重连——问答、分享页、工作流三条链路都在同一条总线上

`ChatRunBus` 现在是**两条链路共用的运行总线**：问答按 `sessionId`，工作流按 `wf:{runId}`（`WorkflowRunStreamService`
从「自带一条通道」改成它的第二个使用方）。宽限 `chat.detachGraceMs` 默认 180 秒；提问/计划等待豁免宽限。

- **游客分享页接流**（原结论「是产品决定不是遗漏」已翻案）：游客轮也登记总线，但归属用**访客身份**
  （`share-visitor:{客户端随机}`）而不是发布者 uid——`ChatCommand.guestUid` 就是为这件事加的；用发布者的 uid 挂归属
  等于任何拿到链接的人都能接走别人会话的流。新增 `GET /share/{token}/chat/resume`、`GET .../chat/run`
  两个免登录端点（访客标识 + 会话归属校验放行）。
  顺带补了 **`POST .../chat/stop`**：轮既然挂上总线，前端 abort 只掐自己那条通道，后台会跑满宽限期白烧发布者额度——
  游客的「停止」必须打到服务端。授权先按访客认会话归属，过了再按发布者 uid 叫停（本轮的执行身份就是他）。
  访客标识缺失（老链接没带 visitorId）退回**不登记**，绝不退成「按发布者放行」。
- **工作流运行页接进总线**（原结论「等 P1 seam 化后再谈」已翻案）：补掉三件旧实现真做不到的事——
  ①单订阅者（后订阅顶掉先订阅，两个人看同一次运行时先开的那个静默失去更新）；
  ②跑到一半刷新（旧快照取自 run 行的 `node_traces`，而那一列**只在收口时写**，所以中途重连是「状态在跑、时间线空白」；
  现在快照取自内存事件缓冲，已跑过的节点都回放得出来）；③重复事件（帧带本轮单调序号，前端按快照序号去重）。
  两处与问答刻意不同：**没有宽限期**（观众全走也不中止，任务要跑完才叫结果），也不受 `chat.resumeEnabled` 影响
  （那个开关管的是问答「断开即中止」的旧行为回滚，工作流没有这个旧行为可退）。
- **进程重启**（原结论「与提问卡 live=false 同口径，接受」已翻案）：`ContextClosedEvent` 监听把还在跑的每一轮
  按**重启专属**的截断文案落库（`RESTART_SUFFIX`：「服务在这一轮中途重启」——写成「已停止本轮」会让人以为是自己手滑停的），
  补一条 `stop` 账本留痕，并立刻 `chatRunBus.finish` 让接流的观众当场看到停。
  为什么走事件而不是 `@PreDestroy`：同一个 bean 上多个 `@PreDestroy` 不保证顺序，而容器关闭事件先于所有 bean 销毁——
  必须抢在 `pipelineExecutor.shutdownNow()` 之前读到状态表、抢在 DataSource 关掉之前写完。
  边界照旧：跨进程**续跑**不做（跑一半的 LLM 流接不回来），这条只是不再把已经产出的部分弄丢。

   （工具轨迹第一次回灌模型输入）都还没碰——那是路线里单列的 8–12 人日灰度项，动它要过评估集基线。

5. **接流设备不代发起设备续发插话**：那几句话是发起设备上的人说的，换一台机器替他发出去是错的语义——保持原样。

  没有声明就没有默认，属预期。兜漏的是启动自检 `[Config][自检]`，而它只扫 schema 里 `type=switch` 且 `def=true` 的键。

## 四、真机验证结果（2026-10-12 已跑完，含触屏一屏；本机 8090 + 5800 + provisioner 8002）

**验过并通过的**（行为断言，不是代码推断）：

1. **留存拿到整份原文 + 分段续读 + 服务端检索 + 跳读**（① ②）：问答里让智能体跑 `seq 1 300000` → 盘上落 **1,988,895 字节**（改动前这份最多 262,144 字节）；`GET /tool-output` 第一段 524,288 字、`more=true next=524288`，按 `next` 拼回去**与盘上字节数一字不差**；`/search?q=299999` 扫 30 万行给出 `line=299999 offset=1988881`。浏览器里点开「查看完整输出」：自动进按行模式（`共 300,000 行 · 1,988,895 字`、200 行一页、上一页在第一页禁用），搜「299999」命中 1 处，点命中跳到 299979–300000 且**命中行高亮在第 21 行**（留了 20 行上文）。
2. **人在回路卡片落终态**（③）：探针智能体（档位=常规 / 审批=每次问我）跑 `echo` → 审批卡挂起 → `POST /chat/stop` → `c_ai_tool_approval.status=STOPPED`、`resolved_at` 写上、`/tool-approval/pending` 清零。**这一刀真机抓出我自己的一个错**：原先把落库放在 `disposeSafe()` 之后，而 `disposeSafe()` 会中断正阻塞在 `future.get()` 上的工具线程（走 `InterruptedException` 分支，既不落库、`finally` 还把挂起项摘掉），等到 `releaseHumanWaits` 时表已经是空的——日志里先出「审批未通过 outcome=CANCELLED」再出「解开人工等待 命中=0/0/0」，叫停接口照样返回成功。改成**掐流之前先落终态**（`markHumanWaitsTerminal`）后验通。
3. **游客分享页接进总线**（⑥）：免登录发一轮 → `GET /share/{token}/chat/run` 回 `running:true + turnId + viewers:1`；换一个 `visitorId` 打同一个会话 → **403「无权访问该会话」**（连「在不在跑」都不告诉别人）；`/chat/resume` 接上的那条通道 10 秒内拿到快照，之后**实到 162 条 token 增量、1004 字**并收到 `done`；`POST /chat/stop` 打到服务端后探测转 `running:false`。
4. **工作流运行页接进总线**（⑦）：建一条 start→llm→llm→end 的流程异步跑，两个订阅者**同时**收到 `trace/trace/trace/done`（旧实现后一个会顶掉前一个）；第 9 秒接上的订阅者快照里 `traces=['a']`（旧实现这里必是空白，因为 run 行的 `node_traces` 只在收口时写）；第 16 秒接上的回放全部 3 个节点。
5. **进程重启半程正文落库**（⑤）：正出字 321 字时 `SIGTERM` → 日志 `[SHUTDOWN] 进程收尾：1 轮在跑的半程正文已按中断态落库`；库里那一行 assistant 正文 347 字、`turn_id` 已带，尾部标记是重启专属那句「> ⏹ 服务在这一轮中途重启，以上为已生成的部分」（不是「已停止本轮」），账本另有一笔 `stop / 进程收尾中止：正文 321 字、工具步 0 步`。
6. **存量轮身份回填**（⑨）：开关打开+回读正确（默认关的键也登记进 `defaults()` 才回显，这是 §五.3 那条坑的复现点）；重启一次 → `[回填] 会话 185 个 · 轮窗口 59 个 · 补 68 行 · 因二义跳过 19 个`，库里 NULL 行数 519 → 451（差 68 对得上）。效果真看得见：一条 **2026-10-09** 的老回答（补账前不可能有轮身份）现在「更多 → 看这一轮的过程」打得开，9 条账本、4 个工具步与正文卡片同编号。跑完已把开关关回。
7. **对照视图**（⑧）：面板默认进对照（左正文右账本），左栏「1 execute 完成 3198ms」与右栏编号「1」的那条工具终态行同序号；点账本行两侧同时高亮。事件类型标签不再露英文原名。

8. **触屏一屏端到端**（补上一屏没目视的欠账）：`playwright-core` + 系统 Edge，390×844 / hasTouch，
   13 条断言全过——移动壳确实挂载（`.mrow` 在、没有 `.bubble.ai` 串到 PC 模板）、单轮 sheet 里有
   「看这一轮的过程」、点开后面板取到 9 条事件并**默认进对照**（正文侧 1 个工具步、账本侧 1 个编号行联动）、
   事件类型全是中文标签、**横向溢出 0px**；同一份组件里「查看完整输出」在触屏上也是按行窗口
   （`共 300,000 行 · 1,988,895 字`、一页 200 行），服务端检索命中 1 处，点命中跳读并**高亮在第 21 行**。
   跑法：`cd /tmp/wq-verify && node h5-full.cjs [可复用的会话 id]`（前置：本机后端 8090 + vite 5800，

## 五、这三刀撞出来的四个既有缺陷（都已修，判据在此）

都不是新机制的欠账，是**早就在、静态检查全绿、只有真跑才露出来**的四条。按老规矩把判据与"为什么以前没发现"写清楚。

### 1. 审批=「每次问我」这一档自 P1 第一刀起整个是坏的（最严重）

`RagService.toolTurnContext(st)` 那个匿名 `ToolTurnContext` 里写的是：

```java
@Override public long approvalTimeoutMs() { return approvalTimeoutMs(); }   // 调的是自己
```

`ApprovalGate:50` 一读等待上限（`approver.approve(inv, turn.approvalTimeoutMs())`）就无限递归，
**StackOverflowError 直接把工具线程所在的 scheduler worker 打爆**，症状是：审批卡永远不出现、
这一轮停在"正在生成回答…"、屏幕上一点错都看不到。日志里是
`reactor.core.Exceptions : throwIfFatal detected a jvm fatal exception` 加一屏同名栈帧。

- 引入提交：`b377ccf`（P1 第一刀，守卫链接入 seam 骨架）。同文件里 `subCallTurnContext` 那一处写的是
  `return base.approvalTimeoutMs()`，是对的——只有主轮这一处漏了限定符。
- 为什么以前没发现：P1 的落地记录自己写了「审批闸只做了结构迁移，**沙盒默认关所以 ask 分支没在真机上跑到**」，
  后来又记「仍未真机验：审批闸的 ask 分支」。这次为了验刀3 才第一次把 审批=ask + 沙盒 组合真跑一轮。
- 修法：`return RagService.this.approvalTimeoutMs();`，并顺手全仓扫了同形态的自递归改写（命中 0 条）。
- 真机判据：探针智能体（审批=ask / 档位=standard）跑 `echo ping-cut3-live` → 审批卡出现 → 批准 → 回答带出输出。

### 2. 外溢原文的元信息一直没被删过（保留期清理留孤儿）

`ToolSpillService.purgeExpired()` 删 meta 时拼的是 `x.txt` + `.json` = **`x.txt.json`**，而写的时候落的是
`x.json`——所以保留期清理**只删正文、孤儿元信息永久留在盘上**，且下一轮扫描又跳过 `.json`，
它们连计数都进不去。配额淘汰复用同一个删除动作，会继承这个坑，所以一并修：
`metaOf()` 按 basename 换后缀，另在清理任务里把历史孤儿（没有对应正文的 `.json`）一次结清并打日志。
探针断言覆盖：淘汰不留孤儿、过期连 meta 一起删、扫孤儿不误伤在用原文。

### 3. 两项留存治理参数"改了看不出改过"

`tool.spillCleanupIntervalMs` 与 `cleanup.toolSpillRetentionDays` 在 `config-schema.json` 里有字段、
却没在 `ConfigService.defaults()` 登记，而 `snapshot()` **只回显 defaults() 里存在过的键**（见
`scripts/gen_config_schema.js` 开头那段说明）。症状：设置页把清理间隔改成 2 小时，重开页面又显示 3600000，
用户读成"没生效"（实际库里已经生效，跑的是新值）。这次补登记后真机复验：改成 7200000 / 3 天再取，
回显就是 7200000 / 3。新加的 `tool.spillMaxMbPerUser` 同步登记，未进漂移名单。
**同一课又上了一次**：本轮新加的 `trace.turnIdBackfill` 是默认**关**的开关，也一并登记进 `defaults()`——
默认关的键不登记不会行为错，但设置页不回显，用户打开后重开页面看到"关"，读成"我刚才没点上"。

### 4. 占位泡的 `stage` 文案两端都没渲染（**未修，记录在案**）

`hydratePendingAsk / Plans / Approvals` 给占位气泡写了 `stage: '等你作答，回答才不会跑偏'` 之类的说明，
但 PC 模板与 `MobileMsgRow` 都不消费消息级 `stage`（grep 只有赋值点），所以那颗气泡在屏幕上就是一颗
转圈的空泡。本次没动它：改动面是"气泡头部要不要多一行状态"，属 UI 口径决定而不是归属判据，
而且我的验证断言已改成按可观测形态（末尾多一行空的 ai 气泡）而不是按文案。
