## 一、一句话定位（推荐 + 备选）

**推荐（对外主句）**

> **问渠是一个把答案说得出来源的私有化 AI 平台：问得出引用，调得成服务。**

配套三段（官网首屏副文，各一句，不铺开）：

- **答得准，也敢被查**：每个结论带 `[N]` 角标，点开是知识块原文与原文档位置级截图。
- **知识是活的**：差评、无命中问题、检索评测三路回流，缺口一键补块，越用越准。
- **答案能直接被系统调用**：同一个知识库，网页能问、API 能调、MCP 能给 Cursor 用、链接能分享出去。

**备选 A（更偏"平台"，适合投标/大客户材料）**

> 问渠是私有化部署的企业知识平台：把散在文档与人脑里的答案收成一处，每条答案可溯源、可治理、可对外提供服务。

**备选 B（更偏"工作台"，适合产品页/开发者）**

> 问渠把「知识库 + 智能体 + 沙盒 + 工作流」装进一套私有化工作台：模型自己选，数据不出内网，答案带出处。

**已排除的写法**（别再回到这些上面）：

| 写法 | 为什么排除 |
|---|---|
| 「以智能体为核心的 AI 工作台，覆盖 X→Y→Z→W 完整链路」 | 这是能力清单不是定位。五个箭头读完记不住一句，官网首屏放它就等于没有首屏 |
| 「通用智能体平台」 | 与 Dify/Coze 正面撞定位，而编排生态不是我们的强项（见 §四-3） |
| 「企业级」（9-27 已全局去掉） | 无依据的形容词，去掉是正确的，别加回来 |
| 「文档问答助手」（9-27 前的旧定位） | 已经装不下现状：知识只是入口，服务化交付才是长出来的那一半 |

## 三、三个能用画面讲清的场景（官网、销售、演示共用）

### 场景 1 · 问一句，拿到带出处的答案
- **谁**：业务岗
- **做什么**：问「这个季度的报销标准变了吗」「上一版合同模板里违约金怎么写的」
- **看到什么**：流式回答 + 句末 `[N]` 角标 → 点开是知识块全文与图文交错的原文档截图；回答下方检索状态行可展开全部命中来源
- **凭什么选我们**：市面上能答的产品很多，**能答且当场敢被点开核对**的少。这条是产品名「问渠那得清如许，为有源头活水来」的字面兑现，也是唯一一个不需要向用户解释的卖点
- **依赖的已落地能力**：混合检索（向量+关键词双命中叠加）、查询改写、重排、父子分块、GraphRAG 一跳扩展、引用配额与相关度门

### 场景 2 · 让一个部门的知识能被全公司问，而不必反复答
- **谁**：法务／人事／客服负责人 + 全公司提问者
- **做什么**：该部门把自己的资料建成库，配一位智能体（人设+知识范围+工具），全公司直接问那一问
- **看到什么**：对话页不必"先选人"——不挑用默认助手，跨主题的问题由模型经 `consultAgent` 派给职责对口的助手去查，对方带着自己的库跑完整子轮，结论与引用交回，回答仍由当前助手汇总
- **凭什么选我们**：**知识驱动的子智能体**是 DSH 这类本机 runtime 结构上做不出的形态（它没有内建记忆、RAG、向量库），也是 Dify 系"由你搭编排"之外的另一条路——**不由用户搭流程，由模型按知识域分工**
- **依赖的已落地能力**：P5「agent-as-tool」、子轮独立知识域、父轮二次过门与引用配额、`subagent_route` 挑选理由随 SSE 下发

### 场景 3 · 把答案交付出去，而不是留在对话框里
- **谁**：运营／分析岗 + 内部系统集成方
- **做什么**：让智能体跑一段代码出图表、把结果交成产物卡片；或者把这条链路接进公司自己的系统
- **看到什么**：沙盒容器里执行 shell／读写文件（输出实时流式回传）→ `deliver_artifact` 落到「我的产物」，签名 URL 可预览可下载；再往前一步，同一个智能体发布成 MCP 端点，Claude/Cursor 直接粘地址就能调
- **凭什么选我们**：**"智能体即服务"是四条差异化里工程投入最小、外部感知最快的一条**——对外 MCP server（含调用审计）、免登录分享页、工作流 API 触发、H5 外壳，四件都在，缺的只是被讲出来和开起来
- **注意**：本场景能力**默认全关**，见 §五-2

## 四、和谁不一样（诚实版，含我们不占优的地方）

### 1. 对照表

| 产品 | 它最强的地方 | 问渠的差别 |
|---|---|---|
| **Dify** | 编排广度、插件与社区生态、模板市场 | 它从"编排"出发，知识只是节点之一；问渠从"知识+溯源"出发，编排是结果的延伸。**在广度上不要和它比**（见 §四-3） |
| **FastGPT** | 知识库问答做到极致、流程编排友好 | 形态最接近的对手。问渠的差别在**三重收口**：答案可溯源到原文位置、知识可治理（缺口/坏例/评测回流）、能力可对外（MCP/API/分享）。它更"问答"，我们更"平台" |
| **RAGFlow** | 解析深度与版面识别（DeepDoc） | **解析上我们不占优，也不该硬拼**。我们已把 OCR/版面引擎做成可插拔（PaddleOCR PP-StructureV3 / MinerU / 视觉模型三路可选）——定位是"接得住好引擎"，不是"自己造引擎" |
| **DSH / Claude Code 类本机 runtime** | 单机开发者的编码与长任务体验 | 形态不同不是优劣：它没有内建 RAG／记忆／多租户／计费；我们的沙盒是**同步一次性 HTTP**、没有持久 PTY／LSP／worktree。**别把用户往这条赛道上引** |
| **MaxKB / WeKnora 等** | 轻量、开箱即用 | 我们在"轻"上不占优（部署面比它们重：MySQL+Redis Stack+Meili+Docker 沙盒）。差别在深度治理与对外服务化 |

### 2. 差异化分层（按"别人补起来的难度"排，不是按我们写代码的辛苦程度排）

| 层 | 能力 | 别人复制的难度 | 为什么 |
|---|---|---|---|
| **护城河** | 引用溯源体系 + 混合检索 + 质量治理闭环 | 高 | 单点功能都能抄，但这套是**互相咬合**的：任何把命中送进上下文／引用／节点结果的路径都必须先重排再卡门，阈值作用域还分两域（重排 0.6／融合 0.5）。抄一个函数没用，要抄整条口径 |
| **护城河** | 多租户治理（RBAC + 用量记账 + 配额 + 可见性两级判定） | 高 | 记账在路由出口统一收口、`ModelQuotaGuard` 是唯一判定出口、裸 429 与额度不足互斥、可见性必须在发起检索前收窄。这些是"事后加不上去"的设计 |
| **主场** | 智能体即服务（MCP 双向 / 分享页 / API 触发） | 中（易做，但已做且见效快） | 服务端形态天然具备；本机 runtime 结构上做不到 |
| **主场** | 知识驱动的子智能体（`consultAgent`） | 中高 | 需要 RAG + 记忆 + 分支编排三者齐备 |
| **主场** | 跨设备人在回路（提问卡／审批卡／计划卡三卡跨刷新恢复） | 中 | 服务端才有；本机 runtime 反而做不到 |
| **长板但不独特** | 知识库解析（OCR 三路）、可视化工作流 11 节点、MCP 双向 | 低—中 | 市场已有成熟做法，**够用即可，别加码** |
| **轻差异** | 长期记忆、产物交付、运营看板 | 低 | 保留，但不作为首屏卖点 |

### 3. 明确不做的（写下来是为了挡住下一轮"顺手也做了吧"）

| 不做 | 理由（有据） |
|---|---|
| **不做通用编排平台的广度竞赛** | 不做插件市场、不追节点数量、不追社区模板。我们的 11 类节点是"够用"，不是"最多" |
| **不自研文档解析引擎** | 接 PP-StructureV3／MinerU／视觉模型，保持 SPI 可插拔。省下的时间投到答案质量 |
| **不做面向个人开发者的本机编码助手** | 沙盒是同步一次性执行，没有持久 PTY／LSP／worktree，形态优势为零 |
| **不做第三方带代码的插件运行期装载** | 共享 JVM 里跑第三方字节码 = 供应链风险进安全边界。唯一正确形态是进程外 sidecar，独立立项，不在本路线内 |
| **不追模型数量当卖点** | 供应商是用户自登记的 OpenAI 兼容网关。**"支持 N 个模型"不是差异，是噪声** |

### 2. 差异化能力默认关（决定"首装印象"）

| 配置键 | 默认 | 后果 |
|---|---|---|
| `agent.enabled` | false | 场景 2 的多智能体分工新用户看不到 |
| `tool.sandbox.enabled` | false | 场景 3 的沙盒执行看不到 |

这些"默认关"当初都有正当理由（安全边界、成本闸、能力形态变化由管理员决定）。但结果就是：**定位讲的和首装体验是两件事**。建议按新定位重排默认值——至少把"零副作用、零成本风险"的项打开（`tool.todo.enabled`、库级 GraphRAG 属于此类），把有副作用的三项（沙盒／run_code／MCP 服务端）改成**首次登录时的引导式开关**，而不是埋在设置页。

### 3. 词不对：对话不只是 UI，是运行时

`ChatController` **42 个端点**，是第二大控制器（`WorkflowController` 27）的两倍。里面装着停止、插话（steer）、断线重连、附件、计划裁决、工具审批、子对话卡、编辑重发……对外却只用「智能对话」四个字概括。

**建议口径**：把「智能对话」改成 **「能干活的对话」**，并在功能列表里明确点出可感知的运行时能力（随时停止、跑动中插话、刷新后过程完整重建、跨设备裁决挂起的计划/审批）。这四项 DSH 有、多数国产平台没有，而且用户当天就能感知。

## 六、必须拍板的三个开放项（定了才能冻结本稿）

### D1 · 单品还是平台？（影响最深的一个）
- **A. 单客户私有化产品**：一套部署服务一家公司。默认值、文案、引导都围绕"一个组织的知识中枢"设计。
- **B. 多租户平台**：一套部署服务多家。要加强租户隔离、配额、计费、开通流程。
- **现状证据**：代码两边的痕迹都有——RBAC/OIDC/成员管理偏 A；`UsageLedgerService`/`ModelQuotaGuard`/多副本水平扩展偏 B。
- **我的建议：先按 A 做**（当前线上就是单实例单公司，官网清单里还卡在域名与备案），B 的能力保留但不作为对外叙事，等第二家真客户再翻。

### D2 · 主用户是业务岗还是技术岗？
- **A. 业务岗的知识工作者**（推荐）：首屏讲"问出答案"，智能体与工作流降为进阶能力。
- **B. 懂技术的自动化建设者**：首屏讲"造智能体"，知识库降为数据源。
- **现状证据**：主链路与默认值更像 A；但最近 30 天的投入全在运行时（偏 B 的深度）。
