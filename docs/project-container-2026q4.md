## 一、设计：Project 是什么，不是什么

### 是

一个**属于单个用户**的、**可长期存在**的工作容器，把「一个工作目录 + 若干次会话 + 若干份产物 + 知识/智能体配置」收在一个根下。

```
Project（归属 uid）
  ├─ workdir_path   工作区目录（沙盒在此落盘，跨会话、跨容器重建都还在）
  ├─ conversations  多次讨论（session.project_id）
  ├─ artifacts      多份交付物（artifact.project_id）
  ├─ knowledge/agent 该工作区默认用哪套知识范围与助手（可为空=跟随使用者可见范围）
  └─ scheduled     定时任务（可选，二期）
```

### 不是（写下来是为了挡住下一轮"顺手也做了吧"）

| 不是 | 理由 |
|---|---|
| **不是团队协作空间** | 工作区归属 `uid`，不是部门也不是租户。D1=A（单客户私有化）且 `tenantId` 零命中——**引入共享工作区等于引入一套新的权限模型**，那不是本卡范围 |
| **不是编排单元** | 不装工作流定义、不做画布。工作流是"怎么跑"，工作区是"在哪跑、跑出了什么"。定位稿 §四-3 明确不做编排广度竞赛 |
| **不是新的权限墙** | `project` 不改检索可见性。库里 `walled` 口径（登录页父轮不限库）是 P5 有意解绑的，别顺手加回来 |
| **不是必填概念** | **兜底容器自动创建**。用户不建工作区也能照常问答——只是产物开始有归属。这是本卡能不能不破坏现有体验的关键 |

### §一-5 · 最小字段集（对齐 `Yuxi` 的已验证形状，砍到够用）

```sql
CREATE TABLE IF NOT EXISTS `c_ai_project` (
    `id`             VARCHAR(64)  NOT NULL COMMENT '工作区 UUID',
    `uid`            VARCHAR(64)  NOT NULL COMMENT '归属用户（单用户容器，不做共享）',
    `name`           VARCHAR(255) DEFAULT NULL COMMENT '工作区名；implicit 容器可为空（前端显示「兜底容器」）',
    `selection_status` VARCHAR(20) NOT NULL DEFAULT 'selectable' COMMENT 'implicit=每人一个自动默认 / selectable=用户可显式选',
    `workdir_path`   VARCHAR(512) NOT NULL COMMENT '工作区目录（相对 user-data 根的 POSIX 相对路径；provisioner 侧 normalize_workdir_path 会拒绝对路径与非法分量）',
    `directory_mode` VARCHAR(20)  NOT NULL DEFAULT 'managed' COMMENT 'managed=平台托管 / linked=关联已有目录（二期）',
    `status`         VARCHAR(20)  NOT NULL DEFAULT 'active' COMMENT 'active / archived',
    `deleted`        TINYINT      NOT NULL DEFAULT 0 COMMENT '逻辑删除',
    `idempotency_key` VARCHAR(128) DEFAULT NULL COMMENT '幂等创建键（自动建兜底容器时防并发重复插）',
    `create_time`    DATETIME     NOT NULL,
    `update_time`    DATETIME     NOT NULL,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_project_uid_implicit` (`uid`, `selection_status`, `deleted`),
    KEY `idx_project_uid` (`uid`)
) COMMENT='工作区容器：把工作目录/会话/产物收在一个可持续的根下';
```

**唯一约束只锁 `(uid, implicit)` 这一档**：每人最多一个兜底容器，用户自建工作区不限个数。`migration` 时要处理存量重复。

## 二、三条接线（本卡的全部工程量，按"发现顺序"排）

### §二-1 · 沙盒 workdir 上提（**最重要的一条，且成本最低**）

**现状取证**：
- `ProvisionerSandboxBackend` 构造器**早已接受 `workdirPath`**（`:112/:127/:143`，`null` → `""`）；
- provisioner 侧**早已实现**：`normalize_workdir_path()`（拒绝对路径、拒绝非法分量）→ `shared/{uid}/workspace/<workdir_parts>`（`app.py:210-213`）；
- **只有 `SandboxService` 四处硬编码传 `null`**（`backend` 两处：`:65`/`:95`；`available` 探测 `:77`；`release` `:105`）。

**改动**：把 `backend(sessionId, uid, …)` 的第 1 参数语义从"会话"上提为"**作用域**"，由调用方决定传 sessionId（无工作区）还是 projectId（有工作区）。

**为什么这一条就能实现"同一工作区共用一个工作区"**（机制已存在，无需新造）：

```java
// ProvisionerSandboxProvider:114
sandboxIdForThread(threadId, uid) → sha256(uid + ":" + threadId)[0..12]
```

沙盒容器 id 是 `(uid, 作用域id)` 的哈希。**把 projectId 当作用域 id 传进去，同一工作区的所有会话天然命中同一个容器与同一个 workdir**——容器空闲回收后重建，`shared/{uid}/workspace/<project>` 仍在盘上，**文件不丢**。

**收益**：
1. 工作区内多个会话共享工作区（现在跨会话互相不可见，`app.py:679-695` 注释明说"从挂载层杜绝跨会话读写"）；
2. 现有"容器空闲 60 分钟回收"不再是数据丢失风险——**这是"工作区目录"相对"会话级临时目录"最实质的差别**；
3. 不用改 provisioner 一行。

**已知取舍（诚实记下）**：工作区内**多个会话并发**时共用同一容器，彼此的 shell 进程与文件系统可见。会话级已有一轮互斥（`runtime.tryBeginTurn`），跨会话没有。**本卡先如实记录，不做工作区级互斥**——理由是当前 53 个会话/1 个活跃用户，并发冲突是理论问题；真客户出现并发工作流需求时再补（补法是 `Project` 上加一把轮级锁，不是改沙盒）。

### §二-2 · 会话与产物挂到工作区

**改动**：
- `c_ai_session` 增 `project_id VARCHAR(64) DEFAULT NULL`；
- `c_ai_artifact` 增 `project_id VARCHAR(64) DEFAULT NULL`；
- **两列都可空**——`NULL` = 没挂工作区（存量），非空 = 有归属。**不强加 NOT NULL**（见 §三 迁移）。

**读取口径**：
- 新会话：解析当前工作区（显式选中 → 否则该 uid 的 `implicit` 工作区，懒创建）写入 `project_id`；
- 产物落库：沿用产物已有的 `sessionId`（`Artifact.sessionId` 可空、已存在），**由 session 反推 project**——`ArtifactService.writeBytes` 已拿得到 sessionId，无需新增参数；
- 产物列表：`ArtifactController./list` 增可选 `projectId` 过滤（**不加就还是现在那张全量扁平表，行为不变**）。

### §二-3 · 删除工作区时的收容（安全边界）

**删除一个工作区，按"谁归谁"分三类处理**：

| 对象 | 处理 | 依据 |
|---|---|---|
| 沙盒容器与 workdir | **释放容器**；workdir **默认保留**（它是工作区的工作产出，不是缓存） | 与产物"会话可删、成果归人"同一口径 |
| 会话 | **不删**，`project_id` 置 `NULL`（退化成没挂工作区） | 会话是历史记录，删工作区不该销毁对话史 |
| 产物 | **不删**，`project_id` 置 `NULL` | `Artifact` 注释原话"产出的成果仍归人生"——**这条设计意图必须在本卡里被继续遵守** |

**明确不做**：级联删除。理由：本产品的既有设计反复强调"成果归人"，级联删除与它直接冲突；用户要清产物有独立的批量删除入口（`ArtifactController./batch-delete`）。

## 三、存量迁移（57 个产物 / 53 个会话怎么归属）

**原则：零破坏、可回退、不猜测。**

### 不做的（明确否掉）

| 方案 | 为什么否 |
|---|---|
| 按时间窗/文件名正则把存量产物分到"猜出来的工作区" | **猜测会产生错误归属**，而错误归属比"没挂工作区"更难纠正——用户没法知道系统把哪份文件分错了 |
| 强制 `project_id NOT NULL` + 按会话逐个回填 | 会话与"工作区"不是一对一（一个工作区本来就该有多次会话），回填必然造假 |
| 直接把每个会话变成一个工作区 | 会产生 53 个同名/无名工作区，把列表淹掉——**兜底容器存在的意义就是避免这个** |

### 要做的（三步，每步都可单独回退）

1. **加列（可空）+ 建表**：`schema.sql` 加 `c_ai_project` 与两个可空列，`SchemaMigrator` 自动补存量库。**此步对现有行为零影响**（不读新列 = 一切照旧）。
2. **懒创建兜底容器**：第一个**新**会话/新产物落库时，为该 uid 创建 `selection_status='implicit'` 的兜底容器（走 `idempotency_key` 防并发重复）。存量数据**一个都不动**。
3. **可选回填（不做也行）**：给一个管理员触发的迁移端点，按"同一会话的产物归到该工作区"把**已有 `sessionId` 的产物**归到该会话所属工作区——**只处理有一条明确归属链的**（artifact.session_id → session.project_id），链断的一律留 `NULL`。

**回退**：三步都不删数据、不改既有列。回退 = 停止写入新列 + 前端不显示工作区入口，**旧行为完整保留**。

## 四、四条规则（本仓既有的、本卡继续遵守的）

1. **fail-loud，不静默降级**：工作区解析失败（如 `implicit` 工作区建不出来）→ 如实告诉用户，按"无工作区"继续问答，**不假装有工作区**。
2. **不发明权限**：`project` 不是权限边界。`project_id` 只做归属与过滤，**任何检索/可见性判定都不读它**。
3. **可空即合法**：`NULL` 是一等状态（"没挂工作区"），不是待修复的脏数据。所有读路径必须容忍 `NULL`。
4. **不猜**：迁移不回填无法确定归属的数据（§三）。

## 六、两个开放项（定了才开工）

### A-D1 · 兜底容器要不要在 UI 上可见？

- **A. 完全不可见（推荐）**：`implicit` 工作区只作为后台归属容器，对话页与产物页**不出现"工作区"字样**。用户显式建工作区时才露出切换器。
  - 依据：D2 选业务岗，且定位稿 §五-2 的教训是"别让用户面对一堆要先配的东西"。**首装体验 = 还是那个问答框**。
- **B. 可见且可命名**：首装即显示"兜底容器"，鼓励用户改名。
  - 代价：多一个要理解的概念；收益是产物分组立刻可被用户控制。

**我倾向 A**：本卡的第一目标是"让产物有归属、让工作区能跨会话"，不是"教用户自建工作区管理"。可见性可以在一刀之后按反馈加。

### A-D2 · `workdir_path` 用工作区 id 还是可读名？

- **A. 工作区 id（推荐）**：`projects/{id}`——重命名工作区不影响路径，无重名冲突，无需转义中文。
- **B. 可读 slug**：`projects/{name}`——用户在沙盒里 `ls` 更直观，但要处理重名、特殊字符、重命名迁移。

**我倾向 A**，理由是本仓对路径安全已有硬口径（`normalize_workdir_path` 拒绝非法分量），**把不可信输入（用户起的名）放进路径是自找边界问题**。可读性用前端展示解决。

## 八、验收断言（真机行为，对齐 P5 卡的写法）

1. **不建工作区也能用**：全新用户不碰任何工作区设置，问答链路与今天**逐字相同**；产物照常产出。
2. **同工作区共享工作区**：同一工作区下开两个会话，会话 A 在沙盒写 `a.txt`，会话 B `ls` 看得到；换到另一工作区看不到。
3. **容器回收不丢文件**：会话 A 写文件 → 等空闲回收（或手工释放）→ 会话 B 读同一工作区，文件仍在。
4. **存量零损失**：57 个存量产物一条不少，全部显示为"没挂工作区"；**没有任何一条被猜到某个工作区里**。
5. **删除工作区不毁成果**：删除工作区后，其下产物与会话仍在（`project_id=NULL`），产物仍可下载。
6. **回归**：既有 72 项测试保持全绿；`config-schema.json` 校验通过（本卡不改配置项）。

### 施工中发现并修掉的两个真缺陷

1. **`workdir=projects/null`**：`@TableId(ASSIGN_UUID)` 在 insert 时才回填 id，而工作目录在 insert 前就用了它 → 所有用户的兜底容器会落到同一个 `projects/null`。由真实上下文集成测试当场抓出（mock 单测测不到）。修法：insert 前自行生成 id。
2. **provisioner 的 docker 路径无法共享工作区目录**：会话沙盒把 `sessions/{thread_id}` 挂成 `/home/gem/user-data`，每个会话一个独立根；工作区目录若落在那里，同工作区两个会话看到的仍是各自目录。修法（已改 `deploy/sandbox-provisioner/app.py`）：带 workdir 时改挂 **workspace 根**并预建目录，与 k8s 路径口径对齐；bind 源必须是**宿主路径**（容器内路径会报 "not shared from the host"）。

### 工作区级共享工作区：根因与验收（2026-10-17 第二轮）

**根因**：`deploy/sandbox-provisioner/app.py` 的 `_has_expected_user_data_mounts()` 把 `/home/gem/user-data` 的挂载源**写死成会话目录**。带工作区 workdir 的容器挂的是别的目录，于是 `discover()` 判定「unexpected user-data mounts」→ **直接把容器删掉** → 代理随即返回 `404 sandbox not found`。这解释了「创建返回 200 但容器立刻消失」这个自相矛盾的现象（直连创建之所以"看起来成功"，是因为出问题的环节在 discover，不在 create）。

**修法**：挂载期望按 `workdir-path` 标签分两套——无 workdir 认会话目录（原行为），有 workdir 认**工作区目录本身**。同时把工作区沙盒的挂载根从 workspace 根改成工作区目录，跨工作区隔离才成立（挂 workspace 根时实测另一个工作区的会话能读到本工作区文件）。

**真机验收（`sandbox.projectWorkdirEnabled=true`）**：

| 断言 | 结果 |
|---|---|
| 同工作区两个**不同会话**共用工作区 | A 写 `/home/gem/user-data/marker.txt` → B 读出 `SHARED-ACROSS-SESSIONS` |
| 跨工作区隔离 | 另一工作区的会话读同一路径 → `No such file or directory` / `ISOLATED` |
| 容器回收后文件仍在 | 删掉容器 + 重启应用（清连接缓存）→ 重建后仍读出 `SURVIVED-RECYCLE` |
| 每工作区一个容器 | 两个工作区 → 两个 `wenqu-sandbox-*`，同工作区内复用 |

**已知边界**：若容器被**带外删除**（`docker rm`，不经 `releaseIdle`），Java 侧连接缓存有 touch 节流窗口，窗口内的下一次调用会撞 404；正常空闲回收路径会同时摘掉缓存条目，不受影响。该边界未修（需要「404 自愈重试」），记为后续项。

**默认值**：代码默认仍为 `false`（新装不改变隔离语义：兜底容器下所有会话共用一个工作区，这是行为变化，应由部署方显式决定）；本机实例已按验收结论置为 `true`。

**真机发现并修掉的两个问题**：

1. **`create` 没有请求超时**（`SandboxProvisionerClient`）：provisioner 一旦卡住，这个调用会**永久**占住一个 Tomcat 线程，重试还会在同一把 scope 锁上叠加阻塞（jstack 实测线程停在 `send`）。已加 330s 上界（= provisioner 健康检查 300s + 余量）。
2. **「运行」按钮只有 22px 图标**：业务岗用户基本发现不了这个能力。已改成「图标 + 运行」带文字标签，并上主题色描边。

**真机发现的未解问题（如实记录）**：

- ~~**provisioner 会整体卡死**~~ → **已定位并修复（2026-10-17）**：
  - **根因**：`/health` 是 `def`（同步）端点，与所有同步端点共用 anyio 线程池（默认 40 token）。创建是最重的调用（起容器 + 等健康最长 300s），并发/中断的创建请求把 token 占满后，连 health 都拿不到线程 → 表现为「服务整体无响应」，而不是某个接口报错。
  - **修法**：`/health` 改 `async def`（只读几个属性、不做 IO，放事件循环安全）；新增**全局创建并发闸**（默认 6，排不上 15s 后快速 503 而不是继续堆线程）；同一 sandbox_id 的操作 pin 等待加 10s 上界（503）；代理路径的 `discover` 加 15s 上界。
  - **实测**：12 个不同 id 并发创建 + 40 次 health 采样 → **health 40/40 = 200**，12 个创建全部成功；20 个**同 id** 并发创建（原始卡死场景）+ 30 次采样 → **health 30/30 = 200**，20 个请求全部 200；执行链路 `echo exec-ok` 正常。
  - **未验证**：并发闸的「排不上就 503」这条分支没有被真实触发过（两次压测都在窗口内完成），属代码审查级别而非实测。
- **容器带外被删后的 stale 连接**：Java 侧 touch 节流窗口内会撞 404（`docker rm` 绕过 `releaseIdle` 时）。正常空闲回收不受影响。

### 11.7 工作区绑定工作流（2026-10-17 收尾）

- 数据：`c_ai_workflow.project_id`、`c_ai_workflow_run.project_id`（可空；SchemaMigrator 自动补齐）。
- 语义：
  1. 建/改工作流可传 `projectId`，校验归属（`ownedOrNull`，绑别人工作区 fail-loud）；

## 十二、补全为可用产品（2026-10-17 第三轮）

用户反馈「还是看不到工作区的意义」。查证结论：**机制在工作，但界面层看不到**——

### 12.1 存量归属回填（立项卡 §三 第 3 步落实）

- 新端点：`POST /api/ai/project/backfill`（管理员）；服务：`ProjectBackfillService`。
- 语义：**只处理 `project_id IS NULL` 的历史行**，归到**各用户自己的兜底容器**（先 `ensureImplicit` 再批量更新）。
  这不是"猜工作区"——这些数据产生于工作区概念出现之前，本来就属于该用户的默认容器；有归属的行一行不动。幂等。
- 实测：`{"users":24,"sessions":258,"artifacts":44}`；回填后 `NULL` 会话从 264 → 6（剩余 6 条属 `anonymous` 共享池），
  `NULL` 产物 44 → 0。
- 后果：兜底容器从"空壳"变成**该用户的全部历史**（admin：187 条会话 / 45 份产物）。
