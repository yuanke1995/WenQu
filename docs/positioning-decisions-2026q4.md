## 一、D1 · 单品还是平台？

### 推荐：**A · 单客户私有化产品**

### 取证（比定位稿更硬的一条）

定位稿 §六-D1 说"代码两边的痕迹都有"，把 `UsageLedgerService`/`ModelQuotaGuard`/多副本列为偏 B 的证据。**这条判据经审计后不成立**：

| 定位稿的判断 | 代码实况 | 结论 |
|---|---|---|
| "RBAC/OIDC/成员管理偏 A" | 成立 | 支持 A |
| "`UsageLedgerService` 偏 B" | 成立，但**记账维度是 `uid`（人），不是租户** | 公司内部成本可见性，不是跨租户计费 |
| "`ModelQuotaGuard` 偏 B" | **判据不成立**：它是解读供应商配额报错的静态工具（`isQuotaExhausted` / `isRateLimited` / `userMessage`），不做任何配额核算 | 与多租户无关 |
| "多副本水平扩展偏 B" | 多副本是**可用性**，不是租户隔离 | 与 D1 无关 |
| —— | **`tenantId` / `tenant_id` 全仓 0 命中** | **决定性：租户隔离从未建过** |

**判定**：问渠是一套**部署即单公司**的产品。它没有租户这个维度——不是"做了但不用"，是**从来没做**。把它讲成"多租户平台"，等于对外承诺一个不存在的东西，而采购方做尽调时第一轮就会问"换租户的数据怎么隔离"。

### 为什么现在不能翻成 B（三条，按推翻难度排序）

1. **租户隔离是"事后加不上去"的设计**：定位稿自己把"可见性必须在发起检索前收窄"列为护城河，而这条口径现在全都锚在 `uid` 上（`RetrievalScopeService`、`HybridRetrievalService.buildAclFilter`、`loadVisibleDocIdsOfAcl`）。改成租户要先在所有读点插入一层，正是那份稿说"事后加不上去"的同一类活。
2. **没有第二家真客户**：定位稿 §六-D1 原话"等第二家真客户再翻"。这句话到今天仍然成立——**没有任何新增证据表明出现了第二家**。
3. **对外通道还没通**：定位稿 §七 记着"官网清单里还卡在域名与备案"。多租户平台是**自助获客**形态，而连获客通道都还没搭起来。先翻 B = 为一个还没有入口的市场做隔离层。

### 推翻条件（什么情况该回来重判）

- 出现**第二家真实付费客户**且要求**共用一套部署**（不是各自私有化）；
- 或出现渠道/集成商要求"一套部署开多个账号卖给不同法人"。

任一条件成立即重判，**不必等本季度结束**。在条件成立之前，所有"平台化"的工程投入都应视为**沉没风险**。

### 对默认值与文案的直接含义

- 不引入租户层、不做开通流程、不做计费账单；
- `UsageLedgerService` 的定位**改为**"公司内部成本可见性"，对外文案只说"每个人用了多少"，不说"计费"；
- 配额相关文案统一为**供应商额度**语义，不发明"平台配额"概念（现在也没有）。

## 二、D2 · 主用户是业务岗还是技术岗？

### 推荐：**A · 业务岗**，但"建设者"要显式保留（§二-3）

### 取证：57 个真实产物的文件名就是用户画像

上一轮审计扫了 `data/artifacts/`（**真实产出，不是设计意图**），文件名分四类：

| 类别 | 实例 | 说话用户 |
|---|---|---|
| **文档/研究产出**（最大一类） | 竞业限制经济补偿-条文核查记录、四条文检索汇总、问渠十项功能查证汇总、文档解析段落清单 | 法务、研究员 |
| **方案/清单产出** | 考勤系统需求方案、智能报表系统落地实施清单、问渠官网建设清单、首页优化自查清单 | 产品、工作区管理 |
| **可交付网页** | `wenqu-home.html`×3、`index.html`×4、`wenqu-homepage.html`×2 | 运营/内容 |
| **长文档** | 问渠使用手册-知识库权限段落清单、问渠-工作流功能说明汇总 | 文档作者 |

**"条文核查""需求方案""落地实施清单""官网建设清单"——这四条没有一条是工程交付物，全部是业务岗的工作产物。** 而且注意第一类：**用户在做"核查"和"查证"**，这正是"答得准、也敢被查"那句主句的目标场景，只是它现在以"产物"而不是"对话"的形态出现。

### 反向证据（诚实列出，它偏 B 的只有这些）

- **建设者侧页面有 7 个**：`FlowEditor`（工作流画布）、`WorkflowPanel`、`AgentsPage`、`AgentsHubPage`、`SkillPanel`、`McpPanel`、`WorkflowRunHistory`——投入是实打实的；
- **近 30 天 627 笔提交全在运行时**（P5 拆派遣路由 → P6 拆 RagService → AgentScope 平移），这些投入**业务岗看不见**；
- 库里 4 个智能体里，`知识库智能体`/`法律子智能体`/`智报平台操作手册智能体` 三个都是**业务域命名**，只有内置"问渠"是产品自身。

### 判定

**用的人是业务岗，造的人是建设者，而过去 30 天只服务了造的人。** 这不是 D2 选错，是**D2 的执行偏了**——所以推荐 A 不是"放弃建设者"，而是**把资源配比扭回来**。

### §二-3 · 建设者不能降级为"进阶功能"（对定位稿 §六-D2 推荐 A 的一处修正）

定位稿说 A 档"智能体与工作流降为进阶能力"。**这句要改**，理由是取证：

- 7 个建设者页面 + 13 类工作流节点 + 24 个工具是**已沉没的成本**，降级为"进阶"等于承认这笔投入不计入叙事，下次评审就会被问"那为什么留着"；
- 更实际的是：**60 人的公司里，能让知识库被全公司问起来的那 1~2 个"知识管理员"，本身就是业务岗**（定位稿 §二 已把他们列为"次·建设者"）。他们不是工程师，是懂一点自动化的业务同学。

**修正后的口径**：主用户业务岗；**建设者是"业务岗里的那个人"，不是另一个用户群**。首屏讲"问出答案"，第二屏讲"**把你手上这摊事建成一个能反复用的东西**"——落点是"这件事以后不用再问我"，不是"来搭个工作流"。

### 对默认值的直接含义（本轮 B 阶段欠账的答案）

B 阶段要求"把零副作用零成本能力改为默认开启"。**逐项审计后结论是：真正符合"零成本"的极少，而这一项就该由 D2 定，不该由工程擅改。** 15 个默认关开关的完整裁决：

| 开关 | 表面看是"零成本"？ | 裁决 | 理由 |
|---|---|---|---|
| `chat.retrievalDebugEnabled` | 是（纯显隐） | **建议开**（但归 D2 拍板） | 它管的是`归属徽标`/`路由提示`/`降级提示`。审计发现**检索降级信息被它一起关掉了**，而本仓对降级的既定口径是"必须让用户看见"。这正是定位稿说的"不敢展示召回率"那条——**默认关等于系统性地不告诉用户检索失败了** |
| `keyword.reconcileOnStartup` | 是（单实例） | 保持关 | 真零成本仅限单实例；多副本下每个副本各扫一遍 = 真实开销。D1 选 A 后可重判 |
| `trace.turnIdBackfill` | 是（一次性） | 保持关 | 补历史账，与"用户能否感知价值"无关 |
| `tool.todo.enabled` | **否** | **不开**（定位稿 §五-2 原建议在此被推翻） | 它自己的 note 写着"开了每轮多一个工具"——**每轮 token 成本**。多步任务才用得上，一次性问答是纯损耗。定位稿把它列为"零副作用零成本"，判据不成立 |
| `memory.enabled` 相关 | 否 | 已开 | 现状已开，无需动 |
| `tool.sandbox.enabled`、`tool.runcode.enabled`、`webSearch.enabled`、`mcp.server.enabled` | 否 | **保持关** | 真实副作用/安全边界/成本，按定位稿 §五-2 原议走"首次登录引导式开关" |
| `oidc.*`（4 项） | 否 | 保持关 | 依赖客户 IdP，属地化配置 |
| `chat.agentscopeRedisEnabled` 等 4 项 | 否 | 保持关 | 多副本才需要，且属"调试设置"面板 |

**`chat.retrievalDebugEnabled` 的两个选项**（请择一，这是本稿唯一需要你二选一的工程项）：

- **方案 1（推荐）**：`def` 改 `true`，同时把 schema 里 `debug` 面板那句"生产环境建议全部关闭"改成"调试设置：控制归因与降级信息对用户的显隐"——因为**降级信息不是调试信息，是诚实性信息**。
- **方案 2（更省事）**：保持 `false`，但在对话页对"无命中/检索降级"单独走一条不受该开关管的可见通道，只把真正的排障项（步数、路由理由）留给开关。

方案 1 改动小、立刻消除"系统性沉默"；方案 2 更贴合"业务岗不该看内部术语"。**我倾向方案 1**，因为它把"检索失败"这件事从"内部排障"重新归类为"用户该知道的事"，与主句"答得准，也敢被查"同源。

## 三、D3 · 下一步投哪边？

### 推荐：**都不投——先投「工作区容器」**（这是对定位稿"B 先做一轮"的修正）

定位稿 §六-D3 的建议是"B（对外服务化）先做 1–2 周，再回 A（质量）"。理由写得很清楚："B 的代码基本都在，缺的只是开箱即用与文档，投入产出比明显更高"。

**这个判断在"代码在不在"这一层是对的，但它漏了一层：代码在，而代码的形态不支持"有状态的业务会话"。**

### 取证：四条差异化里唯一 DSH 补不了的那条，正好卡在同一个缺口上

定位稿 §四-2 把"智能体即服务"列为**主场**（别人复制难度：中，但已做且见效快）。审计四条对外通道的实际形态：

| 通道 | 代码状态 | 审计发现的形态限制 |
|---|---|---|
| MCP Server | `McpEndpointConfig` 注册 `/mcp/{token}` 与平台级 `/mcp`，**真实存在** | **无状态一次性**（`WebMvcStatelessServerTransport`，`McpServerService` 原话"每次请求都是完整的一次性对话"）；且**沙盒/产物一律不暴露**——**外部调用方拿不到交付物** |
| 对外工作流 API | `POST /api/ai/v1/workflows/{id}/run`，API Key 鉴权，只跑已发布版本 | **排除人工审核节点**（含则 400 fail-loud），"外部调用方没有审批交互面" |
| 游客分享页 | `ShareController` 10 端点，可续聊 | 访客可续聊，但**产物/沙盒/MCP 一律不对访客暴露** |
| 会话分享 | `SessionShare` 只读 | 设计如此，无缺口 |

**共同点：四条通道都停在"调一次问答"或"触发一次图"，没有一条能承载"多轮往返 + 带交付物的业务流程"。** 而这恰恰是定位稿 §四-2 说的那句"本机 runtime 结构上做不到"——**我们现在也还没做到**。

**根因就是 A 阶段要立的那个 `Project`**：external 调用方要的是"围绕一个持续存在的工作对象反复干活"，而问渠的持续载体只有**会话**（todo 挂会话、沙盒目录按 `sessions/{thread_id}` 切分且跨会话互不可见、审批挂 turn）。换个会话 = 换一个世界。

### 所以 D3 不是"质量 vs 服务化"，是同一个缺口的两种说法

- **走 B（服务化）**：要给外部一个有状态的会话——**必须先有工作区容器**，否则只是把"无状态问答"换个协议再暴露一遍；
- **走 A（质量）**：定位稿把"质量治理闭环"列为护城河，而闭环的一环是**缺口补块**（差评/无命中 → 补文档）。真实产物显示用户已经在做"条文核查""查证汇总"——**这些核查结论就是质量反馈，但它们现在只落在文件里，回不到知识库**。要回流，同样需要"这个产物属于哪个工作/哪个库"的归属关系——**还是工作区容器**。

### 修正后的建议顺序

1. **先做工作区容器**（A 阶段立项稿，1 个立项、可切 2–3 刀施工）；
2. 容器落地后，**B 的服务化只需接一根线**：把 MCP/工作流 API 的"会话"参数换成"工作区"参数，外部就能围绕工作区多轮往返；
3. 治理闭环的"产物→知识缺口"回流，在容器之上是一个**小功能**而非新体系。

### 推翻条件

- 若出现**明确的集成方需求**（某公司要接问渠做一个多轮、带交付物的业务流程），则容器立项范围立刻收紧到"只为这一个集成方服务"，不再讨论通用形态；
- 若容器施工超过 **2 周**仍不能交付最小闭环（工作区 + workdir + 产物归属），则退回定位稿原方案（先 B 后 A），**不追加投入**。
