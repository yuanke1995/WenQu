## 2. 目标与非目标

### 目标

1. 采样不再直接入集：落「待复核」态，人工采纳后才参与回归与门禁。
2. 复核有依据：能看到原轮回答与期望引用对照，判断「这题是否自包含、期望引用是否可信」。
3. （P2-b）依赖上文的轮次成为合法用例：携带前文快照回放，只评末轮。

### 非目标（本期不做）

- 不做评判模型预筛候选排序（可选增强，复核闸落地后按需评估）。
- 不做用户模拟器与 pass^k（P3）。
- 不做长任务/副作用评测（建站类题在复核时丢弃；放开副作用仍是安全边界，维持只读）。
- 不做评测集跨智能体复用/市场模板（P3）。

## 3. P2-a 采样复核闸（本期落地）

### 3.1 状态机

```
采样 ──→ pending（待复核，不参与运行/门禁）
            ├─ 采纳 ──→ approved + enabled=1（参与回归）
            ├─ 编辑 ──→ 仍 pending（改完再采纳）
            └─ 丢弃 ──→ 删除
手动新增 / 存量用例 ──→ approved（默认，行为不变）
```

- `review_status` 与 `enabled` 正交：approved 后仍可停用/启用；pending 不存在启停语义。
- 运行清单判据从「enabled=1」收紧为「enabled=1 且 review_status=approved」；
  门禁 caseCount、套件用例数同口径。显式勾选 caseIds 同样过滤 pending。

### 3.2 数据结构（V25）

`c_ai_agent_eval_case` 追加两列：

| 字段 | 说明 |
|---|---|
| review_status | VARCHAR(16) NOT NULL DEFAULT 'approved'：pending=待复核 approved=已采纳。存量行默认 approved，不回填 |
| origin | TEXT：采样原轮快照 JSON {sessionId, messageId, answer(≤2000 字)}。手动用例为 NULL；P2-b 的前文快照在此基础上扩展 |

### 3.3 采样行为变更

- 过滤条件维持现状：只采含知识块/文档引用的轮次（2026-11-16 已落地）；**不再加任何词表/长度启发式**。
- 落库：review_status=pending，enabled=1，origin 存原轮回答快照。
- 差评回流同样进 pending——差评轮的期望引用可能本身就是错的，正是复核要看的。
- 返回与提示：「已采样 N 条（待复核）」。

### 3.4 端点变更（不新增端点）

| 端点 | 变更 |
|---|---|
| POST /agents/{id}/cases/generate | 落 pending + origin |
| POST /agents/{id}/cases | update 支持 reviewStatus:'approved'（采纳）；add 默认 approved；非法值拒绝 |
| GET /agents/{id}/suite | cases 带 reviewStatus/origin；补 refTitles（期望引用 ID→标题，复核对照用，与 runDetail 同实现） |
| POST /agents/{id}/runs | 运行清单排除 pending |
| GET /agents/{id}/gate | caseCount 排除 pending |

### 3.5 前端（评测集 Tab）

- 状态列三态：待复核（黄）/ 启用（绿）/ 停用（灰）；表头旁「待复核 N」计数。
- pending 行操作：**采纳**（主链接）/ 编辑 / 丢弃（删除）；approved 行维持 编辑/停用/删除。
- 行展开（复核视图）：原轮回答全文（origin.answer）+ 期望引用标题对照——复核人据此判断
  「问题离开上下文是否成立」「期望引用是否可信」，不成立就丢弃。
- 采样 toast 与空态文案同步「待复核」语义。

### 3.6 验收

1. 采样 10 条 → 全部待复核，运行回归提示「没有可运行的用例」（若无非 pending 用例）。
2. 采纳 3 条 → 运行只跑 3 条；门禁 caseCount=3。
3. 展开待复核行能看到原轮回答与期望引用书名。
4. 编辑待复核用例保存后仍待复核；丢弃后消失。
5. 手动新增用例直接 approved，行为与改版前一致。
6. 存量库：既有全部用例视为 approved，不需要任何迁移操作。

## 4. P2-b 上下文回放（本期落地）

> **实施纠偏（2026-11-16 调研）**：原设想「前缀落消息表铺底」不成立——历史上下文活在
> 框架 Redis 会话状态（stateStore）里，消息表只做展示/持久化，往临时会话的消息表铺底
> 进不了模型。改走与「# 历史引用」同一条现役装配通道：前缀作为引用上下文前置进模型输入。

- **用例结构**：origin 扩展为 {sessionId, messageId, answer, prefix:[{role, content}…]}；
  采样时自动带出目标问之前的会话前缀：最近 10 条 user/assistant、总预算 4000 字、就近优先、
  单条截断（user 400 / assistant 600）。
- **执行**：`ChatCommand.replayPrefix`（评测专用字段）携带前缀转录（用户：…/助手：…），
  `TurnPromptAssembler.userContentWithContext` 将其套 UntrustedContent 信封前置到问题之前
  （旧回答里可能埋指令，与附件正文同口径消毒）。前缀是既定事实的引用数据，不重放模型调用、
  不落临时会话消息表；只评末轮。
- **评判同语境**：前缀转录一并喂给评判模型（「前文对话」段），相关性按前文语境理解问题真实意图——
  否则追问类用例的切题回答会被判成答非所问。防注入声明覆盖前文。
- **口径**：评分权重不变（召回+两维 judge+judgeMode）；前缀只供语境，不参与评分。
- **成本**：前缀进作答上下文，token 随前缀长度线性涨；运行确认弹窗对带前缀用例明示成本提示。
- **复核联动**：复核视图展示前缀轮次，支持逐轮移除（裁剪）；`cases` update 的 `originPrefix`
  键受控更新（≤20 轮、单条 ≤1000 字、总 ≤8000 字，角色仅 user/assistant；
  sessionId/messageId/answer 快照不接受客户端改写）。
- 依赖上文的建站迭代类题由此成为合法用例；长任务超时问题不在本期范围（仍靠复核丢弃）。
