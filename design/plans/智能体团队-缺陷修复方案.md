## 0. 一页结论

上一轮排查确认了 3 个 P0、6 个 P1。**它们的根因只有三个**：

| 根因 | 派生缺陷 | 本文修复 |
|---|---|---|
| **A. 成员身份没有唯一真源**：`c_ai_session` 与框架 BaseStore 名册两份，3 处写入点，无唯一约束 | 同名成员多行、名册互相覆盖、孤儿会话、消息发进永不唤醒的会话 | §1、§2 |
| **B. 成员状态机不闭合**：`STOPPED` 一个词承担「用户叫停」「关开关」两种语义，且写状态走 `updateById`（租户谓词下静默 0 行） | 关开关→永久"已停止"、永远"执行中"、唤醒后状态不翻转 | §3 |
| **C. 唤醒/叫停没有统一入口**：4 条唤醒路径 + check-then-act，失败只吞 warn | 并发丢唤醒、`shutdownMember` 不停轮、关开关不 evict、越权 interrupt | §4、§5 |

修复原则：
1. **单一入口**：所有状态迁移只走 `AgentTeamService` 的 `markRunning/markIdle/markSuspended/markStopped`；所有唤醒只走 `AgentTeamService.wakeMember`。
2. **失败要响**：团队关键路径禁止 `catch (Exception ignored)`，状态写入必须校验影响行数。
3. **向后兼容**：存量数据靠迁移脚本一次性收敛，不改事件信封、不改前端协议。

**一处更正**：上一轮报告的「服务器收件箱 key 对不上（P0#3）」经反编译框架核实**不成立**——`MessageBus.inboxPush/inboxDrain/inboxHasMessages` 三个默认方法共用同一常量 `agentscope:inbox:\u0001`，且问渠 `teamsMode(client, ctx, cmd.getSessionId())` 与 `RuntimeContext.sessionId` 是同一个值，`boundSessionId` 与 drain key 一致。**该条撤销**，不在本方案内。

## 1. P0-1：团队成员唯一性（根因 A）

### 1.1 缺陷回放

- [SubAgentBranchRuntime.java:197-213](../../src/main/java/com/wenqu/ai/agent/subagent/SubAgentBranchRuntime.java) 派成员时 `createTeamSession` + `addMember`；
- 子轮（`memberSessionId` 已设）仍挂团队工具，模型可再调一次框架 `spawnMember` → [WenquTeamGateway.java:144-162](../../src/main/java/com/wenqu/ai/agentx/team/WenquTeamGateway.java) **又建一条同名 kind=team 会话**；
- `addMember` 用 `store.put(...)` 按 `memberName` **无条件覆盖**（[WenquTeamGateway.java:135-139](../../src/main/java/com/wenqu/ai/agentx/team/WenquTeamGateway.java)）；
- `listTeamMembers` 不去重（[SessionService.java:218](../../src/main/java/com/wenqu/ai/service/SessionService.java)）。

后果：面板出现两个同名成员；被覆盖那条会话 `findTeamMember` 永不命中，用户发的消息、任务完成后的 `notifyLeadTaskSettled` 全落空。

### 1.2 修复

**① 数据库唯一约束**（新迁移 `V44__team_member_unique.sql`）

```sql
-- 团队成员在同一棵树内名字唯一：名册与 c_ai_session 必须一对一。
-- 先收敛存量重复（保留最早创建的那条，其余软删），再建唯一索引。
UPDATE c_ai_session s
JOIN (
    SELECT root_session_id, member_name, MIN(id) AS keep_id
    FROM c_ai_session
    WHERE kind = 'team' AND deleted = 0
    GROUP BY tenant_id, root_session_id, member_name
    HAVING COUNT(*) > 1
) d ON s.root_session_id = d.root_session_id
   AND s.member_name = d.member_name
   AND s.id <> d.keep_id
SET s.deleted = 1, s.update_time = NOW()
WHERE s.kind = 'team' AND s.deleted = 0;

ALTER TABLE c_ai_session
    ADD UNIQUE KEY `uk_team_member` (`tenant_id`, `root_session_id`, `member_name`);
```

> 注意：MySQL 唯一索引对 `NULL` 不去重，而根会话 `root_session_id`/`member_name` 为 NULL，正好不受约束影响——这是我们要的（唯一约束只作用于成员行）。
> 若存量库里 `deleted=0` 的重复行软删后有残留（`deleted` 列参与索引也可，但会与 `@TableLogic` 冲突），改为把重复行 `member_name` 追加 `#dup-{id前6位}` 后缀并记日志，避免误删用户可见的成员。

**② `addMember` 改为「只增不改」**

### 1.3 验收

## 2. P0-2：成员状态写入静默失效（根因 B 的一半）

### 2.1 缺陷回放

`c_ai_session` 有 `tenant_id`（[V1__baseline.sql:201](../../src/main/resources/db/migration/V1__baseline.sql)），`WenquTenantLineHandler` 会给 `updateById` 拼 `AND tenant_id = ?`，匹配 0 行是**一声不响**的（[TenantContext.java:180](../../src/main/java/com/wenqu/ai/util/TenantContext.java)）。

而这几个团队状态写全都走 `sessionMapper.updateById`：

- [SessionService.java:238-243](../../src/main/java/com/wenqu/ai/service/SessionService.java) `updateMemberState`
- [SessionService.java:252-257](../../src/main/java/com/wenqu/ai/service/SessionService.java) `advanceReadCursor`
- [SessionService.java:161-173](../../src/main/java/com/wenqu/ai/service/SessionService.java) `createTeamSession`（写完 `RUNNING`）

`spawnMemberSession` 在 `asUser(uid)` 里调用，线程租户与行上 `tenant_id` 一旦不一致 → 状态写不进去、无异常 → 面板"永远执行中"。

### 2.2 修复：状态写入改成显式 wrapper + 校验行数

```java
/** 更新成员在线状态快照；写 0 行是错（行被删/租户不符），必须响亮失败。 */
public void updateMemberState(String memberSessionId, String state) {
    int n = sessionMapper.update(null, new LambdaUpdateWrapper<Session>()
            .eq(Session::getId, memberSessionId)
            .set(Session::getMemberState, state));
    if (n == 0) {
        throw new BizException(500, "成员状态写入失败（会话不存在或租户不符）：" + memberSessionId);
    }
}

/** 推进已读游标：同上，但允许 0 行（成员被回收时不需要报错），仅记 debug。 */
public void advanceReadCursor(String memberSessionId, long eventId) {
    int n = sessionMapper.update(null, new LambdaUpdateWrapper<Session>()
            .eq(Session::getId, memberSessionId)
            .set(Session::getLastReadEventId, eventId));
    if (n == 0) log.debug("[TEAM] 已读游标未更新（成员可能已回收）session={}", memberSessionId);
}
```

`createTeamSession` 里那条 `updateById(row)` 同样改为 wrapper 写并检查行数（它写的是 `root_session_id/member_name/member_state` 三列，绝不能静默丢）。

> 这一改会让"租户不符"从静默变成**显式 500**，所以必须和 §2.3 一起上线，否则会把原本"看起来正常"的写入变成报错。

### 2.3 定租户口径：团队写入统一按根会话属主

团队的写操作跑在无身份线程（`boundedElastic` / `commonPool`）上，`TenantContext.current()` 为空。统一成：

```java
// AgentTeamService 内统一入口：团队所有写都在这把身份/租户里做
private <T> T asOwner(String rootSessionId, Supplier<T> body) {
    Session root = sessionService.sessionById(rootSessionId);
    if (root == null) throw new BizException(404, "团队根会话不存在");
    return userIdentityService.asUser(root.getUserId(), body::get);
}
```

`spawnMemberSession`、`shutdownMemberSession`、`interruptMember`、`wakeMember` 全部套这一层。

## 3. P0-3 / 你反馈的「已停止」：成员状态机闭合（根因 B）

### 3.1 现状与问题

```
createTeamSession → RUNNING（写死）
SubAgentBranchRuntime  → markRunning(RUNNING) / markIdle(IDLE)
interruptMember        → STOPPED（关开关也走这里）
shutdownMemberSession  → STOPPED（不停轮、不 evict）
wakeMember             → 什么都不写   ← 断了
成员页普通轮            → 什么都不写   ← 断了
listMembers            → STOPPED 显式保留，不回落
```

你报的"关开关后变已停止"，就是 `setEnabled(false)` 复用 `interruptMember` 写 `STOPPED`，而重新开启**没有任何代码把它改回 IDLE**。

### 3.2 目标状态机

```
                     spawn
                       │
                       ▼
                    IDLE ──── wake/派活 ────► RUNNING
                     ▲ │                        │
         轮正常结束 ──┘ └── 用户叫停该成员 ──► STOPPED ── 重新唤醒 ──► RUNNING
                     │                                  ▲
      关开关 ──► SUSPENDED ── 开开关 ──► IDLE          │
                     │                                  │
      进程重启/实例被逐出 ──► OFFLINE ───────────────────┘
```

| 状态 | 含义 | 面板文案 | 谁写 |
|---|---|---|---|
| `RUNNING` | 有真实在跑的轮 | 执行中 | 轮开始 |
| `IDLE` | 在册、可唤醒 | 空闲 | 轮结束 / spawn / 开开关 |
| `SUSPENDED` | 团队开关关闭，成员挂起 | 已暂停 | 关开关 |
| `STOPPED` | 用户显式叫停该成员 | 已停止 | interrupt / shutdownMember |
| `OFFLINE` | 实例不在内存（进程重启） | 离线 | 推导 |

**关键规则**：
1. `STOPPED` 是**用户对单个成员的显式动作**，只有 `interrupt`/`shutdownMember` 能写；
2. `SUSPENDED` 是**团队级挂起**，关开关写它，开开关清回 `IDLE`；
3. **任何一次成功唤醒都先写 `RUNNING`**，轮结束写 `IDLE` —— 这样 `STOPPED` 在一次新唤醒后自然解除（与 `WenquTeamGateway:164` 注释"可再唤醒"一致）。

### 3.3 改动清单

**① 新增 `SUSPENDED` 与两个方法**（`AgentTeamService`）

```java
/** 团队开关关闭：整树挂起（停轮 + 逐出实例 + 落 SUSPENDED），不是"终止"。 */
public void suspendTree(String uid, String rootSessionId) {
    sessionService.setTeamEnabled(uid, rootSessionId, false);
    try { frameworkSessions.evictSession(uid, rootSessionId); } catch (Exception e) {
        log.warn("[TEAM] 根实例逐出失败 root={}: {}", rootSessionId, e.toString());
    }
    for (Member m : listMembers(rootSessionId, uid)) {
        try {
            chatRunRuntime.stopTurn(m.sessionId(), uid);
            frameworkSessions.evictSession(uid, m.sessionId());
            sessionService.updateMemberState(m.sessionId(), "SUSPENDED");
            emitMemberState(m.sessionId(), "SUSPENDED");
        } catch (Exception e) {
            // 不吞：单个成员挂起失败要能定位，但不阻断其余成员
            log.warn("[TEAM] 成员挂起失败 root={} member={}: {}", rootSessionId, m.sessionId(), e.toString());
        }
    }
}

/** 团队开关打开：把挂起/停止的成员恢复成可唤醒的 IDLE。 */
public void resumeTree(String uid, String rootSessionId) {
    sessionService.setTeamEnabled(uid, rootSessionId, true);
    try { frameworkSessions.evictSession(uid, rootSessionId); } catch (Exception e) {
        log.warn("[TEAM] 根实例逐出失败 root={}: {}", rootSessionId, e.toString());
    }
    for (Member m : listMembers(rootSessionId, uid)) {
        if ("SUSPENDED".equals(m.state()) || "STOPPED".equals(m.state())) {
            sessionService.updateMemberState(m.sessionId(), "IDLE");
            emitMemberState(m.sessionId(), "IDLE");
        }
    }
}
```

`setEnabled` 改写为：

```java
public void setEnabled(String uid, String sessionId, boolean enabled) {
    if (enabled) resumeTree(uid, sessionId); else suspendTree(uid, sessionId);
}
```

### 3.4 你报的那个场景修复后的行为

| 动作 | 修复前 | 修复后 |
|---|---|---|
| 关开关 | 成员全部 `STOPPED`（永久） | 成员全部 `已暂停`（`SUSPENDED`），在跑的轮真停 |
| 开开关 | 仍是 `已停止` | 全部回到 `空闲`，可被消息唤醒 |
| 开开关后发消息 | 标签仍是 `已停止` | 先 `执行中`，跑完 `空闲` |
| 面板手动「叫停」某成员 | `已停止`，实例还在跑 | `已停止`，实例已逐出；下次唤醒变 `执行中` |

## 4. P1：权限与叫停（根因 C）

### 4.1 缺陷：`interrupt` 缺归属校验

[TeamController.java:87-94](../../src/main/java/com/wenqu/ai/controller/TeamController.java) 只 `assertOwned(rootId)`，随后把**请求体里的任意 `memberSessionId`** 交给 `interruptMember`，而它只判 `kind=team`。隔壁 `memberHistory` 做了三重校验——这是遗漏。

### 4.2 修复：抽公共校验

```java
// TeamController
private Session assertTeamRoot(String rootId, String uid) {
    Session root = sessionService.assertOwned(rootId, uid);
    if (SessionService.KIND_TEAM.equals(root.getKind())) {
        throw new BizException(400, "rootId 必须是团队根会话，不能是成员会话");
    }
    return root;
}

private Session assertTeamMemberOf(String rootId, String memberId, String uid) {
    Session m = sessionService.sessionById(memberId);
    if (m == null || !SessionService.KIND_TEAM.equals(m.getKind())
            || !rootId.equals(m.getRootSessionId()) || !uid.equals(m.getUserId())) {
        throw new BizException(403, "该成员不属于此团队");
    }
    return m;
}
```

**所有**团队接口的首行换成 `assertTeamRoot(rootId, uid)`；`interrupt` 加：

## 5. P1：唤醒统一入口（根因 C）

### 5.1 缺陷

- [TeamWakeService.java:64-67](../../src/main/java/com/wenqu/ai/agentx/team/TeamWakeService.java) 先读 `turnIdOf` 再异步 `chat()`，真锁在 `chat()` 里 → check-then-act；
- 第二个 `chat()` 被 `rejectTurn`，[:88-94](../../src/main/java/com/wenqu/ai/agentx/team/TeamWakeService.java) **只打 warn** → 消息静默丢失；
- 跑在 `ForkJoinPool.commonPool`，无身份/无租户。

### 5.2 修复：在 `AgentTeamService` 收口

```java
private final Set<String> waking = ConcurrentHashMap.newKeySet();

/**
 * 唤醒成员的唯一入口：占坑 → 起轮 → 失败回滚。收件箱里的消息不会被重复消费，
 * 占坑失败说明已有活轮，交给活轮的 InboxMiddleware 读（不丢）。
 */
public void wakeMember(String rootSessionId, String memberName, String message) {
    Session m = sessionService.findTeamMember(rootSessionId, memberName);
    if (m == null) { log.warn("[TEAM] 唤醒目标不在名册 root={} member={}", rootSessionId, memberName); return; }
    String sid = m.getId();
    if (!waking.add(sid)) return;                       // 本地占坑，跨进程序列化由 chat 的租约兜底
    try {
        asOwner(rootSessionId, () -> {
            sessionService.updateMemberState(sid, "RUNNING");
            emitMemberState(sid, "RUNNING");
            teamWakeService.wake(rootSessionId, sid, m.getAgentId(), message,
                    () -> { sessionService.updateMemberState(sid, "IDLE"); emitMemberState(sid, "IDLE"); });
            return null;
        });
    } catch (Exception e) {
        // 起轮失败：状态回 IDLE，消息仍在邮箱里，下一轮或用户手动发消息能捞回来
        sessionService.updateMemberState(sid, "IDLE");
        emitMemberState(sid, "IDLE");
        log.warn("[TEAM] 唤醒失败 root={} member={}: {}", rootSessionId, memberName, e.toString());
    } finally {
        waking.remove(sid);
    }
}
```

`TeamWakeService.wake` 增加 `onSettled` 回调。`CollectingSseEmitter` **不提供 `onCompletion/onError` 注册口**，它已有的是 `awaitDone(long)`（阻塞到 `done`/`error` 帧或超时）与 `finished` 标志，所以按现成 API 落地：

```java
java.util.concurrent.CompletableFuture.runAsync(() -> {
    com.wenqu.ai.service.CollectingSseEmitter em = new com.wenqu.ai.service.CollectingSseEmitter();
    java.util.function.Consumer<Void> settle = v -> { if (onSettled != null) onSettled.run(); };
    try {
        r.accept(cmd, em);
        em.awaitDone(0L);                 // 0 = 不超时；也可给个上限兜底
    } catch (Exception e) {
        log.warn("[TEAM] 唤醒失败 session={}: {}", sessionId, e.toString());
    } finally {
        settle.accept(null);              // 无论正常/异常都回到 IDLE，避免状态卡在 RUNNING
    }
}, executor);
```

同时两处配套调整：
- **执行器**：不再用 `ForkJoinPool.commonPool()`（公共池被 I/O 阻塞会拖累整个 JVM），换成团队专用的有界线程池（`ThreadPoolExecutor`，核心 4、峰值 16、有界队列，拒绝策略记 warn）。
- **身份/租户**：在 `runAsync` **之前**用 `userIdentityService.asUser(uid)` 包一层再提交任务，解决无身份/无租户问题（上轮 P2#13）。

> `TeamWakeService` 保留，但**只有 `AgentTeamService.wakeMember` 能调它**；`WenquTeamClient` 的 `MemberController.wake` 改为直接委托 `AgentTeamService.wakeMember`，去掉现在 `WenquTeamGateway.wakeMember` 里那条"找不到人就静默 return"的路径。

## 6. 实施顺序与最小可交付

每一步都能独立上线、独立回滚，建议按此顺序：

| 步 | 内容 | 改动面 | 风险 | 验收 |
|---|---|---|---|---|
| **1** | §4.2 归属校验 + §4.3 `send` 校验 | `TeamController` 单文件 | 极低 | 用一个成员 id 调 `interrupt` 返回 403 |
| **2** | §3.3①②③ + §3.4 前端文案 | `AgentTeamService`、`TeamPanel.vue`、V44 迁移 | 低 | 关→已暂停，开→空闲 |

## 8. 不在本方案内（需另行决策）

| 项 | 为什么不一起做 |
|---|---|
| 成员消息卡无时间戳（ADR §5 P2） | 需要新增一张消息时间账本表 + 回填历史，属于功能补充不是缺陷；建议与「消息游标分页」一起做 |
| `FrameworkSessions.evictSession` 只清 `held`，其余按会话的 map 无界增长 | 影响普通问答路径，改动面大，应单独做一次资源生命周期梳理 |
| `TurnRegistry.HANDLES` 用 `put` 而非 `putIfAbsent` | 多副本才触发；当前单副本部署不受影响（见 ADR §6） |
| 租户不入 namespace、任务事件按属主租户读 | 与现有上线策略（单租户）冲突，需产品确认多租户启用时间 |
| 任务板 500 条 / 名册 100 条上限 | 框架内部限制，需要分页改造或换 `TeamClient` 实现 |
