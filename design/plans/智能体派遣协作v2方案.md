# 智能体派遣协作 v2：审批作用域、子会话延续与并行派遣

> 本文是方案 + 本次落地的记录。依据是 2026-11-24 线上会话 `c8260e6be2ae4ba4a4f3dc176cebbf19` 的日志、框架会话归档与 `c_ai_tool_approval` 记录（只读排查）。落地部分见第 10 节。

## 1. 现象与证据

同一轮问答（16:43:31–16:46:44）里出现了五件事：

| # | 现象 | 证据 |
|---|---|---|
| 1 | 用户多次点「本次会话都允许」，下一次派遣仍弹同一把工具 | 16:43:45 / 16:43:56 已登记 `本次会话都允许 tool=w_q_db_overview / w_q_sql_query`，但 16:44:20 换到新子会话 `a1fe98` 后重新弹卡；一轮共 13 张审批卡（16:44:30 一次 3 张、16:45:18 一次 6 张） |
| 2 | 触发「工具调用上限 25 次」 | 取数助手 `max_tool_steps=50`，分支深度 1 被 `50 >> 1 = 25`；子会话归档有 3 条 DENIED「已达到本轮工具调用步数上限(25)」；两次派遣分别跑到 22 / 17 步后中断 |
| 3 | 派遣像单线，且续问「失忆」 | `AGENT_SPAWN_FORCE_SYNC=true`，父轮同步等；提示词写「可以派多次，每次一位」；`agent_send` 新建子会话 `a1fe98`，它的首条输入只有【父轮上下文】+ 新消息，于是重新 `SHOW TABLES` 一遍 |
| 4 | 团队成员 `data-fetcher` 的 6 个 SQL 全部 `Permission denied by rules` | 会话 `241c329d...`；归档里 6 条 `w_q_sql_query` 结果全是 `state=denied`；`[TEAM] spawnMember member=data-fetcher agent=null` |
| 5 | 被拒的 6 步在界面上显示 ✓、算进「7 步」 | 框架 `tool/result` 落卡只按 `failed ? error : done`，没有把 `denied` 当第三态；`executedCount` 因此也把它们当已执行 |

用户真正感知到的是 1、3、2；第 4、5 是同一个根因链在团队会话上的另一副面孔。

## 2. 根因

### 2.1 审批放行绑在「执行用的临时会话」上

- 登记逻辑（[FrameworkSessions.java:667](file:///Users/wangxi/workspace/WenQu/src/main/java/com/wenqu/ai/agentx/FrameworkSessions.java#L667)）按当前会话 key 写入 `AgentxTurnSlot.sessionApproved`（[AgentxTurnSlot.java:116](file:///Users/wangxi/workspace/WenQu/src/main/java/com/wenqu/ai/agentx/AgentxTurnSlot.java#L116)）。
- 每次派遣/续问都会新建一个子会话（[SubAgentBranchRuntime.java:196](file:///Users/wangxi/workspace/WenQu/src/main/java/com/wenqu/ai/agent/subagent/SubAgentBranchRuntime.java#L196)）：`d65dab` → `a1fe98` → `16af9fe0`（团队/分支还会再建）。放行集合在进程内的旧槽位上，新子会话读不到。
- 审批行其实已经有 `parent_session_id = c826...`（团队为 `team_root_session_id`），但 `respond(scope=session)` 没有用它做作用域。
- 结论：**「本次会话」在代码里等于一次执行，在用户心里等于一条对话**。这是本轮所有重复弹卡的直接原因。

### 2.2 `spawnMember` 丢了智能体绑定

- 框架 `spawnMember(agent_ref=a1b2...)` 进入 [WenquTeamGateway.spawnMemberSession:144](file:///Users/wangxi/workspace/WenQu/src/main/java/com/wenqu/ai/agentx/team/WenquTeamGateway.java#L144)。
- 它在框架工具线程上执行，没有请求身份；`agentService.resolveForTurn(agentRef, null)` 的可见性判定读不到当前用户，返回 null → 回落 `root.getAgentId()`；而根会话 `c826...` 的 `agent_id` 也是 NULL → 成员 `data-fetcher` 以 `agent=null` 落库。
- 成员于是按平台默认档（standard / ask）运行，拿不到取数助手的人设、工具面、`max_tool_steps=50` 与 `tool_approval_mode=auto`，`listMembers` 里也显示 `agentRef=""`。
- 这是**静默降级**：lead 以为派出去的是取数助手，实际是一个没有身份的平台默认工人。

### 2.3 团队成员的轮被当成「无人可答」的 headless 轮

- 成员唤醒由 `TeamWakeService` 发起，`source("team")`（[TeamWakeService.java:86](file:///Users/wangxi/workspace/WenQu/src/main/java/com/wenqu/ai/agentx/team/TeamWakeService.java#L86)）。
- `interactiveTurn` 只认 `source` 为空或 `user`（[AgentscopeChatEngine.java:2008](file:///Users/wangxi/workspace/WenQu/src/main/java/com/wenqu/ai/agentx/AgentscopeChatEngine.java#L2008)），于是 `approvalCanAsk=false`。
- `SpringAiToolAdapter.checkPermissions` 在需要审批且无人可答时返回 DENY（[SpringAiToolAdapter.java:156](file:///Users/wangxi/workspace/WenQu/src/main/java/com/wenqu/ai/agentx/SpringAiToolAdapter.java#L156)），框架把所有自动拒绝统一写成 `Permission denied by rules`，真实原因（「本轮回合没有可应答的在场通道」）被丢掉。
- 但团队成员会话是**有界面的**（团队面板/成员会话页），用户就在看。把它按 headless 处理，等于让成员永远调不动 MCP。

### 2.4 denied 被渲染成成功

- 框架 `tool/result` 落卡只分 `failed` / 非 failed（[AgentscopeChatEngine.java:2896](file:///Users/wangxi/workspace/WenQu/src/main/java/com/wenqu/ai/agentx/AgentscopeChatEngine.java#L2896)），没有把 `toolResultDenied` 当第三态。
- 结果：6 个被拒 SQL 全是 ✓，计入「7 步」，`executedCount` 也算成已执行；用户看到的是「跑了 6 个查询，只有最后一个失败」，实际一个都没跑。
- `tool/decision` 的 WARN（[:2902](file:///Users/wangxi/workspace/WenQu/src/main/java/com/wenqu/ai/agentx/AgentscopeChatEngine.java#L2902)）也没形成卡片上的可见标记。

### 2.5 预算语义：把「委派」当成「降级」

- `maxToolSteps` 按 `depth` 右移（[ToolAssemblyService.java:43](file:///Users/wangxi/workspace/WenQu/src/main/java/com/wenqu/ai/service/ToolAssemblyService.java#L43)）。50 步的取数助手派出去自动变 25 步。
- `AGENT_CONSULT_MAX_PER_TURN=3` 统计的是**总调用次数**，同一助手的续问也算一次（[SubAgentConsultService.java:192](file:///Users/wangxi/workspace/WenQu/src/main/java/com/wenqu/ai/agent/subagent/SubAgentConsultService.java#L192)）；第三次派遣得到「额度已用完」。
- 被拒的调用也占步数（设计如此，防免费重试），但在 2.3 的场景里，6 个注定被拒的调用把成员的步数直接烧光。

### 2.6 串行来自两处

- 平台强制同步：`AGENT_SPAWN_FORCE_SYNC=true`（[ConfigDefaults.java:97](file:///Users/wangxi/workspace/WenQu/src/main/java/com/wenqu/ai/config/ConfigDefaults.java#L97)），父轮一直等。
- 提示词明确写「可以派多次，每次一位」（[WenquAgentxTools.java:913](file:///Users/wangxi/workspace/WenQu/src/main/java/com/wenqu/ai/agentx/WenquAgentxTools.java#L913)），模型只会串行。
- 加上 2.1 / 2.2 的失忆，每次续问都要重新探查，单线感被放大。

### 2.7 auto 仍弹卡：已定位为团队根封顶，不是解析 bug

`d65dab` / `a1fe98` 的会话行是 `kind=team`、`member_name=取数助手`，虽然智能体配置是 `tool_approval_mode=auto`，但团队成员会走 `capToTeamRoot`：根会话 `c826...` 是 standard/ask，成员被取更严的 ask。所以这是「委派不放大权限」的设计结果，不是 `agentOf` 解析错。
真正的问题是两处闸读了两份口径：挂载闸看智能体字面值 `approvalAsk()`，审批闸看本轮 policy。P0 已把两处统一到本轮生效策略，并加按轮 `[PERM] ...` 日志。

## 3. 目标与非目标

**目标**

1. 「本次会话都允许」以**用户看到的根会话**为作用域，覆盖该根会话下所有分支、续问与团队成员；跨副本一致。
2. 团队成员一定按 lead 指定的智能体运行；解析失败要 fail-loud，不静默回落。
3. 团队/分支轮在有人可见时能审批；确实无人可答时，在装配期就不挂需要审批的工具，并给出中文降级说明。
4. denied 是独立状态：卡片「被挡下」、不计入已执行、不误导下一步。
5. 预算语义可解释、可配置：不隐式砍半；咨询额度按不同助手/并发分支计；命中后能 partial 收尾并在同一子会话续做。
6. 互不依赖的派遣可以并行；提示词与 UI 都按多分支设计。

**非目标**

- 异步派遣（父轮不等、后台跑完再收）本期不做；它牵涉审批卡在异步期的投递与等待，单独立项。
- 跨用户/跨会话共享放行；放行只属于一个根会话。
- 团队成员的审批卡是否要在根面板做成完整操作台，本期只做聚合徽标 + 可跳转。

## 4. 方案

### 4.1 审批作用域：根会话级放行（P0）

**数据模型**

新增 `SessionToolGrants`（根会话 key = `uid + '|' + rootSessionId`）：

- 值：`Set<toolName>`，带 `grantedAt` 与 TTL（建议 7 天，或随根会话删除清理；进程重启不丢）。
- 存储：Redis（复用 `TransientSessionState` 的连接/命名空间），本地 ConcurrentHashMap 做读缓存；**不要**继续用 `AgentxTurnSlot` 里的进程内集合做唯一来源。
- 作用域解析：`cmd.teamRootSessionId` > `cmd.parentSessionId`（向上取到根）> `session.rootSessionId` > 自身 sessionId。

**写入**

- `POST /chat/tool-approval/{id}` 的 `scope=session`：从审批行取 `parent_session_id`（团队为根的 id）与 `tool_name`，写根会话 grants；同时写一条审计事件 `tool/grant`（工具名、根会话、审批行 id、操作者）。
- 不再只写执行侧子会话的槽位；子会话读根 grants 即可。

**读取**

- `SpringAiToolAdapter` 的 `sessionApproved` 供应商改为 `grants.allowed(rootKey, name)`（或与子槽位并集）；`AgentxNativeToolGuard` 的强制确认同样读它。
- 更贴框架的一层：在开轮时为子/团队会话构造 `PermissionContextState` 时，把根 grants 注入 `allowRules`。这样 `PermissionEngine` 在 `checkAllowRules` 就先放行，审批路径、审计与状态回放都统一；`sessionApproved` 只作为兜底。二者读同一份 grants，不产生第二套判定。
- 迁移：审批行已有 `parent_session_id`，无需改表；增量加 grants 的审计表/事件即可。

**UI**

- 审批卡下拉文案改为「本会话都允许（所有子助手对同一工具也不再询问）」。
- 根会话头部加一个可展开的「本会话已放行」清单，支持撤销；撤销后下一次调用重新询问。
- 不把「放行」做成全局/跨会话设置；换会话、换用户一律重新问。

**为什么不是把放行写进子会话的 allowRules 就完事**：子会话是一次性的，写进去随会话消失；必须落在根作用域，子会话开轮时读取/注入。这与 DSH「审批是一次授权，会话策略是持久状态」的分层一致。

### 4.2 团队成员身份与会话延续（P0）

- `spawnMemberSession` 在解析 `agentRef` 前恢复根会话用户的身份（`RequestUser.restore`），解析成功才建成员；解析失败不回落 null：
  - 回给 lead 一句可执行的错误：「agent_ref=a1b2 不存在或你无权使用，未创建成员」；
  - 不把「无 agent 的成员」当成成功。
- 根会话也没有 agent 时，成员显式使用平台默认智能体（与根问答同一身份），并在日志/名册里标出，不再留空。
- `agent_send` / 团队 `sendMessage` 续问复用同一 child/member session：
  - 分支临时会话不再「跑完即删」，保留到父轮结束 + 宽限期（建议 10 分钟），同一轮内的续问直接续上下文；
  - 团队会话本来就是持久的（IDLE 唤醒），只需修好 agent 绑定与审批通道；
  - 临时会话最终回收时，若根 grants 存在，不影响下一次派遣的审批（4.1 已解耦）。

### 4.3 团队/分支轮的审批通道（P0）

- `interactiveTurn` 增加 `source=team`（团队成员会话有可见 UI）；`scheduled` / `workflow` / `eval` / `apiKey` / `guest` 仍 fail-closed。
- 团队成员审批卡的路由：
  - 成员会话内展示（用户点开就能看见）；
  - 根团队面板/会话列表加「待确认 N」徽标与通知，点击跳到成员会话那张卡；
  - 超时按拒绝处理（与主轮一致，默认 300s），不代批。
- 真无人可答的轮（定时/工作流/评测）：**装配期**把「需要审批」的工具从工具表移除，并发一条可见降级「本轮无人可确认，MCP/沙箱工具未挂载」，而不是让模型调用后吃 `Permission denied by rules`。
- 即使保留调用期拒绝，也必须把真实原因带出来；框架的 `writeAutoDeniedResults` 会覆盖工具返回文案，所以优先用装配期排除，避免依赖框架文案。

### 4.4 denied 的第三态（P0）

- `tool/result` 落卡：`failed ? "error" : (toolResultDenied(data) ? "denied" : "done")`，同时把 `denied:true` 写进卡片条目。
- 前端：`tool_status` 的 denied 走「被挡下」黄色标记；`processEvents` 已支持 `status=denied`，补齐持久化卡片的映射即可。
- 计数：`executedCount` 继续排除 denied；时间线显示「被挡下」；步骤总数可以保留（预算确实消耗了），但要与「已执行」分开。
- 文案：拒绝、超时、无通道三种原因分别给中文；无通道的提示指向「让团队面板/会话保持在可确认状态」。

### 4.5 预算语义（P1）

- 取消隐式 `>> depth`。新增平台配置 `agent.subagentMaxToolSteps`（0=不做额外限制，分支跟随智能体的 `max_tool_steps`）。扇出由「深度上限 + 并发分支数 + 咨询额度」控制，不再用右移惩罚被委派的一方。
- `consultMaxPerTurn` 改为按**不同助手数**计；同一助手的 `agent_send` 续问不占新名额。团队 `sendMessage` 与分支 `agent_spawn` 共用一份台账，但不互相挤掉。
- 命中步数上限时：
  - 强制模型先作答（现有 WRAP_UP_HINT 已做一半）；
  - 子轮回报标记 `partial` 而不是 `DONE 15 字`；
  - 父轮可以在同一子会话用一次「继续」续做，新 turn 重置步数但保留上下文（依赖 4.2 的会话延续）。

### 4.6 并行派遣（P1/P2）

- 提示词改为：「几个问题互不依赖时，在同一个 assistant step 里发多个 `agent_spawn`，框架会并行执行；不要一位一位串行等。」
- 先实测两个 `agent_spawn` 同一步是否真并发（`SpringAiToolAdapter` 已声明 concurrencySafe，需用真实沙盒/子轮验证）；如果不并发，需要在框架侧确认 spawn 工具的并发标记或改走多分支。
- 前端：多分支按 `branchIndex` 并排/分组展示；过程面板显示「N 个分支在跑」，每个分支有自己的步骤行；审批卡按 4.1 的根 grants 去重，避免并行批量弹卡。
- 真异步派遣（父轮不被阻塞）放到 P3：需要解决子轮审批卡在异步期的投递、根面板聚合与超时收口，不建议和本期混做。

### 4.7 策略可观测性（P0，钉子）

- 每轮开轮记录一行 `ExecutionPolicy.describe()`（档位/沙盒/审批/约束/可写根/禁用）到日志与会话事件，带 `session/turn/depth/agentId`。
- 单测覆盖：
  1. 智能体显式 `auto` + 继承 `ask` → `auto`；
  2. 团队成员 `capToTeamRoot`：根 ask + 成员 auto → ask；
  3. `agentRef` 不可见/不存在 → fail-loud，不回落 null；
  4. 根 grants 存在 → 子会话 adapter 不再 ASK。
- 用这条日志回放本次会话，确认 2.7 的 auto→ask 是解析 bug 还是设计；是 bug 就修，是设计就改文档与 UI 文案。

## 6. 分期与验收

**P0（正确性，先做）**

1. 同一根会话：第一次派遣对某工具选「本会话都允许」后，第二次派遣 / 续问 / 团队成员不再弹同一把工具。
2. 团队成员 `data-fetcher` 按 lead 指定的 agent 运行（名册里 agentRef 非空）；MCP 查询能执行，或在无人可答时给出中文降级而不是 `Permission denied by rules`。
3. 被拒调用显示「被挡下」，不计入「已执行」；6 个 SQL 被拒时用户看到的不是 6 个 ✓。
4. 策略日志能解释本次会话每个子轮的审批档来源。

**P1（预算/连续性）**

1. 取数助手派出去不再被砍到 25；命中上限后回报 partial，父轮可续同一子会话。
2. `agent_send` 不再重建子会话、不再重新探查表结构；同一子会话的审批放行继续有效。

**P2（并行）**

1. 两个互不依赖的 `agent_spawn` 在同一步发出，总耗时接近单支最长而不是求和；前端两个分支并排可见。
2. 并行产生的多张审批卡按根 grants 去重，不出现同一工具 6 张卡。

**P3（可选）**

- 异步派遣与审批 inbox；不在本期。

## 7. 风险与回滚

- **作用域扩大**：grants 严格按 `uid + 根会话 + 工具名`，TTL 到期或用户撤销即失效；不跨用户、不跨会话。
- **团队轮可审批**：无人时超时拒绝，不代批；与主轮同一语义。
- **agentRef 解析**：只允许根用户可读的智能体；解析失败 fail-loud，不能让成员读别人的智能体。
- **预算放开**：靠深度/并发/咨询额度与既有 token 记账兜底；`agent.subagentMaxToolSteps` 可随时调回小值。
- **并行**：先小流量验证框架并发；不并发就回落串行，不阻塞 P0/P1。

## 8. 业界对标

- DSH：核心审批是 per-call（allowed-once / rejected / cancelled / unavailable）+ 会话策略 `ask/never`；「Allow for this session」属于会话级能力授权，不是一次调用的结果。团队成员会话保留、回到 IDLE 可再唤醒。
- Claude Code / Codex CLI：会话级放行绑定的是会话，不是某次执行；子任务续问保留上下文。
- 结论：**放行挂根会话、执行会话可丢弃；worker 的身份与审批通道必须与用户看到的会话一致**。这正是本期 v2 的两条主线。
