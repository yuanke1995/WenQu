# 智能体评测 P2 剩余项 · 可执行实施方案

> 范围：智能体评测与发布门禁线在 P1 + P1.5 + P2-a + P2-b 之后的剩余能力。
> 已落地部分：P1（套件/用例/回归/门禁五态/对比/基线）、P1.5（保存前检查 + 通知 + 费用 kind）、
> P2-a（采样复核闸）、P2-b（上下文回放）。
> 本方案只写**剩余项**与**为剩余项必须先收口的口径**，已落地部分不复述实现。

## 0. 勘验结论（代码级事实，方案的依据）

### 0.1 已具备的骨架（剩余项直接挂在这上面）

| 能力 | 落点 | 状态 |
|---|---|---|
| 套件/用例/运行/逐条结果四表 | `c_ai_agent_eval_suite/_case/_run/_result`（V1 基线） | 在 |
| 回归执行器 | [AgentEvalRunner.java](../../src/main/java/com/wenqu/ai/service/AgentEvalRunner.java) | 在 |
| 评分器 | [AgentEvalScorer.java](../../src/main/java/com/wenqu/ai/service/AgentEvalScorer.java) | 在 |

### 0.2 两处口径更正（以代码为准，与既有账本/文档不一致）

1. **门禁拦截已不存在**。`agentEval.gateMode` 键已下线（V18 清库、ConfigKeys 摘除），
   `AgentEvalService#gateCheck` 只返回状态与变更清单，不拦截保存/发布。
   账本 [roadmap.md](../../.zcode/skills/wenqu-dev/references/roadmap.md) 的 S3-4 行「门禁 block 下沉服务端 ✅」
   描述的是已下线的形态，本方案按**恒提示档**写，不再把「服务端拦截」列入剩余项。
2. **`expected_tools` 字段已在表里但评分器不读它**。V1 基线注释写明「P2 参与评分，本期仅记录」，
   `AgentEvalService#applyCaseFields` 已能写入该列，但 [AgentEvalScorer.java](../../src/main/java/com/wenqu/ai/service/AgentEvalScorer.java)
   的 `score(...)` 完全不读它 —— 这是「工具期望评分」的准确缺口。

### 0.3 智能体配置的直读点（P2-F 的全部难点）

历史版本重测要求「本轮用历史快照配置而非当前行」。当前配置读取点分两类：

**已按 Agent 对象传递（override 后天然生效）**
- `ToolAssemblyService#mountContext(Agent, ...)` → 工具族三态 / 具体项选择 / 权限档位 / 步数上限
- `RetrievalScopeService#resolve(Agent, ...)` → 知识库范围 / 标签 / 过滤条件
- `RolePrompt.of(Agent, ...)` → 人设
- `WenquAgentxTools#agentOf(cmd)` → 上述全部的上游（但它自己走 `agentService.get`）

**按 agentId 直读库（override 后不会生效，必须收口）**
- [HttpToolService.java](../../src/main/java/com/wenqu/ai/service/httptool/HttpToolService.java) `mount(String agentId)` → `agentMapper.selectById`
- [WorkflowToolService.java](../../src/main/java/com/wenqu/ai/service/workflowtool/WorkflowToolService.java) `mount(String agentId, ...)` → `agentMapper.selectById`
- `ChatService#loadAgentQueryOverrides(agentId)` → `agentService.get`
- `AgentService#consultCandidates(selfAgentId)` → `get` + `list()`

结论：**收口需要一个统一解析口 `AgentConfigResolver.resolve(agentId)`**，所有直读点改为走它，
override 通过该口生效。

### 0.4 评测轮的工具副作用面（安全边界，P2-F 放大）

`ToolFamily.HTTP_API` 与 `ToolFamily.WORKFLOW` 的 `blockedWhenApprovalOff=false`，
`ToolMountContext#approvalPolicyAllows` 对这两族直接放行 —— 即便审批档是 `off`，
带凭据的 HTTP 工具与工作流工具在评测轮里**会真实执行**。
`ToolRegistry#requiresApproval` 对未登记名 fail-closed 返回 true，但审批闸只在 `approvalMode=ask` 时才拦。

含义：
- 现状下评测一个配了 HTTP 工具集的智能体，会拿真实凭据调宿主 API。
- P2-F 若引入历史快照重测，会额外用**旧凭据**调旧接口，风险放大一档。

因此本方案把「评测轮强制不挂有副作用族」列为 P2-F 的**前置收口**（P2-C/D/E 顺带受益）。

### 0.5 其他口径缺口

- `AgentService.VERSION_FIELDS`（版本快照白名单）**不含 `goalEnabled`** →
  历史版本重测时深度执行开关只能沿用当前值。本方案按「沿用当前值 + 界面提示」处理，不扩白名单
  （扩白名单会连带改变回滚语义，超出本项范围）。
- `AgentService.VERSION_FIELDS` 不含 `disabled` / `isDefault`（正确：非调优内容不进快照）。
- 版本快照里的 `httpTools` 存的是**原始值**（含 JWE 密文凭据），可解密 —— 这是 §0.4 风险的来源。
- `ConfigDefaults.AGENT_EVAL_THRESHOLD_RATE` 无任何读取点（阈值实际落在套件行的 `threshold_rate`），是死常量。
- `AgentEvalScorer#judgeModel()` 里 `fallback` 变量与上一行读同一个键（`eval.judgeModel`），是死代码。

## 2. P2-C · 工具期望评分

### 2.1 口径

- 用例行 `expected_tools` 存**必须调用的工具名**（JSON 数组，模型可见工具名口径，
  与 `done.toolCalls[].name` 同一命名空间，如 `search_knowledge` / `webSearch` / `writeTodo`）。
- 判据：**全部命中**才算该维度通过（与引用召回的「命中 ≥ 1」不同，工具期望是白名单式强约束）。
- **不进综合分**。综合分仍是「召回×40% + 忠实×30% + 相关×30%」，
  工具期望只作**通过闸**（与 `recallHit` 同级）。理由：综合分权重是历史运行的口径，
  改权重会让已有运行的 `avg_score` 与新运行不可比，而门禁门槛是按通过率算的，不受影响。
- 期望工具未调用时：`passed=0`，`failure_reason` 追加人话说明（缺哪个、实际调了哪些）。
- 期望工具**当前不可用**（该族在智能体上没开 / 该工具未挂载）时同样记未命中，
  但失败文案额外标注「期望工具在当前配置下不可用」，让用例编写者知道是配置问题还是模型问题。

### 2.2 后端改动

| 文件 | 改动 |
|---|---|
| `model/AgentEvalCase.java` | 无（`expectedTools` 已有） |
| `model/AgentEvalResult.java` | 加 `expectedToolHit` / `expectedToolTotal`（Integer）两列，落统计值 |
| `service/AgentEvalScorer.java` | 加 `expectedToolsOf(c)`（解析 JSON 数组 → Set）；`score(...)` 入参增 `actualTools`（Set<String>）；判据与失败文案 |
| `service/AgentEvalRunner.java` | 从 `done.toolCalls` 抽工具名集合传进 scorer；结果落两列 |
| `service/AgentEvalService.java` | `applyCaseFields` 已支持 `expectedTools`，补前端下拉选项来源（见 2.4） |
| `db/migration/V28__agent_eval_expected_tools.sql` | `c_ai_agent_eval_result` 加两列 + 索引无需（按 run 查） |

`score(...)` 签名变化会波及调用方（只有 `AgentEvalRunner` 一处），不扩散。

### 2.3 前端改动

| 文件 | 改动 |
|---|---|
| `web/src/views/AgentEvalPage.vue` | 用例编辑器加「期望工具」多选（选项来自 `GET /api/ai/agent/tool-catalog`，中文名以工具注册中心为唯一来源）；结果表加「工具期望」列（命中/总数） |
| `web/src/api.js` | 无新端点（复用既有 tool-catalog） |

### 2.4 验收

1. 用例填期望工具 `search_knowledge`，跑回归 → 命中则通过，不命中则失败且失败原因写明缺哪个。
2. 结果表「工具期望」列显示 `2/2` 形态。
3. 智能体关了联网搜索、期望工具填 `webSearch` → 失败文案含「期望工具在当前配置下不可用」。
4. 存量用例（`expected_tools` 为空）行为逐字不变，综合分与通过率口径不变。
5. `mvn test` 全绿；`npm test` + `npm run build` 通过。

## 3. P2-D · 定时回归

### 3.1 口径

- 定时计划挂在**套件**上：一个智能体一个套件 → 一条计划（唯一键 `agent_id`）。
- cron 沿用平台既有 5 段口径（分 时 日 月 周）+ timezone，与 `c_ai_scheduled_job`、
  工作流定时触发同一套解析（`ScheduledJobService.nextRunAt`）。
- 扫描与执行分离：平台周期任务扫描到期计划 → 推进 `next_run_at` → 触发回归（`trigger_kind=scheduled`）。
  **先推进再执行**是幂等保证：进程崩在执行途中，本周期不会重复触发。
- 撞闸处理：全局并发 2 / 每智能体 1 个的闸是既有的。定时回归撞闸时**跳过本轮并留日志**，
  不排队、不堆积 —— 下一周期自然补跑。人工触发的 `startRun` 仍是显式报错（行为不变）。
- 费用与通知：定时回归的用量记在**套件创建人**名下（`run.created_by`），
  沿用 `agentEval.done` / `agentEval.failed` 通知；用量 kind 仍是 `eval`。
- 无人可问的轮不能被定时回归触发成「等审批」——见 §0.4 副作用收口（副作用族整族不挂，
  剩下的都是只读工具，不需要人在场）。

### 3.2 数据结构

新增表 `c_ai_agent_eval_schedule`：

```
id            VARCHAR(50)  PK
tenant_id     VARCHAR(32)  默认 'default'
agent_id      VARCHAR(50)  NOT NULL   UNIQUE（一个智能体一条计划）
suite_id      VARCHAR(50)  NOT NULL
cron          VARCHAR(100) NOT NULL   5 段
timezone      VARCHAR(64)  默认 'Asia/Shanghai'
enabled       INT          默认 1
next_run_at   DATETIME     NULL（停用时清空）
last_run_id   VARCHAR(50)  NULL（最近一次定时触发的运行）
last_run_at   DATETIME     NULL
created_by    VARCHAR(64)
create_time / update_time DATETIME
```

### 3.3 后端改动

| 文件 | 改动 |
|---|---|
| `model/AgentEvalSchedule.java` | 新增实体 |
| `mapper/AgentEvalScheduleMapper.java` | 新增 mapper |
| `service/AgentEvalService.java` | 计划的增删改查；`tickSchedules()`：扫 `enabled=1 AND next_run_at<=now` → 推进 next → 调 `startRun(trigger="scheduled")`；推进失败/触发失败都留日志并保持 next 推进（不重试风暴） |
| `service/AgentEvalRunner.java` | 定时触发的运行 `created_by` 取套件创建人 |
| `controller/AgentEvalController.java` | `GET/POST /agents/{agentId}/schedule`、`POST /schedule/{id}/toggle` |
| `schedule/ScheduleCenter.java` | 注册平台扫描任务「智能体评测定时回归」，`registerWork` 形态（空跑不记日志），内置节拍 60s，configKey 传 null（节拍不进设置项） |
| `db/migration/V28__agent_eval_expected_tools.sql` | 增表 + `c_ai_agent_eval_result` 两列（同批迁移，编号顺延） |

`tickSchedules()` 幂等性依赖 `next_run_at` 单调推进 + 每智能体 1 个运行闸，两层都已有。

### 3.4 前端改动

| 文件 | 改动 |
|---|---|
| `web/src/views/AgentEvalPage.vue` | 套件设置区加「定时回归」块：cron 输入 + 时区 + 启停 + 下次执行时刻 + 最近一次结果跳转 |
| `web/src/api.js` | 新增 schedule 三个端点封装 |

### 3.5 验收

1. 建计划（cron `0 3 * * *`）→ 到点后运行历史出现一条 `trigger=scheduled` 的运行。
2. 运行详情页可见该次运行，用量记在套件创建人名下，通知照发。
3. 停用计划 → 不再触发，`next_run_at` 清空。
4. 进程重启后残留 running 照旧由启动清理器置 failed（`AgentEvalStartupCleaner` 已覆盖）。
5. 同智能体手动回归在跑时，定时触发被跳过并留日志，不产生第二条并发运行。

## 4. P2-E · 多轮评测

### 4.1 口径

- 一个用例可以包含**多轮**追问：第 1 轮提问，第 2 轮依赖第 1 轮的真实回答继续追问。
- 多轮的每一轮**各自判分**，各落一条 `result`；用例整体通过 = **所有轮都通过**。
- 套件通过率分母口径：**用例数**（不是轮数），与前端「共 N 条」一致；轮数另计一列
  `run.total_turns`，用于看成本。
- 单轮用例（存量全部）走原有路径，行为逐字不变。
- 多轮上限：单用例最多 **3 轮**（平台常量），超出在保存时拒绝。
- 轮数上限与总预算：单轮超时、单次总预算沿用既有常量；多轮用例的各轮共用同一条运行的总预算。

### 4.2 数据结构

新增表 `c_ai_agent_eval_case_turn`：

```
id                    VARCHAR(50) PK
tenant_id             VARCHAR(32)
case_id               VARCHAR(50) NOT NULL   INDEX
turn_index            INT          NOT NULL   （0 起）
question              VARCHAR(2000) NOT NULL
expected_knowledge_ids TEXT        NULL
expected_doc_ids       TEXT        NULL
expected_tools         VARCHAR(1000) NULL
judge_mode             VARCHAR(16) NULL
note                   VARCHAR(500) NULL
```

`c_ai_agent_eval_result` 加 `turn_index`（INT，默认 0），
历史行默认 0 —— 与「单轮用例的轮序号 0」天然对齐，历史结果表无需回填。

### 4.3 后端改动

| 文件 | 改动 |
|---|---|
| `model/AgentEvalCaseTurn.java` / `mapper/...` | 新增 |
| `model/AgentEvalResult.java` | 加 `turnIndex` |
| `service/AgentEvalService.java` | 用例的轮次 CRUD（`mutateCases` 扩展 `turns` 载荷）；`casesOf` 一并带出轮次；采样生成用例时同时落轮次 |
| `service/AgentEvalRunner.java` | 多轮执行：同一临时会话内按 `turn_index` 顺序连发多轮（每轮一轮问答 + 一次评分 + 一条 result）；会话清理仍在整条用例的 finally（多轮共用一个临时会话，**跑完整条用例才删**） |
| `service/AgentEvalScorer.java` | 无变化（评分口径与轮次无关） |
| `db/migration/V28__...` | 增表 + result 加 `turn_index` |

**多轮连续发问的实现要点**：`ChatService` 的轮级互斥按 sessionId，
串行 awaitDone 后再发下一轮即可；框架会话状态在 Redis 按 session 存，天然延续上下文。
第二轮及以后**不再带 `replayPrefix`**（那是固定前文回放，与真实延续互斥）。

### 4.4 前端改动

| 文件 | 改动 |
|---|---|
| `web/src/views/AgentEvalPage.vue` | 用例编辑器支持增删轮次；结果表按轮次分行展示（用例名 + 第 N 轮） |
| `web/src/api.js` | 无新端点（轮次随 cases 载荷走） |

### 4.5 验收

1. 建一条 2 轮用例 → 运行后结果表出 2 行（第 1 轮 / 第 2 轮），第 2 轮的回答确实接着第 1 轮。
2. 第 1 轮失败 → 整条用例判失败（不通过）。
3. 套件通过率分母是用例数（不是轮数），与用例列表条数一致。
4. 临时会话在整条用例跑完后被删（多轮中途不删）。
5. 存量单轮用例的运行结果与改动前逐字一致。

## 5. P2-F · 历史版本重测（config override 收口）

### 5.1 目标与口径

- 能按**某个历史版本的智能体配置**跑一轮回归，从而回答「v3 那会儿的表现比现在好还是差」。
- 覆盖范围 = `AgentService.VERSION_FIELDS` 白名单的 30 个调优字段（含人设、知识范围、
  工具开关、HTTP/工作流工具集、权限档位、记忆域等）。不在白名单的字段沿用当前行取值
  （`goalEnabled` 即属此类，界面须提示「深度执行开关沿用当前配置」）。
- 语义：**不落库**。历史快照只在内存里覆盖本轮生效的 Agent 行，不写 `c_ai_agent`，
  不产生版本记录，不改门禁状态（`changed` 判据只看真实保存产生的版本号变化）。
- 有副作用的工具族在评测轮**整族不挂**（见 §0.4）：历史快照含旧凭据，
  真实调用旧接口既越权又不可回滚。界面明确提示「历史版本重测不执行有副作用的能力」。

### 5.2 前置收口（先做，它是本项的主体工作量）

**(a) 统一解析口**

新增 `service/AgentConfigResolver.java`：

```
Agent resolve(String agentId)
```

- 先查本轮线程级 override（见 (b)），有则用快照 JSON 覆盖 `VERSION_FIELDS` 白名单字段，
  其余字段沿用当前行；无则等价于现行为。
- override 装载点：`ChatService` 的**流水线线程**内，与既有 `loadIdentity(userId)` /
  `configService.putUserOverrides(...)` 同一段、同一生命周期（finally 清理）。

**(b) override 的传递**

线程级 override 无法跨线程自动传递（评测 runner 线程 → `pipelineExecutor` 线程），
所以 override 随命令走：`ChatCommand` 加字段 `agentConfigOverride`（String，AgentVersion 快照 JSON）。
流水线线程按 `cmd` 装载。

**(c) 直读点改走解析口**

| 位置 | 现状 | 改为 |
|---|---|---|
| `AgentService#get(id)` | 直接查库 | 内部走 resolver（保持对外签名不变，调用点零改动） |
| `HttpToolService#mount(agentId)` | `agentMapper.selectById` | 走 resolver |
| `WorkflowToolService#mount(agentId, ...)` | `agentMapper.selectById` | 走 resolver |
| `ChatService#loadAgentQueryOverrides` | `agentService.get` | 走 resolver |
| `WenquAgentxTools#agentOf(cmd)` | `agentService.get` | 走 resolver（且优先用 `cmd` 里的 override） |

**(d) 副作用族收口**

`ToolAssemblyService#mountContext` 增一条：本轮 `source=eval` 时，
`HTTP_API` / `WORKFLOW` / `MCP` / `SANDBOX` / `LOCAL_BROWSER` 五族整族不挂，
并在 `degrade` 里登记一条可见降级（说明「评测只读，未挂载有副作用能力」）。
该收口对 P2-C/D/E 一并生效（现状下评测就会真调 HTTP 工具，属现存风险）。

**(e) 记忆隔离**

专属/叠加记忆域的根按 agentId 分，历史重测与当前配置共用同一根 → 污染。
评测轮强制按「不写记忆、不注入用户全局记忆」处理（不影响召回与引用判分）。

**(f) 框架实例指纹**

`AgentscopeChatEngine#bindingOf` 的 key 用 `id@updateTime`。override 行沿用当前 `updateTime`，
同会话可能复用旧实例配置。override 生效时把 key 追加 override 标识（版本号），
保证不同版本的实例不互相复用。

## 7. 风险与边界

- **成本**：多轮评测与定时回归都会放大模型调用量。定时回归的频率由用户 cron 决定，
  平台不代设「每日最多一次」这类硬限；单次运行的用例数上限沿用既有常量。
- **单副本**：平台部署形态是单副本（见账本 D1 拍板），定时扫描不引入分布式协调；
  进程重启后残留 running 由既有启动清理器收口。
- **评审口径**：工具期望与多轮都只加「更严的失败条件」，不加新的打分维度，
  因此门禁门槛数值与历史运行的口径不需要重标定。
- **不做**（明确出界）：
  - P3 用户模拟器（生成对抗变体问题）、pass^k（多次运行一致性）—— 立项方案列为「待定」，本期不做。
  - 评测集市场模板 / 跨智能体复用 —— 同上。
  - 历史版本重测的「配置差异可视化对比」—— 现有两次运行对比已能看分数变化，
    不再叠一层配置 diff 视图。

## 9. 提交拆分与验证顺序

一个批次一笔提交，串行推进：

```
feat(eval): 工具期望评分参与通过判定           ← P2-C
feat(eval): 评测定时回归（套件级 cron 计划）      ← P2-D
feat(eval): 多轮评测（用例含追问轮次）           ← P2-E
feat(eval): 历史版本重测——配置覆盖收口          ← P2-F
```

每笔提交前的自查（沿用 CONTRIBUTING 口径）：

1. 后端编译通过 + `mvn test` 全绿
2. 前端 `npm test` + `npm run build` 通过
3. 未引入密钥或本地私有配置
4. 本批无设置项新增 → `config-schema.json` 无需同步（若后续引入设置项则必须同步）
5. 文档同步：README / 手册 / 账本随该笔一起改

真机验证（每批）：隔离库 + 后端 + 前端 + 真实模型，按上表验收清单逐条走查。
