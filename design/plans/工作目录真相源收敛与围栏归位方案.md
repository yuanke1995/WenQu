# 工作目录真相源收敛 + 安全边界归位 实施方案

> 目标：消除「声明的 root 围栏 ≠ 实际执行的边界」「工作目录三套口径各算各的」两类架构缺陷。
> 不做：会话内 cwd 切换工具（它是第三步之后才谈的能力，见 §8）。
> 本文所有行号 based on 2026-11-23 工作树；改动以方法名与语义为准，行号仅供定位。

## 0. 背景与问题陈述（为什么做）

审计确认两个事实，构成本方案的出发点和验收标尺：

**事实 A — root 围栏不闭合。**
`ProvisionerSandboxBackend.canReadPath/canWritePath/canListPath`（`ProvisionerSandboxBackend.java:199-234`）是工具层字符串前缀 allowlist，根为 `virtualPathPrefix()`（默认 `/home/gem/user-data`）。但：

- 模型主链路的框架文件系统 `ProvisionerSandboxFilesystem` 的 `write/uploadFiles/ls/glob/downloadFiles` 直连 `backend.getClient()`，**不过 `canWritePath/canListPath/canReadPath`**（`ProvisionerSandboxFilesystem.java:236-242, 269-278, 325-330, 393-410`）；真正过检查的只有 `backend.read()`（`:369`）。
- `workspaceAbsolutePath()` 对以 `/` 开头的路径原样返回（`:724-734`），框架传绝对路径不被收窄。
- `execute()` 只包 `cd /home/gem/user-data && (...)`，无任何路径围栏（`:709-713`）；`SandboxEnforcement.PARTIAL` 明确承认"命令内写入不受束"。
- `backend.edit()/uploadFiles()/grep()/glob()` 全仓零调用方。
- 真正守住宿主数据的是 Docker bind mount（仅 `/home/gem/user-data` rw）与容器命名空间，与这段 Java 检查无关；且 provisioner `seccomp=unconfined`。

**事实 B — 工作目录没有单一真相源。**
`projectId` / `Session.ws_*` / 沙盒 scope 三套口径被十余个消费者各自解析；`sessionWorkspaceKey()`（`SandboxService.java:107-123`）只覆盖部分变化：

- 显式本机工作区 A→B、`bindRoots()` 本机重绑，key 恒为 `"project"`，不触发实例重建 → build 期 FS、prompt、guard roots、skill 根留旧值。
- `sandbox.userScope` false→true 不改 key、无配置监听。
- local→cloud 回退时 `localExecutorEnvironment()` 仍只读 `Session.wsRoot`，提示词说"在本机"而实际在云端（`AgentscopeChatEngine.java:2424-2437`）。
- `wsBackend` 代码从不写 `"cloud"`，与实体注释冲突。
- `SandboxService` 类注释（`:39-50`）描述的"scope=工作区 id、workdir=projects/{id}"早已不存在。

**本方案要建立的架构不变量（invariant）**：

1. **一条会话在某一轮，有且只有一份被解析好的工作目录描述**（`EffectiveWorkspace`），所有消费者从它取；不允许任何消费者重新查库自己算根/scope。
2. **实例键是这份描述的完整函数**：描述里的任何字段变了，实例键必变，下一轮必重建。
3. **围栏只有一个声明点**：`ProvisionerSandboxBackend` 的路径判定是唯一判据，`ProvisionerSandboxFilesystem` 的每条结构化 I/O 都先过它；shell 不在围栏覆盖范围，并在 UI/提示中如实标注。

## 2. P0 — 止血（5 个已确认缺陷）

### P0-1 修正 `sessionWorkspaceKey()` 的完整度

**文件**：`src/main/java/com/wenqu/ai/service/SandboxService.java`（方法 `sessionWorkspaceKey`，约 :107-123）

**现状**：显式本机工作区返回常量 `"project"`；不含 `projectId`、root 列表、`userScope` 结果。

**改法**：
```java
public String sessionWorkspaceKey(String sessionId, String uid) {
    Project bound = projectService.projectOfSession(sessionId);
    if (bound != null && Project.SELECTION_IMPLICIT.equals(bound.getSelectionStatus())) {
        // 隐式会话沿用现有分支（SSH/本机/cloud）
        ...
    }
    if (bound == null) { ... } // 原逻辑
    // 显式工作区：把 projectId + 所有 root 的 (alias,path,primary) 稳定排序后编进 key
    StringBuilder k = new StringBuilder("project:").append(bound.getId());
    for (ProjectRoot r : sortedRoots(projectService.rootsOf(bound))) {
        k.append('|').append(r.getAlias()).append('=').append(r.getPath())
         .append(r.getPrimaryRoot() == ProjectRoot.PRIMARY ? "*" : "");
    }
    // SSH 别名已在原逻辑里通过 executorId+primary 编入；此处统一为「全部 root」覆盖 bindRoots 重绑
    return k.toString();
}
```
要点：显式工作区**不再有"换 root 但 key 不变"的口子**；`bindRoots()` / `moveSessionProject()` 都无需额外失效代码——下一轮 key 自然变化触发 `FrameworkSessions.openLocked()` 重建（`FrameworkSessions.java:326-343`）。

**行为不变的部分**：隐式会话 `local:<executorId>:<rootPath>` / `cloud` 两种值及其触发的重建语义不动。

**验收**：见 §6 T1。

### P0-2 修正 local→cloud 回退时的提示词

**文件**：`AgentscopeChatEngine.java`（`localExecutorEnvironment`，约 :2424-2437；调用点 :3405）

**现状**：只读 `sandboxService.pinnedLocalWorkspaceRoot()`（库里的 `wsRoot`），不检查本轮是否真的走本机。

**改法**：
- 在 `buildAgent()` 里（:3380 附近）取本轮 `SessionWorkspaceService.Workspace ws = sessionWorkspace.resolve(...)`，作为局部变量。
- `localExecutorEnvironment(cmd, ws)` 改为接受该 ws 参数：
  - `ws == null || !ws.local()` → 返回 ""（本轮不是本机后端，整段缺席；本轮在云端由别处的沙盒提示负责说明）。
  - `ws.local()` → 用 `ws.rootPath()` 渲染（不再读库）。
  - `ws.fallbackNotice() != null` → 额外渲染一句"本机执行器不在线，本轮文件改在云端"，与 UI 的 `wsEffective` 口径一致（`SessionService.java:259-272`）。
- 断言：本轮提示里出现的"当前工作区根目录"必须是模型实际能 `cd` 到的那个目录。

**验收**：见 §6 T2。

### P0-3 确定采用 B：`wsBackend` 三列只存「已钉住的本机绑定」，本轮后端由 `EffectiveWorkspace` 派生

**结论：选 B。B 的完整态不止改注释，见下文三部分。A 是错的，必须否决。**

**为什么 A 错（三条硬理由）**：

1. **目录名含标题，不是"含短 id 就稳定"**：`dirNameOf()` = `yyyyMMdd-{标题slug}-{短id}`（`SessionWorkspaceService.java:223-228`）。短 id 稳定，标题 slug 不稳定——会话改名是常态。A 要求 cloud 时清 `wsRoot`、恢复在线时重建，那一步会用**新标题算出新目录**，旧目录的文件就此脱离会话视图。原方案里"目录名含短 id，稳定"那句是错的。
2. **破坏钉住不变量**：类注释明确"解析结果首轮落库后钉住：目录跟着会话走，不因为本轮换了哪台在线设备而搬文件"（`:24-25`）。执行器上下线是运行时抖动，不是用户改绑；把它写进库等于让抖动改写持久状态。
3. **连锁退化**：`existingLocal/pinnedLocal/pinnedLocalRoot/localReady` 全以 `wsBackend=local && wsRoot` 为判据（`:137-172`）。落库 cloud 后，离线期间这些全变 null/false → 分档粘性掉档、文件栏空、prompt 丢根说明。用户只是执行器暂时离线，会话却像"丢了工作区"。

**B 的完整态（三部分，缺一不可）**：

1. **持久化侧**：`wsBackend/wsExecutorId/wsRoot` 定义为本机绑定的钉住记录；`resolve()` 永不写 `cloud`，离线只返回瞬时 cloud（现状代码已如此，行为不动）。实体注释改为："这三列记录已钉住的本机工作区绑定；`cloud` 是本轮由执行器在线状态派生的瞬时后端，不落库。"
2. **accessor 分层**：把"读钉住绑定"与"算本轮后端"拆成两个 API——`pinnedLocalBinding(sessionId)` 只读库（供重连后找回目录、文件栏、粘性判据）；`resolve(sessionId, uid)` / `EffectiveWorkspace` 算本轮后端（供 FS/prompt/执行）。禁止消费者拿 binding 当"当前后端"，也禁止拿 ew 当"持久绑定"。
3. **派生侧落到 ew**：`EffectiveWorkspace.kind/executorId/scopeId/rootPath/fallbackNotice` 是"本轮在哪跑"的唯一真相；P0-2 已让 prompt 用它，P1 让所有消费者用它。

**明确不做**：不加 `wsBackend=cloud` 的写入路径；不清空 `wsRoot`；不把瞬时后端塞进数据库。

**验收**：见 §6 T3。

### P0-4 删除过时的 `SandboxService` 类注释

**文件**：`SandboxService.java:39-50`

**改法**：把"作用域：工作区优先，会话兜底 / scope=工作区 id / workdir=projects/{id} / 同工作区多会话共享容器"整段替换为与 `scopeOf()` 一致的描述：

```
作用域：显式工作区走本机执行器/SSH，不经服务器沙盒；服务器沙盒只服务无工作区会话，
scope 默认 = sessionId，sandbox.userScope=true 时 = uid；workdirPath 恒为 null，

```

**验收**：静态契约测试（§6 T4）扫描该注释里不得出现"scope = 工作区 id"等旧说法。

### P0-5 `sandbox.userScope` 热切换失效

**文件**：`ConfigService.java`、`SandboxService.java`、`FrameworkSessions.java`

**改法**：
- 在 P0-1 的 `sessionWorkspaceKey()` 里，`scopeOf()` 的结果（sessionId / uid）已经体现在隐式 cloud 分支；补充：隐式 cloud 分支返回 `"cloud:" + scopeOf(sessionId,uid).scopeId()`，这样 `userScope` 从 false→true 时 key 从 `cloud:<sid>` 变 `cloud:<uid>`，下一轮自动重建。

**验收**：见 §6 T5。

## 3. P1 — 引入 `EffectiveWorkspace` 统一真相源

### 3.1 类型定义

**新增文件**：`src/main/java/com/wenqu/ai/service/EffectiveWorkspace.java`

```java
public record EffectiveWorkspace(
    String key,                  // 实例键的 workspace 分量：任何影响 build 期状态的字段都必须进来
    Kind kind,                   // EXPLICIT_LOCAL / EXPLICIT_SSH / IMPLICIT_LOCAL / IMPLICIT_CLOUD / CHAT_SCRATCH
    List<String> roots,          // 工作区根，主根第一（guard / prompt / fs 共用，不再各算各的）
    String primaryRoot,          // 主根绝对路径；无根为 null
    String executorId,           // 本机执行器 id（IMPLICIT_LOCAL / EXPLICIT_* 有值）
    String scopeId,              // 沙盒 scope（IMPLICIT_CLOUD 有值）
    boolean serverSandbox,       // 本轮是否挂服务器沙盒
    String fallbackNotice,       // 离线回退说明；null=无
    String displayName           // UI/prompt 用的工作区名（可空）
) {
    public enum Kind { EXPLICIT_LOCAL, EXPLICIT_SSH, IMPLICIT_LOCAL, IMPLICIT_CLOUD, CHAT_SCRATCH }
}
```

设计约束（写进类注释）：
- **不可变**：一轮内不重算；`key` 是全部字段的稳定函数（用 `String.join` + 排序，保证 root 顺序变化也稳定）。
- **一次解析**：由 `SandboxService.resolveWorkspace(sessionId, uid, wantsSandbox)` 产出；任何消费者不得再自行调 `projectOfSession` / `sessionWorkspace.resolve` / `scopeOf` 推根。

### 3.2 解析入口

**文件**：`SandboxService.java`

新增：
```java
public EffectiveWorkspace resolveWorkspace(String sessionId, String uid, boolean wantsSandbox) {
    if (sessionId == null || sessionId.isBlank() || uid == null || uid.isBlank())
        return null;
    Project p = projectService.projectOfSession(sessionId);
    boolean explicit = p != null && !Project.SELECTION_IMPLICIT.equals(p.getSelectionStatus());
    if (wantsSandbox && explicit) {
        List<ProjectRoot> roots = ... // 排序：primary 第一
        String execId = projectService.executorIdOf(p);
        boolean ssh = projectService.isSshAlias(p);
        return new EffectiveWorkspace(
            keyOfExplicit(p, roots, execId, ssh),
            ssh ? EXPLICIT_SSH : EXPLICIT_LOCAL,
            paths(roots), primary(roots), execId, null, false, null, p.getName());
    }
    SessionWorkspaceService.Workspace sessionWs = sessionWorkspace.resolve(sessionId, uid);
    if (wantsSandbox && sessionWs != null && sessionWs.local()) {
        return new EffectiveWorkspace(
            "local:" + sessionWs.executorId() + ":" + sessionWs.rootPath(),
            IMPLICIT_LOCAL, List.of(sessionWs.rootPath()), sessionWs.rootPath(),
            sessionWs.executorId(), null, false, sessionWs.fallbackNotice(), null);
    }
    if (!wantsSandbox) {
        return new EffectiveWorkspace("scratch:" + uid + ":" + sessionId, CHAT_SCRATCH,
            List.of(), null, null, null, false, null, null);
    }
    SandboxScope s = scopeOf(sessionId, uid);   // 私有方法保留
    return new EffectiveWorkspace(
        "cloud:" + s.scopeId(), IMPLICIT_CLOUD, List.of(), null, null,
        s.scopeId(), true, sessionWs == null ? null : sessionWs.fallbackNotice(), null);
}
```

要点：
- `resolveWorkspace` 是**唯一的解析入口**；现有 `sessionWorkspaceKey/localSessionWorkspace/sessionWorkspaceNotice/pinnedLocalWorkspaceRoot` 保留为薄封装（内部调它），供工作流/定时任务等旁路调用，但**引擎主链路只调 resolveWorkspace**。
- `key` 的算法集中在 `keyOfExplicit` / `keyOfImplicit`，P0-1/P0-5 的改动并入此处，不再散落。

### 3.5 失效协议

- 实例键已经是 `ew.key()` 的函数 → 所有 root 变化自动失效（P0-1/P0-5 已覆盖）。
- `FrameworkSessions.markConfigStale/markAllConfigStale`（:1184-1201）保留给真正的平台级配置（`memory.*`）。
- 新增 `SessionService.moveSessionProject()` / `ProjectService.bindRoots()` 的**后置钩子**：不需要调用 markStale（key 会变），但要在日志里打 `oldKey→newKey`，便于排障。
- 跨副本：切 root 若发生在另一副本，下一轮该副本按库算出的 `ew.key()` 必然不同，`openLocked()` 自行重建；无需新增 Redis 状态（与 `AgentxCluster` 现有租约语义一致）。

## 4. P2 — 安全边界归位

### 4.1 结构化 I/O 全部接入 backend 路径判定

**目标**：`ProvisionerSandboxFilesystem` 的每条结构化 I/O 与 `ProvisionerSandboxBackend` 的结构化方法，走**同一个** allowlist 判据，杜绝"声明有围栏、主链路绕过"。

**改法**（`ProvisionerSandboxFilesystem.java`）：

1. 在 `ProvisionerSandboxBackend` 暴露包级/公有判定入口（供 filesystem 复用，避免复制判据）：
```java
public String guardRead(String path) {          // 返回 null=放行，否则返回给模型的错误串
    String n; try { n = normalizePath(path); } catch (RuntimeException e) { return "Invalid path ..."; }
    return canReadPath(n) ? null : "Error: " + permissionError("read", n);
}
public String guardWrite(String path) { ... canWritePath ... }
public String guardList(String path)  { ... canListPath ... }
```
2. 在 filesystem 的每个入口先判、再打容器：
   - `uploadFiles()`（:227-255）：每条 `target = workspaceAbsolutePath(path)` 后 `guardWrite(target)`，拒则 `FileUploadResponse.fail(path, err)`，不打 client。
   - `write()`（:199-210）：复用 uploadFiles 的判定，无需重复。
   - `downloadFiles()`（:269-297）：每条先 `guardRead(workspaceAbsolutePath(path))`，拒则 fail。
   - `ls()`（:325-343）：`guardList(target)`，拒则 `LsResult.fail`。
   - `glob()`（:393-441）：`guardList(target)`，拒则 `GlobResult.fail`。
   - `read()`（:359-379）：已走 `backend.read()` → 已有检查，不动。
3. `workspaceAbsolutePath()`（:724-734）：绝对路径不再无条件原样返回——改为：若绝对路径不在 `userDataRoot` 下，**仍原样返回**（因为 guard 会拒），保证错误信息里是真实路径；不要在解析层静默改写用户路径。
4. 零调用方方法 `backend.edit()/uploadFiles()/grep()/glob()`：保留（对齐参考实现的合同），类注释明确"框架主链路不调这些方法；它们仅供直接 API 使用"。

**验收**：见 §6 T6（契约测试扫描：filesystem 的每个 override 方法体内必须出现对应的 guard 调用）。

### 4.2 shell / danger-full-access 的诚实标注

**不改代码行为**，只改声明，避免"围栏管住了 shell"的误解：

- `ProvisionerSandboxBackend.execute()` 类注释与 `inWorkspace()` 注释（:695-713）补一句："此处的 cd 只设默认工作目录，**不是访问边界**；容器内 `/etc`、`/tmp` 等路径 shell 可达，只是不在宿主 bind mount 上，容器回收即丢。"
- `SandboxEnforcement.PARTIAL` 已在工具卡暴露；确认 UI 上"工作区内修改"档的文案不承诺"不能读工作区外"——如果承诺了，改为"写操作被限制在工作区内；命令可读取容器内其它路径"。
- `config-schema.json` 里 `sandbox.virtualPathPrefix` 的说明补："仅约束结构化文件工具与写类路径；不约束 shell 命令"。

## 8. 为什么现在不做 cwd 切换工具（架构理由，不是接受度）

审计列出的联动面有九处：真相源/解析层/实例键与失效/build 期 FS+SandboxContext/prompt+schema/技能+记忆/产物+浏览 token/后台进程/跨副本。P1 之前没有"运行期可切 root"的抽象——现有模型的 root 在 build 期固化，靠实例键变化间接重建。P1 完成后，`EffectiveWorkspace` + key 失效协议提供了唯一落点：届时切 root = 改变工作区归属（复用 `moveSessionProject`）或新增会话级 override 字段，两者都自然触发 `ew.key()` 变化 → 重建。届时还需先定义：产物归属、工作区记忆、技能、后台进程、prompt 各跟不跟新 root。这些现在没有答案，所以 P3 不在本方案范围。
