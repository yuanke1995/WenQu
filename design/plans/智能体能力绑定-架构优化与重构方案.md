# 智能体能力绑定：架构对齐与重构方案（借鉴优先版）

- 日期：2026-11-24
- 定位：**不做第二套框架**。站在 DSH / AgentScope 的肩膀上，能直接用的直接接，不能直接用的只做胶水。
- 目标：把「智能体绑定知识库/技能/MCP/HTTP/工作流/记忆/子智能体」从自研装配层，收敛到框架已有的扩展点上；删除重复实现，而不是再自研一套新概念。
- 关系：此前 4 个 bug 修复是执行债清理；本文是架构收敛方案，不把 bug 修复包装成架构成果。

---

## 0. 一句话原则

> **框架有的，直接用；框架没有但别人做对的，按同一契约接；只有业务语义（租户、权限、知识库、市场）才自研。**

问渠现在的很多“设置项”其实是在重复框架已经解决的问题：
- 技能：AgentScope 已有 `RuntimeContextSkillRepository` + `SkillFilter` + 渐进披露；
- 工具：AgentScope `HarnessAgent` / `Toolkit` 已有工具注册、分组、可见性与执行链；
- 团队：已经改成框架 `teamsMode`，自研团队层已删除；
- 子智能体：框架 `agent_spawn` / subagent provider 已有名字树、深度、容量、权限边界；
- MCP：DSH 的 `mcp-client` 已有配置化接入、命名空间、重连、凭据 scrub；
- 记忆/工作区：框架的 Workspace/Memory tools 已有按 RuntimeContext 隔离；
- 会话状态：框架已有 session/state，团队事件账本也只是投影。

所以本次架构工作的主基调应该是 **“对齐框架 + 删除重复层 + 薄适配”**，而不是设计 `CapabilityRegistry`、`BindingLayer`、`ToolPolicyPipeline` 这类自研基础设施。

## 1. 借鉴清单：谁已经做好了，我们直接用

| 需求 | 成熟实现（直接借鉴/接入） | 问渠只保留什么 |
|---|---|---|
| 智能体版本化配置 | DSH `@deepseek-ai/dsh-agent-preset` 的声明式 preset + revision；本仓已有 `c_ai_agent_version` 快照 | 版本读取与权限判断的胶水；不要另造 `AgentRevision` |
| 技能目录/正文加载 | AgentScope `RuntimeContextSkillRepository`、`SkillFilter`、`WorkspaceSkillRepository` | 只做 ref 解析与来源校验；不要自研技能注册中心 |
| 工具注册/可见性 | AgentScope `HarnessAgent` builder + `Toolkit` / tool groups；`ToolMountContext` 已是收口点 | 领域工具本身；不要另造工具策略引擎 |
| 工具执行审批 | 框架 `ToolGate` / 现有 `AgentxFrameworkToolGate` / `SpringAiToolAdapter` | 统一到框架 gate，删除散落 if |
| MCP 接入 | DSH `@deepseek-ai/dsh-mcp-client` 的配置形状（serverName / transport / reconnect / credential template / env scrub） | 用现有 Java MCP SDK 适配；不要自研协议层 |
| 子智能体/团队 | 框架 `teamsMode` + `agent_spawn` + subagent provider | 只保留任务板/邮箱的领域 shim（已存在） |
| 会话状态 | 框架 session/state + 现有 team task event 投影 | 不新造状态机；UI 从事件/投影派生 |
| 提示词组装 | 框架 `systemPrompt` section/variable；工具 schema 自动进装配 | 只写业务 section；不要手工拼整段 sysPrompt |
| 凭据 | DSH credentials record + Loader 引用 + 运行期 credential template + redaction | 保留现有 JWE 作为存储实现；不要把密文塞进工具 schema |
| 用户授权动作 | DSH `user-actions`：一个 Host 方法，UI 与 agent tool 共用；批准类 user-only | 沿用现有审批卡形状，不另造两套 |

## 2. 当前哪些是“自研重复层”，应该删掉

| 自研层 | 与框架重复在哪 | 处理 |
|---|---|---|
| `ToolAssemblyService.agentFlagFor` 的「族→列」映射 | 框架已有工具可见性/分组；这层只是把 Agent 列翻译成开/关 | 保留为**临时适配器**，迁到统一 tool selection 后删除 |
| 各 provider 自己写 `agentFlag` / `agentSelection` / `guest whitelist` | 框架 `Toolkit` 与 `ToolMountContext` 已能表达 | 去掉 provider 内重复判断，统一在装配点一次生成可见工具集 |
| `HttpToolService` / `WorkflowToolService` 自己解析 Agent 行、自己判停用/可见性 | `AgentService.get/readable` 与框架 RuntimeContext 已有身份 | 用统一解析结果，删除 mount 内重复查询 |
| 技能 `{uid}/{name}` / 裸名 / 新规范 ref 三套解析 | 框架 `SkillFilter` 只认 name；来源应由 Provider 决定 | 只保留一个薄 `SkillRef` 解析器；**不要**再自研技能 registry |
| 自研团队层（历史） | 框架 `teamsMode` | 已删除；保持只读 thin shim（`team_task_depend`） |
| 自研记忆/工作区上下文 | 框架 Workspace/Memory tools | 保留业务策略（记忆域三态），删除重复的工具/路径实现 |
| 每族一个平台开关 | 框架按 policy/tool descriptor 控制 | 新增能力不再长平台开关 |

## 3. 目标架构 = 框架 + 薄适配

```text
Agent 配置（身份/人设/策略）
    ↓  读取现有版本快照（c_ai_agent_version），不新造模型
Framework HarnessAgent
    ├── Toolkit / tool groups      ← 工具可见性、执行、审批全部走框架
    ├── RuntimeContextSkillRepository / SkillFilter ← 技能目录与按需加载走框架
    ├── teamsMode / agent_spawn    ← 团队与子智能体走框架
    ├── Memory / Workspace tools   ← 记忆与文件上下文走框架
    └── session/state              ← 会话与投影走框架
    ↑
问渠薄适配层（只做四件事）
    1. 领域资源解析：知识库、市场、租户、权限、共享范围
    2. 业务策略：知识检索范围、记忆域、游客/API Key 收窄
    3. 数据形状：Agent 版本快照 ↔ 框架 builder 参数
    4. 可观测：审计、台账、工具卡、降级原因
```

**关键决定**：不再引入 `CapabilityRegistry` / `BindingLayer` / `ToolPolicyPipeline` 这类自研底层。需要的“能力目录”用现有 `ToolRegistry` + provider descriptors 表达；需要的“版本”用已有 `c_ai_agent_version`；需要的“审批”用现有 `AgentxFrameworkToolGate`。

## 4. 对齐/删除路线（每一阶段都删旧路径）

### Phase 0：先看清框架已有什么（1 周，只读）

- 对照 AgentScope `HarnessAgent` builder 的现有参数（`toolkit`、`skillRepositories`、`skillFilter`、`teamsMode`、`subagentFactory`、`memory`、`workspace`）逐项盘点。
- 产出一张「框架能力 × 问渠现状 × 重复层」表；确认哪些开关其实由框架原生支持。
- 不写业务代码；只做基线测试（现有工具表、技能目录、检索范围、团队行为）作为后续等价性验收。

### Phase 1：把技能/工具接回框架原生扩展点（1–2 周）

- 技能：保留 `WenquSkillRepository` 作为 `RuntimeContextSkillRepository` 适配器；`SkillFilter` 只传裸名；删除工作流/智能体里各自的技能解析分支，统一用同一个薄 `SkillRef`。
- 工具：各 provider 只提供 `descriptors()` 与 `callbacks()`，三态/白名单/游客/审批全部上移到 `ToolMountContext` 一处；provider 内重复判断删除。
- 出口：新增一个工具族时只写 provider，不改 Agent 表、不改 `agentFlagFor`、不改前端三态。

### Phase 2：把版本/覆盖/默认解析收回一个入口（2 周）

- 用已有 `c_ai_agent_version` 做 revision 读取；`resolveForTurn` 作为唯一临时覆盖入口（已有雏形）。
- 统一 `agentOf` / `get(agentId)` 的读取路径：所有消费点拿同一份 resolved 视图。
- 删除各 mount 里重复的停用/可读/可见性查询；可见性只在这一层结算。
- 出口：全仓只有一处 Agent 解析；ArchUnit 禁止 `agentMapper.selectById` 出现在 service/agentx 消费路径。

### Phase 3：执行链只用框架 gate，不再自研第二套（1–2 周）

- 删除自研的重复 gate 分支（`AgentxFrameworkToolGate` 之外的散落判据），统一由框架工具执行链 + 现有 gate 处理。
- 审批/游客/分支差异通过工具 descriptor 的 policy 字段表达；不再在 provider 里写 if。
- 出口：新增能力自动获得同一套审批与游客约束。

### Phase 4：状态/证据复用框架机制（1–2 周）

- 团队任务事件已是 projection 雏形；继续用框架 session/state，不再新增自研状态存储。
- 审计/版本指纹沿用现有台账；不新造第二套运行日志。
- 出口：fork/resume 后可从日志重建；UI 状态不依赖服务级内存。

### Phase 5：删除旧列/旧适配器（1 周）

- 删除旧 `toolXxx` / `skills` / `mcps` / `httpTools` / `workflowTools` 的读路径；Agent 表只保留身份、人设、策略。
- 删除 `LegacyAgentBindingAdapter`（Phase 0 引入的临时层）。
- 出口：新增能力零表结构变更；`c_ai_agent` 不再膨胀。

---

## 5. 明确不做什么（防止再次自研）

1. **不自研 CapabilityRegistry / BindingLayer**：框架已有 Toolkit、SkillRepository、ToolRegistry、version snapshot；用它们。
2. **不自研 ToolPolicyPipeline**：沿用框架工具执行链 + 现有 `AgentxFrameworkToolGate`；最多补一个薄策略适配器。
3. **不自研技能 Registry/Provider**：`WenquSkillRepository` 已实现框架接口，只做来源适配；不新增技能命名体系。
4. **不自研团队/子智能体层**：`teamsMode` + `agent_spawn` 已经够用，继续只保留 thin shim。
5. **不自研状态机/事件模型**：框架 session/state + 现有事件账本。
6. **不重新发明 MCP 协议/凭据格式**：沿用 DSH `mcp-client` 的配置/凭据/重连语义，Java 侧只做 SDK 适配。
7. **不为每族加平台开关**：能力策略归 descriptor/policy，不归设置页。

---

## 6. 验收（对齐是否真的完成）

- Agent 表只剩身份、人设、策略；新增能力不新增列。
- 工具/技能/团队/子智能体全部走框架原生扩展点，provider 内没有重复的三态/游客/审批 if。
- 全仓只有一处 Agent 解析；ArchUnit 守住「消费点不得直读 AgentMapper」。
- 版本快照、临时覆盖、默认智能体走同一入口；不需要逐字段记得并进实例指纹。
- 任何新增能力只写 provider + descriptor，不改装配层、不改前端三态、不改 Agent 表。
- 旧自研层删除；没有“新旧两套判断长期并存”。

---

## 7. 结论

**架构优化不是自研更漂亮的抽象，而是把能力交还给框架已经做好的机制。** 问渠的竞争力在知识库、租户权限、市场与领域工作流，不在重新发明 skill registry / tool pipeline / team layer。下一步应做的是 Phase 0 的框架能力盘点 + Phase 1 的技能/工具回接，而不是继续给现有装配层加开关或补丁。
