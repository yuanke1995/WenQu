## 0 结论先行：为什么必须补底座

DSH Team 包对自己的最小依赖写得很死：

> 在**已经提供 continuable subagent、其消息工具和持久会话存储**的组合中挂载两个 Team 包。

DAG 方案 §2–§4 把「共享任务板」做出来了，但它明确写了"子智能体分支不挂 TASK 工具（默认）"，并把等待恢复留作降级路径。结果是：任务板能画、依赖能解锁，但**团队成员之间接不上力**——成员 A 把任务让给成员 B，B 收不到；A 完成前置后 B 在跑的轮次不会被告知；B 跑完即删，成果只能一次性回报给父轮。这不是"团队"，是"带依赖图的并行批处理"。

所以分两层走：

| 层 | 内容 | 归属方案 |
|---|---|---|
| **底座层（本文）** | 持久子会话、成员树与身份、双向消息 + inbox、冷恢复、完成通知 | 本文 §2–§5 |
| 任务板层 | 任务实体、依赖 DAG、CAS 认领、看板 UI、等待唤醒 | DAG 方案 §2–§4（挂载在底座之上） |

底座做完后，DAG 方案的 §9-3 答案变成"挂"，且它的降级路径可以升级成主路径（成员在线时直接 `send_message` 唤醒）。

## 1 现状事实链（逐条对应代码，不写没核实的假设）

### 1.1 子会话现在是"一次性"的

- 派出一支：`SubAgentBranchRuntime.branchRunner()` 用 `sessionService.createTempSession(userId)` 建临时会话（[SubAgentBranchRuntime.java:197](../../src/main/java/com/wenqu/ai/agent/subagent/SubAgentBranchRuntime.java#L197)），`ChatCommand` 带 `subagentDepth>0`、`parentSessionId`、`parentTurnId`（:200-221）。
- 跑完删掉：`finally` 里 `sessionService.deleteSession(...)`（[:360-365](../../src/main/java/com/wenqu/ai/agent/subagent/SubAgentBranchRuntime.java#L360)）。
- `kind=temp` 的会话在所有用户侧查询里被排除：`SessionService.java:407,596,746`、`MessageMapper.java:136`、`SessionEventMapper.java:32`、`ConversationSearchService.java:26`、`SessionEventSearchService.java:31`。
- 结论：**没有持久子 Session、没有可恢复的成员身份、用户在界面上点不到子会话**。

### 1.2 成员身份是"配置白名单"，不是"运行时树"

- `Agent.subAgentIds` 是静态逗号串（[Agent.java:221-230](../../src/main/java/com/wenqu/ai/model/Agent.java#L221)），决定谁能被派；前端"委派编排视图"画的是这份配置图（[AgentsPage.vue:22-23](../../web/src/views/AgentsPage.vue#L22)、[useDelegationTopo]）。
- 派遣走框架 `agent_spawn`，问渠把每位可咨询助手登记成 `subagentFactory`（[AgentscopeChatEngine.java:3622-3624](../../src/main/java/com/wenqu/ai/agentx/AgentscopeChatEngine.java#L3622)），工厂造的是 `WenquConsultSubagent`（[WenquConsultSubagent.java:41](../../src/main/java/com/wenqu/ai/agentx/WenquConsultSubagent.java#L41)）——一个不含模型循环的壳。
- 结论：**没有运行时的成员注册表、没有 `list_agents`、没有 name/树路径**。父轮只知道"派了几支、叫什么"，不知道"哪个成员在线、在干什么"。

### 1.3 消息是单向的，没有成员 inbox

- 唯一的回传通道是 `BranchReport`：子轮产出 → `sink.answer()` → `BranchReport` → `SubAgentConsultService.render()` 变成给父轮的文本 + `subChat` 卡（[SubAgentConsultService.java:244-295](../../src/main/java/com/wenqu/ai/agent/subagent/SubAgentConsultService.java#L244)）。
- 框架自带的 steer/inbox 通道被问渠用 `NoopBusComponents` 顶成恒空（[NoopBusComponents.java:13-39](../../src/main/java/com/wenqu/ai/agentx/NoopBusComponents.java#L13)），但**会话内插话**仍走框架 `SessionInbox`（[FrameworkSessions.steer():1313-1341](../../src/main/java/com/wenqu/ai/agentx/FrameworkSessions.java#L1313)、[TurnSessionGateway.java:138-155](../../src/main/java/com/wenqu/ai/agentx/turn/TurnSessionGateway.java#L138)）。
- 父轮向子轮追加任务没有入口：`FrameworkSessions.steer()` 要求"进程内有这条会话的活实例（`held`）、且有正在跑的 run"，临时会话跑完后两者都不满足。
- 结论：**成员之间不能互发消息，任务变化无法推给正在工作的成员**。

### 1.4 但会话状态与恢复基础设施是现成的

- `FrameworkSessions.held` 是进程内活实例表，key = `uid|sessionId`（[:60](../../src/main/java/com/wenqu/ai/agentx/FrameworkSessions.java#L60)）；跨副本用 `RunBusCluster` 判定持有者（[:861](../../src/main/java/com/wenqu/ai/agentx/FrameworkSessions.java#L861)）。
- 会话状态存 Redis（`stateStore()`，[AgentscopeChatEngine.java:3497](../../src/main/java/com/wenqu/ai/agentx/AgentscopeChatEngine.java#L3497)），`SessionLog/SessionInbox/SessionTurns` 是框架持久化层，`TurnSessionGateway` 已经做了中断恢复与积压作废（[TurnSessionGateway.java:50-85](../../src/main/java/com/wenqu/ai/agentx/turn/TurnSessionGateway.java#L50)）。
- `FrameworkSessions.open()` 在 binding 变化时关旧实例、按新配置重建（[:313-404](../../src/main/java/com/wenqu/ai/agentx/FrameworkSessions.java#L313)），冷恢复的口子存在。
- 结论：**"子会话持久化 + 冷恢复"不需要新写存储层，只需要改会话种类语义与调度**。

### 1.5 前端已有子智能体卡，但没有"成员面板"

- `SubAgentChatCard.vue` 一问一答（[文件头注释](../../web/src/components/SubAgentChatCard.vue#L2)），`SubAgentRunFrames.vue` 可展开完整过程帧，`SessionEventsPanel.vue:116` 有聚合行。
- `web/src/chat/consult.js`、`streamSubagentFrames.js`、`toolCalls.js` 负责实时帧与落库同源。
- 结论：**子会话的时间线已经能渲染**，缺的是"成员列表 + 在线状态 + 向成员发消息"的入口。

## 2 改造总原则（踩过的坑不重踩）

1. **不启用框架 teamsMode**：DAG 方案 §1.2 四条理由仍成立（BETA1、`BaseStore` 沙盒持久化、`NoopBusComponents`、`createTask` 不暴露 `blockedBy`）。本方案用问渠原生领域层。
2. **复用框架 `SessionInbox` 而不是自建消息队列**：插话已经走 `SessionInbox`（内存 + SessionLog），成员消息复用 `AgentSession.steer()` + 一份"收件箱投影"即可，不必再写一套 Redis 队列。
3. **持久子会话走"新 kind"，不改 `temp` 语义**：工作流子智能体节点、评测临时会话仍然要"跑完即删"。新增 `kind=team`（或 `subagent`），只有团队模式下派出的人才用它。
4. **成员身份不另建表**：复用 `FrameworkSessions.held`（在线）+ `c_ai_session`（持久）+ `c_ai_session_event`（日志）。DAG 方案的任务表引用 sessionId 即可。
5. **权限边界不变**：成员运行在真实 uid 下，走同一套租户/RBAC/来源可见性；`guestMode`/`apiKey` 收窄继续继承（[SubAgentBranchRuntime.java:209-211](../../src/main/java/com/wenqu/ai/agent/subagent/SubAgentBranchRuntime.java#L209)）。
6. **默认关闭，会话级开关，不新增系统级配置键**：团队模式是会话级属性（对齐 DSH 根 Session 菜单），不是智能体固有属性，也不是平台全局开关。**不往 `ConfigService` / 系统设置页新增任何 `team.*` 或 `subagent.team.*` 全局键**；开关只落在会话行上（§3.1 的 `team_enabled`）。关闭时行为逐字不变——直接复用 DAG 方案 §8 的"关掉即全链路不挂工具"回滚策略。成员上限、超时、保留期一律随会话/工具出错文本收口，**不做平台可调项**。

## 3 领域模型：一棵树、三种会话、七个状态

### 3.1 会话种类扩展

```
c_ai_session.kind:
  chat   用户主会话（现有）
  temp   一次性子轮/工作流节点/评测（现有，跑完即删）
  team   团队子会话（新增：持久、可恢复、有在线状态；用户侧默认不进侧栏，按 root 归集）
```

迁移脚本编号：仓库当前最新为 `V34__document_content_sha256.sql`，DAG 方案已预留 `V35__agent_task_dag.sql`。**已定：本底座方案先落地**，故用 **`V35__agent_team_session.sql`**，DAG 方案的迁移顺延为 `V36__agent_task_dag.sql`。两者必须错号，不能都叫 V35。

- 改 `kind` 注释，加 `team`。
- `c_ai_session` 加 5 列（都 nullable，默认无团队语义；**团队开关也在会话行上，不是系统配置**）：
  - `team_enabled INT DEFAULT 0`：仅根会话有意义，`1`=本会话开启团队模式；关闭即整棵树停止挂 `team_*` 工具，成员会话恒为 0。
  - `root_session_id VARCHAR(50)`：所属团队根会话（父子传递，便于 `list_agents` 与冷恢复）
  - `parent_session_id VARCHAR(50)`：直接创建者会话（树边）
  - `member_name VARCHAR(64)`：模型可见名（`reviewer`、`reviewer/checker`），同父下唯一
  - `member_state VARCHAR(24)`：`IDLE/RUNNING/WAITING/STOPPED/OFFLINE`（在线快照，重启后可重建）
- 索引：`(tenant_id, root_session_id, deleted)`、`(tenant_id, parent_session_id)`。
- **不改**任何 `kind != 'temp'` 的查询——`team` 会被当成用户会话进侧栏，所以要在会话列表查询里加 `.ne(Session::getKind, KIND_TEAM)`（与现有 temp 排除同款，落点 `SessionService.java:407,596,746`、`MessageMapper.java:136`、`SessionEventMapper.java:32`、`ConversationSearchService`、`SessionEventSearchService`）。前端"成员面板"另开入口，不混进普通会话列表。

### 3.2 成员树（运行时，不落新表）

| 概念 | 载体 | 说明 |
|---|---|---|
| 根 | `toolSessionId`（用户会话） | 一棵树一个根；`rootOf()` 沿 `parent_session_id` 上溯 |
| 成员 | `c_ai_session(kind=team)` 一行 | 持久身份；`id` 就是投递地址 |
| 在线 | `FrameworkSessions.held` | `peek(uid, id) != null` 即在线 |
| 名字 | `member_name` + slash 路径 | 从根到该成员，全员命名时给全路径，否则回退 sessionId |
| 创建者 | `parent_session_id` | 权限校验：消息/中断要求发送者是目标祖先或根 |

根名固定 `lead`；成员名规则：1–32 小写字母/数字/连字符、以字母开头、同级唯一、不能叫 `lead`（对齐 DSH `SubagentActivationSpec.name`）。重名时报错，不静默覆盖。

### 3.3 成员消息（不新建队列）

复用 `FrameworkSessions.steer()` 的"运行中注入"语义 + 一条落库事件作为离线收件箱：

- 在线成员：`frameworkSessions.steer(uid, childSessionId, text)` → 框架 `SessionInbox`，下一次模型调用前生效（[FrameworkSessions.java:1300-1341](../../src/main/java/com/wenqu/ai/agentx/FrameworkSessions.java#L1300)）。收据号 = `inputId`。
- 离线成员：写 `c_ai_session_event(type="team_message", payload={from,to,text,msgId})`，并标记 `c_ai_task.next_run_at=NOW()`（若挂在任务上）；成员下次冷恢复时由 `TurnPromptAssembler` 注入未读消息。
- 冷恢复：`FrameworkSessions.open()` 已支持（binding 不同就重建）；新增一个 `openTeamMember()` 包装，按 `member_*` 列装配 `ChatCommand`（`agentId`=成员绑定的智能体、`modelRef` 继承根）。
- 完成通知：子轮 `done` 后沿用现有 `BranchReport` 回报给直接创建者；若创建者离线，写一条 `team_message` 事件给根，根下次上线读到。

### 3.4 与 DAG 方案的接缝

- DAG 方案的 `c_ai_task.owner_agent_id` 改为**双重语义**：存 `agentId`（原义）或 `memberSessionId`（新增，团队模式）；用 `owner_kind VARCHAR(16)` 区分 `agent`/`member`。
- `task_claim` 在团队模式下要求"调用者是活成员"，写 `owner_session_id` + 租约。
- `task_wait` 的唤醒：从"DB 轮询 + 跨轮续跑"升级为"任务状态变化 → 查 owner 成员是否在线 → 在线则 `send_message`，离线则写事件 + `next_run_at`"。DAG 方案 §3.3 的降级路径保留为兜底。

## 7 验收标准

1. 根会话开团队模式 → 派 `reviewer`/`writer` 两人 → 侧栏成员面板显示两名在线成员、名字与树路径正确。
2. `team_send(reviewer, ...)` 在 reviewer 正在跑时下一轮模型调用读到；reviewer 离线时消息落账，下次冷恢复注入。
3. 成员完成一轮后会话不删、状态 `IDLE`；再次 `team_send` 能唤醒新轮次，历史上下文连续（Redis stateStore 恢复）。
4. 任务板：A 建两任务并设依赖，B 认领后置任务；A 完成前置后 B 在跑的轮次收到唤醒（在线 `send_message` 路径）；离线走 `next_run_at` 续跑兜底。
5. 中断：祖先 `interrupt` 只停目标当前轮，排队消息保留；根结束 `drain` 整棵树。
6. 权限：普通用户看不到他人团队成员；租户隔离；guest/API Key 轮不挂 `team_*`。
7. 回归：团队关闭时，所有现有子智能体/temp 会话/工作流节点行为逐字不变（`NoopBusComponents` 不动、首包耗时不回退）。
8. 刷新/换设备/断线重连：成员树、任务图、成员时间线一致；老前端忽略新事件不报错。

## 8 风险与回滚

| 风险 | 缓解 |
|---|---|
| 新增 `kind=team` 混进用户会话列表 | 所有 `kind != temp` 查询同步加 `!= team`；写一条测试枚举所有查询点 |
| 持久子会话拉高 Redis/MySQL 占用 | 成员会话的清理沿用**现有会话保留/清理机制**（不新增系统级参数），上限随会话走：由根会话的成员注册数量收口，超出即拒绝新成员，写 `team_*` 工具出错文本；不做平台级可调项 |
| 消息在线/离线双路径重复投递 | 每条 `team_message` 带 `msgId`，`SessionInbox` 收据与账本事件用同一 id 去重 |
| 与 DAG 方案任务状态双轨 | `owner_kind` 区分 agent/member；状态词沿用 DAG 方案 §2.2 的唯一口径，不反向同步 |
| 冷恢复后成员 prompt 漂移 | binding 指纹（agentId/model/skillFilter）落 `c_ai_session`，`FrameworkSessions.open()` 按指纹重建，复用现有 `markConfigStale` 模式 |
| 框架 `steer` 只认活 run | 离线路径落事件 + `next_run_at`，不强行 `steer`；`steer` 返回 null 按"未接受"处理（现有语义） |

回滚：关闭会话级团队开关 → `team_*` 工具不挂、成员面板隐藏、分支回退 `temp` 语义；新列/新表保留不删，避免历史引用断裂。

## 9 拍板结果（2026-11-23，四项均按建议）

1. **开关粒度 = 会话级，且不新增系统级配置键**。团队是一轮协作的形态，不是智能体固有属性，也不做平台全局开关；不往系统设置页 / `ConfigService` 加任何 `team.*` 全局项。落点：会话设置/顶栏团队胶囊切换，团队状态写进会话行（§3.1 的 `team_enabled` 与 `member_*` 列）。成员上限、超时、保留期一律随会话收口或沿用现有会话清理机制，不做平台可调参数。
2. **成员会话不进侧栏，统一用「团队」面板查看**。不为"固定成员"另设置顶入口——避免和会话列表的置顶语义混在一起。落点：所有会话列表查询加 `.ne(kind, KIND_TEAM)`（§3.1），成员面板是唯一入口。
3. **命名与地址两者都支持**：模型侧优先 slash 全路径 `reviewer/checker`，短名和 sessionId 也都接受，`resolveName` 三者兼容。落点：`AgentTeamService.resolveName`（§4.2），`team_send(agent=...)` 的 `agent` 参数。
4. **父上下文继承开启，但只对直接子代**：`parentBrief` 随首轮注入（fork 语义），孙代由各层自己摘要，不把根的完整历史逐层复制，控制 token 成本。落点：接通 §4.4 的 `parentBrief` 读取，写入侧按 `subagentDepth==1` 才带父摘要。
