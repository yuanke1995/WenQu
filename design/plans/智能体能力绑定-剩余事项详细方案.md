## 2. P0-A 技能名空间与引用身份收敛

### 2.1 问题与证据

- 个人技能物理 key 是 `{uid}/{name}`，但 [AgentscopeChatEngine.java:2297-2306](../../src/main/java/com/wenqu/ai/agentx/AgentscopeChatEngine.java#L2297-L2306) 和 [TurnPromptAssembler.java:122-128](../../src/main/java/com/wenqu/ai/agentx/turn/TurnPromptAssembler.java#L122-L128) 都剥成裸名。
- [WenquSkillRepository.java:140-159](../../src/main/java/com/wenqu/ai/skill/WenquSkillRepository.java#L140-L159) 按裸名合并，用户版覆盖内置版——跨人同名无法精确表达「用谁的那个技能」。
- 技能缓存 15s TTL；编辑/停用后存在短窗口。

### 2.2 目标与非目标

- 目标：技能引用具备稳定身份；智能体配置、用户点名、工作流技能节点三处同口径。
- 非目标：不改技能正文渐进披露、不改现有内置/我的/工作区三层来源语义。

### 2.3 方案

1. **定义技能引用语法**：`builtin:<name>` / `user:<uid>:<name>` / `workspace:<sessionId>:<name>`；保留裸名作为兼容读法（优先按当前 uid + 内置解析）。
2. **单一解析器**：新增 `SkillRefResolver`，统一负责 `parse(normalize(resolve(ref, uid)))`；返回稳定 `SkillKey`。
3. **替换三处裸名调用点**：`skillFilterOf`、`TurnPromptAssembler`、工作流技能节点的服务层（保留 YAML 向后兼容）。
4. **UI 选择器**：`AgentsPage.vue` 的 `skillOptions` 从「只有 name」改为 `{value: fullRef, label: 'name · 来源/归属'}`，保存写 fullRef；老数据加载时转 fullRef 展示。
5. **缓存失效**：技能保存/安装/停用/删除时按 `{uid}/{name}` 主动失效 `WenquSkillRepository` 的 15s 缓存，不再只等 TTL。

### 2.4 验收

- 两个用户各有同名 `review` 技能，智能体 A 指定 `user:u1:review`，执行时调用 u1 的正文。
- 工作流技能节点按 fullRef 解析，与智能体技能过滤器同结果。
- 老智能体只存裸名 `review` 时行为不变（当前 uid 优先）。
- 技能正文修改后立即生效，不等 15s。

## 3. P0-B `resolveForTurn` + 会话钉住配置 revision

### 3.1 问题与证据

- `resolveForTurn(agentId, override)` 只在设计里出现：[智能体评测立项方案.md:243-250](智能体评测立项方案.md#L243-L250)；历史版本重测只能回滚再回滚。
- 常驻实例的 key 只含 `agentId@updateTime` 与若干全局/个人开关（[AgentscopeChatEngine.java:2240-2273](../../src/main/java/com/wenqu/ai/agentx/AgentscopeChatEngine.java#L2240-L2273)）；KNOWLEDGE_REWRITE_ENABLED 等有「context 构造与开关耦合」类的历史问题（[问句分解按轮判定详细方案.md](问句分解按轮判定详细方案.md)）。
- 用户希望「本轮临时换知识库/工具集/人设」与「评测历史版本」应当是同一套机制，不是两个 hack。

### 3.2 目标与非目标

- 目标：调用方可传 per-turn override，仅作用于本轮；同一 override 能复现历史版本。
- 非目标：不把 override 写进 sysPrompt；不新增平台级开关；不把 `ChatCommand` 变成万能配置袋。

### 3.3 数据模型

新增不可变 `AgentTurnOverride`：

```text
agentId                // 显式目标智能体；空=默认
revision               // 版本快照号或时间戳；null=当前
personaPatch?          { systemPrompt? }
knowledgePatch?        { kbIds?, tags?, filter?, disabled? }
toolPatch?             { family: tri?, mcps?, skills?, httpToolIds?, workflowToolIds?, deny? }
permissionPatch?       { preset?, approval?, maxToolSteps? }
memoryPatch?           { mode? }
```

边界：只接受白名单字段，服务端按类型与上限校验；revision 与具体 patch 同时出现时以 patch 为准并记审计来源。

### 3.4 执行链

1. `ChatCommand` 增 `override` 字段（不可变对象）。
2. `ChatService.resolveTurnModel` 与装配期读取 `AgentService.findVersionSnapshot(revision)` 或当前行，再叠加 patch，产出 `ResolvedAgent`（普通 `Agent` 视图 + override 摘要）。
3. `AgentscopeChatEngine.bindingOf`：指纹追加 `override.fingerprint()`；`buildAgent` 使用 `ResolvedAgent`，但每轮数据仍走 `AgentxTurnSlot`。
4. 调用变量继续走用户消息侧，保持前缀缓存。
5. 评测服务使用 override 跑历史版本，不再回滚线上配置；结果账本记 `overrideFingerprint`。

### 3.5 风险与回落

- 风险：改一个大而全的 override 对象会导致每个 provider 都要认识它。回落：先只做 `revision`（历史版本重测）+ `knowledgePatch`（临时换库）两个字段，其余留后续。
- 风险：revision 对应的智能体已被删除。回落：fail-loud 在入口 400，不静默用当前配置。

### 3.6 验收

- 评测重跑 v1 配置：不改线上智能体、不回滚，检索范围/工具面/人设与 v1 一致。
- 本轮指定 kbIds 与工具集，下一轮自动恢复。
- 两次不同 override 之间切换会话时实例按指纹重建，不串配置。
- 无 override 的所有旧路径逐字节不变（日志指纹对比）。

## 4. P1-A 工具执行策略单一管线化

### 4.1 问题

- 装配侧判据已在 `ToolMountContext`：三态、权限档位、黑名单、游客可见性、分支轮（[ToolMountContext.java:88-188](../../src/main/java/com/wenqu/ai/agent/tool/ToolMountContext.java#L88-L188)）。
- 执行侧仍有 `AgentxFrameworkToolGate`、`SpringAiToolAdapter`、原生工具守卫、脚本 `run_code` 子调用清单等分散判据；DSH 的原则是「越强机制越要保留别人贡献」，门禁应是一条有顺序的管线。

### 4.2 方案

1. **冻结语义**：
   - `restrict`：从模型工具表移除（schema、查找、执行三处同时消失）。
   - `guard`：同步、单调拒绝，不能被后续 listener 翻案。
   - `pre-execute`：可返回 allow/deny/ask；需要人时返回 ask，不挂 120s 超时。
   - `post-execute`：只变换/附加上下文，不改变是否执行。
   - `result`：只读观察最终冻结结果，用于审计/工具卡。
2. **统一入口**：新增 `ToolPolicyPipeline`，由 `ToolMountContext` 产出的判据作为 `restrict/guard` 输入；`SpringAiToolAdapter`、框架原生工具、`run_code` 子调用都通过同一管线，不再各写一份 if。
3. **删除重复判据**：逐项把分散 if 搬到管线，先在测试中断言「工具表里没有」而不是「执行时拒绝」；保留底层兜底但由管线调用。

### 4.3 验收

- 一个工具因权限档位被拦时，首轮模型工具表无该 schema（不是调用后报错）。
- 黑名单对动态 MCP 工具按名剔除在装配与执行两处同源。
- 分支轮 + ask 档不挂需审批工具；游客轮无审批通道。
- 工具结果审计事件只由 `result`  observer 产出，无重复记账。

## 5. P1-B 分享安全 P3/P4 收口

### 5.1 现状依据

[设计文档 P0必补收敛方案.md:100-125](P0必补收敛方案.md#L100-L125) 已给出事实：游客消耗发布者配额、无分享级上限、`visitorId` 可重置；注入面已有基础但需要全链清点。

### 5.2 P3 费用面

1. `c_ai_agent_share` 增 `daily_turn_limit` / `daily_token_limit`（可空=跟随平台默认，不允许无上限）。
2. Redis 计数：`share:budget:{shareId}:day:{yyyyMMdd}:{visitorId}` + IP 键；超限 429，文案区分分享预算与发布者配额。

4. 台账按发布者租户落戳（当前未绑线程落 default 的问题一并修正）。

### 5.3 P4 注入面

1. 产出「通道 × 防护 × 证据」表：KB 块、网页搜索、MCP 工具输出、HTTP 工具输出、工作流工具输出、附件 OCR、图片描述、调用变量、宿主数据字典。

## 8. P2-B scope/realm 与权限树

- 显式区分：`scope`=能力贡献与事件可见性；`realm`=服务实例。团队/子智能体注册能力时同时声明两者。
- `WenquTeamGateway` 的 `capPolicy` 继续取更严，但在成员启动时固化权限快照，不允许成员中途放大。
- 增加 realm 审计：发现 provider 与 consumer 不同 realm 时启动 WARN/测试失败。
- 与多副本清单联动：单实例假设（见 [智能体团队-现状与未完项.md:118-153](智能体团队-现状与未完项.md#L118-L153)）未解决前不开放横向扩容。

## 9. P2-C 会话状态改 projection

- 选 `todo/goal/team task` 三个状态先做 proof：定义 `key/stateSchema/stateVersion/init/apply`，`apply` 纯同步；UI 读 checkpoint + tail replay。
- `stateVersion` 变更丢弃旧 checkpoint；未知事件忽略时返回同一个 state 引用。
- 不新造事件 `type`；团队事件继续用现有 `team_member/team_message/team_task`，内部数据落在 projection state。
- 验收：fork/resume 后状态可重建；旧 checkpoint 不污染新语义。

## 11. 实施纪律与回归基线

1. 每批独立提交；提交说明列「改了哪类绑定、哪类轮次零变化」。
2. 每批执行：`mvn test` 全量 + 一轮手工问答（登录/游客/API Key 各一轮）+ 工具表/指纹日志对比。
3. 新增字段必须同步：`Agent.java`、版本快照白名单、`AgentService` 保存/回滚、前端回显/保存、市场模板导出导入裁剪。
4. 禁止：把新增配置直接塞 sysPrompt；把市场安装裁剪当权限边界；给低风险能力增加一排平台开关；用 `system-prompt/assemble` 手改工具列表。
5. 本文剩余事项的账本每季度回写一次，状态只写「已验收」或「未开始/进行中」，不写「代码完成但未验收」。
