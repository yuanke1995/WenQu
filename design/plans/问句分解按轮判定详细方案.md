# 问句分解 · 按轮判定详细方案

> 立项：2026-11-21｜替代 `知识库增强-第一档详细实施计划.md` §8 第 2 条「降级为只补诊断」的结论
> 目标：只对**模型没拆、但问题确实是复合问句**的轮次做工具内多路召回；模型已自行逐问检索的轮次零行为变化。
> 范围：只在 `search_knowledge` 工具回调层；不改 `HybridRetrievalService.search/searchMulti`、不改引擎 prompt、不改工具清单/plan/trace、不改工具返回形状。

---

## 1. 为什么不是"全做"也不是"只识别"

- 前置日志只能证明模型**会**在一轮里发多次 `search_knowledge`，不能证明它**每轮都发**。全局关掉分解，等于把模型没拆的那些轮次也放弃了。
- 全局开启又会在模型已拆的轮次上按"用户原问题"再拆一次，造成双重检索。
- 因此判据必须是**按轮 + 按本次调用**的，而不是按历史日志比例做全局开关。

---

## 2. 触发判据（全部满足才拆）

| # | 判据 | 取值来源 | 不满足时的 `splitSkipReason` |
|---|---|---|---|
| 1 | 有本轮上下文 | `turnQuery != null` | `no-context` |
| 2 | 本轮第 1 次检索调用 | `registrar.markRetrievalCall() == 1` | `call-not-first` |
| 3 | query 就是用户原问题 | `query.trim().equals(turnQuery.question().trim())` | `model-already-split` |
| 4 | 确定性切分出 ≥2 个子问题 | `QuerySplitter.analyze(question)` | `not-multi` |
| 5 | 子问题数 ≤4 | `subQueries.size() <= 4` | `too-many` |
| 6 | 追问改写未生效 | `rewrite == null || !rewrite.applied()` | `rewrite-applied` |

子问题清洗规则：去空、去重、长度 ≥2；切分来自连接词或 ≥2 个问号；单问严格短路。

---

## 3. 数据与控制流

```
用户原问题 ──> TurnQueryContext（WenquAgentxTools:1092-1097 构造，改写开关仍默认关）
                    │
search_knowledge 入口（KnowledgeRetrievalTool:182-202）
                    ├─ registrar.markRetrievalCall() → 本轮第几次
                    ├─ query == question ?
                    ├─ QuerySplitter.analyze(question) → subQueries / multiQuestion
                    ├─ 六道判据全过？
                    │    ├─ 是 → searchMulti(subQueries, diag, kbIds, true, filter)
                    │    │        └─ 并行召回 / 去重合分 / 多路共识加分 / 超时降级首路
                    │    └─ 否 → search(originalQuery, diag, kbIds, true, filter)
                    └─ 原问题始终作为重排 query（rankQuery = originalQuery），不丢原意
```

- `searchMulti` 的 ≤2 路补采、≥3 路自动关补采、共识加分与去重均沿用现状，不改 `HybridRetrievalService`。
- 引用编号仍由 `SourceRegistrar` / `TurnSourceRegistry` 在合并后统一分配，形状不变。
- 非知识库轮（闲聊、写作、编码、联网搜索）不调 `search_knowledge`，整条链路零触发。

## 4. 改动清单

### 4.1 轮级调用计数（并发安全）

| 文件 | 改动 |
|---|---|
| `KnowledgeRetrievalTool.SourceRegistrar` | 新增 `default int markRetrievalCall() { return 1; }`；无注册器（MCP/直接调用）默认 1，但 `turnQuery == null` 仍短路 |
| `WenquSourcePool` | 增 `AtomicInteger retrievalCalls`；`registrar()` 匿名实现覆写 `markRetrievalCall()` 返回 `incrementAndGet()`；按轮新建，天然归零 |
| `KnowledgeRetrievalTool` | 入口处取 `callIndex`；判据 2 用它 |

并发说明：模型一轮并行发多次调用时，`incrementAndGet` 保证只有一次拿到 1；拿到 1 的那次如果 query 不是原问题（模型已拆）也会在判据 3 短路。双保险。

### 4.2 切分器增强（零 LLM 成本）

`src/main/java/com/wenqu/ai/service/QuerySplitter.java`：

- `analyze()` 用连接词集合一次性切分（`，,、和、与、及、；;`），不再只取第一个命中的连接词；结果按原文顺序去重。
- 问号切分规则不变：≥2 个 `?/？` 才拆。
- 每段 trim 后长度 ≥2 才保留；不足则退回单问。
- `split()`（评测口径：原词 + 前两个关键词词元组合）保持现有行为，不改评测基线。

### 4.3 主链路

`src/main/java/com/wenqu/ai/service/KnowledgeRetrievalTool.java`：

- 在改写分支之后、检索选择之前插入分解判定。
- 判据全过：`hits = searchMulti(subQueries, diag, kbIds, true, filter)`，`splitApplied=true`。
- 否则：原 `search(originalQuery, ...)`，并写 `splitSkipReason`。
- 日志：`[RAG-SPLIT] applied=true|false original="…" subQueries=[…] routes=N skip=… supplement=… hits=N elapsed=Nms`。
- 不改工具返回文本、不改引用注册顺序、不改 `KB_SCOPE` / 过滤条件透传。

### 4.4 诊断与前端可见

| 文件 | 改动 |
|---|---|
| `HybridRetrievalService.RetrievalDiag` | 增 `subQueries`、`splitApplied`、`splitSkipReason`、`splitRoutes`、`splitElapsedMs`；`reset()` 同步清空；补 getter |
| `RetrievalDebugController` | 把上述字段映射进 `retrievalDiag`；`subQueries` 在调试入口也用 `analyze()` 取生产同口径 |
| `ChatPage.vue` 调试弹窗 | "多问识别"行显示：已拆/仅识别 + 原因 + 子问题标签；不再写死"仅诊断" |
| `MobileRoundSheet.vue` | H5 调试面板同步显示同一诊断段 |

### 4.5 回滚与安全

- 代码常量 `KNOWLEDGE_DECOMPOSE_ENABLED = true` 仅作应急回滚位，不进设置页、不做平台总闸。
- 真回滚优先 `git revert` 该提交；改常量只用于线上立即止血。
- 判据 6 保证追问改写若未来开启，不会出现"改写两路 + 分解多路"三重叠加。

## 5. 验收口径

### 5.1 单元 / 契约测试

- `QuerySplitterTest`：多连接词一次切分、问号切分、单问短路、短段丢弃、去重、评测 `split()` 口径不变。
- `KnowledgeRetrievalToolDecomposeTest`：
  - 第 1 次调用 + 原问题 + 多问 → `searchMulti(subQueries)`，不调 `search`。
  - 第 2 次调用 / query 是子问题 / 单问 / 改写生效 / >4 子问题 → 一律 `search`，不调 `searchMulti`。
  - `registrar==null` 的 MCP 入口 → 从不分解。
  - `diag.reset()` 后所有 split 字段清空。
- 工作流节点、`/v1/retrieval`、`KbInsightsService`、`RetrievalEvaluationService` 的 `search/searchMulti` 调用结果回归一致（这些入口不经工具回调）。

### 5.2 真机 A/B（yuanke 账号 + 线上库/Redis 快照）

双实例对照：旧类 8097 / 新类 8096，两份独立 DB 拷贝，同一 `yuanke` 账号。

| 组 | 用例 | 通过标准 |
|---|---|---|
| 复合问句 | `1. 登录和4. 提问怎么操作`、`SSE 事件…和多副本部署要求…`、`知识库与文档和智能体有什么区别` | 召回条数 ≥ 旧类；新增覆盖项且无丢失；耗时变化有量化记录 |
| 3 问场景 | 构造 3 子问题 | 记录 `searchMulti` 关补采后的命中数/耗时，不静默接受退化 |
| 单问回归 | 2 条单问 | 工具输出 hash 与旧类完全一致；`splitApplied=false`、`subQueries` 只有 1 项 |
| 非知识库轮 | 闲聊/写作/联网各 1 | 日志无 `[RAG-SPLIT]`、diag 无 split 字段 |
| 模型已拆轮 | 人工构造先发子问题的调用序列 | 第二次调用不触发分解，无重复检索 |
| 调试面板 | 同一复合问句 | `retrievalDiag` 显示 `subQueries`、已拆/原因；前端标签正确 |

### 5.3 出口标准

- 复合问句召回提升有数字；单问与非知识库轮零变化有证据。
- 483+ 单测全绿、`mvn compile`、`npx vite build` 通过。
- 文档回写：README §知识库与检索增强、manual/05、manual/06；详细计划 §8 改为本方案结论。

## 6. 风险与处置

| 风险 | 处置 |
|---|---|
| 模型并行发多次调用，计数竞争 | 原子计数 + query==原问题双门；只有一次拿到 1 且 query 不对也不拆 |
| 连接词误切（如"和"在专有名词里） | 每段 ≥2 字、去停用词、连接词一次性切分；单问短路优先 |
| 3 路以上补采关闭导致召回退化 | 上限 4 路；3 路场景单独量化；超 4 路直接跳过分解 |
| 多路耗时 | 沿用 8s 超时 + 失败降级首路；日志记 elapsed |
| 引用错位 | 合并后再注册引用，编号仍由注册器统一分配 |
| 与追问改写叠加 | 判据 6 互斥 |
