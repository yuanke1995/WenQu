# 本地工作区「只能一轮会话修改」· 诊断与改造方案

> 现场现象已确认为 **A**（工作区级互斥把第二条会话挡在门外）。本方案已按 A 落地：**代码已改、未提交、未部署**；按既定口径不降级、不加兜底开关、不做历史兼容与多档模式。

## 0. 先把「一轮」说清

代码里**没有**「一个工作区只能改一轮」或「一个工作区只能挂一条会话」的设计：`c_ai_session.project_id` 是普通索引（非唯一），`Session.java` 注释明确「会话与工作区是多对一」。用户看到的现象，实际有三条不同的链路，都**只在 `isLocal` 的本地工作区发生**，与「本地工作区」这个限定吻合：

| | 现场表现 | 对应机制 |
|---|---|---|
| A（**现场确认**） | 同一工作区开第二条会话 / 定时任务，发送即被拒：「这个工作区里…正在跑，等它结束或先停掉它再发送」 | 工作区级轮次互斥（`ProjectTurnGuard`）——**设计如此** |
| B | 第二条会话能发消息，但 `write_file` 反复报 `E_CONFLICT`「用户在你上一次回答之后改过 X，请先读取最新内容」 | 「用户改动对账」把**另一个助手轮次**的改动误判成用户改动 |
| C | 同一条会话第一轮已结束，第二轮仍被拒（约 2 小时内） | 租约释放路径不全，残留到 TTL 到期 |

三者可以叠加：A 挡住并发，C 让挡的时间从「一轮」变成「两小时」，B 让「绕开 A 之后依然改不动」。所以「只能一轮会话修改」不是单点 bug，是**一条粗粒度互斥 + 一套建立在「同一时刻只有一轮」假设上的快照/对账体系**。

**现场证据（20:13 聊天页截图）**：在同一工作区里发「把核心能力多写一些」，收到红色错误卡「这个工作区里会话「写一个问渠官网出来呢」的一轮对话正在跑，等它结束或先停掉它再发送」。这句正是 `TurnLease.describe()` 默认分支「会话「名」的一轮对话」逐字拼出来的，只可能来自 `ChatService:487-494` 的工作区级互斥 —— **A 支坐实**。B / C 不是本次现场现象，但删掉锁之后 B 会立刻暴露（另一条会话的改动被当「用户改过」而拒绝写入），所以一并改造。
**代码证据**：链路确凿（下文逐条给文件与行号）。本机 `logs/wenqu.log` 无对应问答记录、本地库 `c_ai_project_root` 为 0 行（真实工作区数据在线上库，不在本机），线上日志未取；现场判据以截图报错原文为准。

## 1. 代码事实（编号诊断）

**D1 · 工作区级整轮互斥，只对本地工作区启用**
`ChatService.java:472-495`：`projectService.isLocal(turnProject)` 为真时按 **projectId** 取 `TurnLease`，抢不到就 `rejectTurn`；锁按工作区不按会话，因此挡的是「同一工作区的第二条会话 / 定时任务 / 工作流」。接口注释 `ProjectTurnGuard.java:4-9` 原文：「同一共用目录的工作区同时只允许一轮在跑」「快速失败不排队」。`JvmProjectTurnGuard.java:37` TTL 2 小时。
释放只有两处：`ChatService.java:632`（流水线 `finally`）与 `:645`（`RejectedExecutionException`）。而取锁之后、`try` 之前还有 `TurnRegistry.registerHandle`、`chatRunBus.open`、起表帧、`TurnDeadline`、三个 emitter 回调注册、`syncPipelineSize()`——**任一处抛非 `RejectedExecutionException` 的异常，租约与会话互斥都不释放**；`ChatService.java:644` 的注释自己写过这个后果：「那个工作区从此再也发不出消息」。这就是 C。

**D2 · 执行器侧写本来就严格串行**
`scripts/local-agent/wenqu-agent.mjs:2300-2306`：读操作并行（`READ_CONCURRENCY=4`），**写操作走 `writeChain` 单链串行**，注释写明「同一轮 turnStart/write/turnEnd 的顺序和快照一致性不能赌」。已有 `expectedHash`（`opWrite` / `opEdit`）、`writeAtomic`、`assertNoUserDrift`。
→ 服务端把「整轮」串行化是**重复保护，不是唯一屏障**。这是本方案敢把工作区锁整个退役的硬依据，也是并发正确性的地基，实施时**不许为吞吐放开写队列**。

**D3 · 改动对账的基线是「同一条会话的上一轮」（B 的根因）**
`ProjectTurnChangesService.start():137-145` → `lastTurnIdBefore(sessionId, turnId)`（`MessageMapper.selectLastTurnIdBefore`）→ 执行器 `detectDrift(state, previousTurnId)`（`wenqu-agent.mjs:1612+`）：比较「上一轮 `afterTree`」与「本轮开场 `tree`」，命中的绝对路径写进 `state.drift`；`opWrite` 前 `assertNoUserDrift` 抛 `E_CONFLICT`，直到模型先 `read`（`clearDriftAfterRead`）才解禁。
两条会话共用一个目录时，会话 A 的「上一轮 afterTree」之后，会话 B 的改动会落进 A 本轮开场 tree 的差值 → **被判成「用户改过」**。模型若不先读就整文件写，会一直撞 `E_CONFLICT`。这是「第二个会话 / 后续轮次改不动」的真实机制，与工作区锁无关。

**D4 · 改动卡自身的归因已经按「谁动的」算**
`opTurnEnd():1790-1805` 用 `isTouched` 过滤 git diff；命令改动用 `execWindows` 时间窗归因（`3e199f1d` 已落地）。因为写队列串行，不同轮的命令窗口不重叠，**并发下两张卡不会互相串文件**。这一层保留，不改。

**D5 · 互斥的附属物**
`TurnLease.KIND_*` 被 `WorkflowEngine`、`ScheduledJobService`、`AgentEvalRunner`、`AgentWebhookService`、`TurnNotifyService` 当作轮来源常量；`ScheduledJobService.awaitWorkspaceFree():366-385` 按占用态退避 30s/2min 再 skipped；`ConfigDefaults.java:225` 有 TTL 常量；`schema.sql:1569` 的**退役键清理名单已经包含** `project.turnGuard.leaseTtlMs`（这条是数据迁移，保留）；`README.md:666` 仍写着「轮次租约用于有轮次在跑时禁止改名移动删除」；`ProjectTurnGuard.isBusy()` 全仓**已无调用点**（死方法），改名/移动/删除不受影响。
前端没有工作区占用态 UI（相关端点在早期收敛时已退役），因此本次前端只需改文案与手册。

**D6 · 不动的部分（正当保护）**
`runtime.tryBeginTurn(sessionId)` 会话级互斥、权限档位（`permission_preset` / `AgentxPermissions`）、归档只读、设备绑定 `foreignWorkspace`、`expectedHash` / 写前冲突检测、快照「内容不出用户电脑」与 git 私有 index 只读约束——都不是过渡层，全部保留。

## 2. 目标与边界

**目标**：同一本地工作区允许多条会话、多轮连续与并发修改；同一条会话仍一次只跑一轮；用户自己的改动不被静默覆盖；改动卡与冲突提示如实反映来源。

**不做**：不提供「串行/并行」开关或多档模式；不做工作树副本 / git worktree 隔离（文件必须留在用户选的真实目录里，这是工作区定义）；不做撤销；不改权限模型与设备绑定；不为历史数据留兼容读路径。

## 3. 推荐方案（一刀切，不做兼容）

### 3.1 服务端：退役工作区级互斥

- `ChatService.java`：删 `:472-495` 取锁与拒绝分支、`:632` / `:645` 释放、`:656` 与 `:661` 里「同工作区并发被拒」的注释口径；**保留** `:462-467` 的会话级 `runtime.tryBeginTurn`。删后 A、C 同时消失（没有锁，就没有残留锁）。
- 删除 `ProjectTurnGuard.java`、`JvmProjectTurnGuard.java`、`RedisProjectTurnGuard.java`、`TurnLease.java`。`RedisProjectTurnGuard` 只是未启用的骨架，其「多副本需共享工作目录」的前提在真实本机目录模型下也不成立。
- 轮来源常量迁移到新建的 `service/TurnSource.java`（`USER/SCHEDULED/WORKFLOW/EVAL`），六处引用一次性改完：`WorkflowEngine`、`ScheduledJobService`、`AgentEvalRunner`、`AgentWebhookService`、`TurnNotifyService`、`ChatCommand` 注释。这是**迁移，不是兼容层**。
- `ScheduledJobService`：删 `awaitWorkspaceFree()` 与 `:398` 调用，定时轮不再因「工作区被占」顺延 / skipped。
- `ConfigDefaults.java:225` 删常量；`schema.sql:1569` 的退役键清理行**保留**（每次启动幂等清掉旧配置行）；`README.md:666` 删除该项与说明列里的租约描述。
- `manual/04-工作区.md`：补「同一工作区可以多条会话同时改文件；同一条会话仍一次只跑一轮；改动卡各算各的；文件被别人改过会要求先读再写」。

### 3.2 执行器：把「谁改的」判据从会话级改成工作区级

这是方案的核心，D3 不解决，删了锁依然「改不动」。

- 执行器维护按**规范化 roots 集合**分组的 `workspaceLastTurn`（随 turnState 一起落盘）：`turnEnd` 收口时记下该轮 `done / afterTree / touched`。
- `opTurnStart` 不再依赖服务端传来的 `previousTurnId` 找基线，取同 roots 组**最近一条已收口**的轮状态。`detectDrift` 比较出的差异文件按来源分流：
  - 能归因到某个已收口助手轮的 `touched` → **不算用户改动**，不写 `state.drift`；
  - 无法归因到任何助手轮（人、IDE、外部程序）→ 才是用户改动，保留现有「先读再写」禁令。
  - 判据与 `3e199f1d` 的「只算助手自己改的」同源，只是把它从改动卡推广到对账。
- 服务端 `ProjectTurnChangesService.start()` 去掉 `lastTurnIdBefore` 与 previousTurnId 下发；`MessageMapper.selectLastTurnIdBefore` 及对应 SQL 退役；`ExecutorFiles.turnStart` 签名与 `ExecutorFilesystem.previousTurnIdSupplier` 一并退役。
- **保留**：`assertNoUserDrift`、`clearDriftAfterRead`、`expectedHash`、`writeAtomic`、写队列串行、`touched` / `execWindows` 归因、快照 TTL 与隐私红线。并发下同一文件的写冲突仍由既有 `E_CONFLICT` 报出，不新增兜底分支。

### 3.3 冲突与可观测性

- 两条会话写同一文件：`edit` 由 `expectedHash` 拒绝覆盖、`write_file` 由 drift / expectedHash 拒绝、shell 写由串行队列排队；错误文案沿用现有 `ExecutorFiles.java:65` 映射，不改语义。
- 改动卡：两条会话各列自己 `touched` 的文件（D4 已成立），补回归用例证明不串。
- 「这个工作区里 X 正在跑」「顺延重试 2 次仍占用」两类文案随互斥退役消失；手册 FAQ 同步删掉对应条目（若现场见到的是 C，这条正是用户当时读到的报错）。

### 3.4 不建议的路径及原因

1. **只修 TTL / 补释放钩子**：仍然按工作区挡第二条会话，诉求没解决；且 try 之外的异常出口无法穷举，属于补丁式兜底，与既定口径冲突。
2. **加「允许并发」配置开关**：两套快照与对账语义要长期并存，是明确否决过的多档模式。
3. **工作树副本 / git worktree 隔离**：改动不再落到用户选的文件夹，违背「文件只在你自己的电脑上、就在你选的那些目录里」，且要引入合并与冲突回滚，成本与风险都远超收益。
