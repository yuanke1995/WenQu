> 状态：**只出方案，不含代码改动**。上游是 `design/mockups/integration-upgrade/对外集成执行方案.html`

> B 期已完成的端点见 `design/plans/对外集成能力补齐计划.md`，本文件不重复。

## 0. 结论先行

| 项 | 结论 |
|---|---|
| **本轮交付** | 本方案；引擎代码、v1 控制器、SDK 都**不写** |
| **核心主张** | **只做投影**：在现有事件出口单点挂一个 v1 订阅者，把 `turnId→runId`、native 事件名→v1 点分名、payload→typed schema、`seq→id:` 一并收口；`ChatService.chat()` / `RunChannel` / `AgentscopeChatEngine` / 前端 `api.js` 一行不改 |
| **最大缺口** | 现有 SSE 帧**从不写 `id:`**，全仓库无 `Last-Event-ID`；事件本体只在进程内存 `ChatRunBus`，无持久回放；**没有 runId，只有 turnId**；审批决策靠进程内 `CompletableFuture` |
| **数据变更** | 新增 1 张 run 映射表 + 1 处 Redis 短 TTL 事件回放缓冲；**不改现有任何表的归属键**（`c_ai_tool_approval.sessionId` 已被工作流 run 借用，动它会串线） |
| **契约** | 8 端点 + 8 事件 + 稳定错误码；新增 `runs.read` / `runs.write` 两个 scope，进 `openapi.json` 与 `contract/openapi.v1.json`（走 `--update`） |
| **验收** | 8096 验证栈实测：token → approval.required → 提交审批 → artifact.created → run.done；插话/停止终态一致；断线 5 分钟 `Last-Event-ID` 续传 seq 连续；webhook 验签通过且同 run 重投不产生第二条业务记录 |
| **不做** | 不改引擎执行语义、不做 UI 全量镜像、不默认对外 `thinking`、不引入分布式调度改造、不动 B1 发包 |

## 1. 现状真源

### 1.1 链路与事件写出

- 主链路：`POST /api/ai/chat`（`controller/ChatController.java:169`）→ `ChatService.chat()`（`:308`）
  → `SseRunEventChannel` → `ChatRunRuntime.sendSseEvent()` → `ChatRunBus` 扇出。
- 写帧有两条路径，**必须都覆盖**：
  - 总线路径（带 `seq`）：`service/ChatRunBus.java:427`，帧由 `frame():719-728` 组装；
  - 直写路径（无 `seq`）：`agent/chat/ChatRunRuntime.java:713-719`，`snapshot` 首帧 `:890-904`，
    产物独立下发 `service/ArtifactService.java:933-949`。
- `SseEmitter` 不设容器超时（`:281`），非 HTTP 场景用 `CollectingSseEmitter`（定时任务即此形态）。

### 1.2 事件枚举

唯一真源 `engine/RunEventType.java:21-124`，**32 个事件名**；前端 `web/src/chat/eventContract.generated.js`
与 SDK `sdk/js/src/types.ts` 由它派生。分两类：

- **可稳定对外候选**（有业务语义、SDK 已建类型/回调）：`token` / `thinking` / `tool_status` / `plan` /
  `deep_plan_approval` / `approval_required` / `ask_user` / `artifact` / `usage` / `retrieved` /
  `warn` / `done` / `error` / `turn_start`。
- **UI 内部细节**（不进 v1）：`process` / `todo` / `deep_state` / `deep_turn` / `compact_state` /
  `runcode_progress` / `subagent_step` / `agent_delegated` / `agent_consulted` / `skill_hit` /
  `steer` / `tool_output` / `image` / `deep_plan_delta` / `snapshot` / `bus_closed`，以及传输层 `seq`/`pos`。

`done` 的唯一构造点 `agentx/turn/TurnDonePayload.java:59-99`；`error` 目前是**纯文本**，
没有稳定 `code`（`ChatRunRuntime.java:714-718`），而 HTTP/v1 层已有稳定错误码
（`config/GlobalExceptionHandler.java:120-147`）——这是要补齐的语义落差。

### 1.3 seq / 续传 / 保留期（最关键的缺口）

- `seq` 存在且单调：`ChatRunBus.java:111-112` 的 `Run.seq`，由 `bump():398-410` 在锁内 `++` 分配；
  订阅者 `Sub.fromSeq = run.seq`（`:451`），`fan()` 按 `if (sub.fromSeq >= seq) continue` 去增量（`:421`）。
- **但**：SSE 帧一律 `SseEmitter.event().name(...).data(...)`，**从不调用 `.id(...)`**；
  全仓库无 `Last-Event-ID` / `lastEventId`；SDK `sdk/js/src/sse.ts:6-32` 的 `SseEvent` 没有 `id` 字段，
  `NativeFrame`（`types.ts:355-360`）也没有 `seq`，SDK 侧**不做去重**。
- `/chat/resume`（`ChatController.java:596`）只吃 query 参数 `sessionId`，先发 `snapshot` 再推增量；
  快照来自 `ChatRunBus.safeSnapshot():461-485` + `ChatService.resumeSnapshot():819-845`。
- 事件本体**只在内存**（`ChatRunBus.runs`，类注释 `:44-52` 明说重启即丢）。Redis 只存协调态：
  `wenqu:run:{sessionId}`（TTL 30 分钟）、`wenqu:run:views:*`（20 秒）、瞬态 Pub/Sub 频道
  （`service/RunBusCluster.java:46-58`）。落库的只有结构性账本 `c_ai_session_event`
  （`V1__baseline.sql:1302-1315`），**不含逐字增量**。
- **与验收直接冲突**：`chat.detachGraceMs = 180000`（3 分钟，`ConfigService.java:654`），
  无观众到点 `onGraceExpired` 按中断收束（`ChatRunBus.java:579-598`）；而方案 09 节要求
  「杀掉客户端 **5 分钟**后用 Last-Event-ID 续传，seq 连续无重复无丢失」。
  ⇒ 3 分钟后轮已经没了，现有机制**不可能**满足这条验收。

### 1.4 一轮的身份

- **无 runId**。`turnId`（32 位 hex，`ChatService.java:328`）贯穿 `c_ai_message.turn_id`、
  `c_ai_session_event.turn_id`、`c_ai_tool_approval.turn_id`、Redis `wenqu:run:*`、
  `done` 载荷、webhook payload。运行态在 `TurnRegistry`（进程内 Map）与 `ChatRunBus.Run`。
- 框架层的 `executionRunId`（`agentx/SessionLogArchive.java:219`）是「一次执行任务」，
  **同一 turnId 可有多个 runId**（`TurnSessionGateway.java:30-40`），语义不等于「一轮问答」，不能拿来当对外 runId。
- 另有 5 类同名 run（工作流 `WorkflowRun`、评测 run、`ScheduledRun` 等），
  其中工作流审批把 `sessionId` 直接存成 runId（`WorkflowEngine.java:1140-1162`）——语义裂缝，勿复用。

### 1.5 审批 / 产物 / webhook / 插话停止

| 能力 | 真源 | 现状 |
|---|---|---|
| 三张审批卡 | `controller/ChatController.java:610/677/804`，`agent/hitl/HitlDecisionService.java`，表 `c_ai_tool_approval` | 机制完整，但 **decision 枚举分散**（`PlanDecision` 四态 / 工具审批只有 bool / askUser 是作答），全靠字面量；无 run 级端点 |
| 审批超时 | `HitlDecisionService.java:430-450`、`agentx/turn/TurnInteractionCoordinator.java` | 工具/计划超时收敛 `TIMEOUT` + `notice#timeout`；askUser 超时**不收终态**（`CONTINUED`）。方案要求统一 `approval_timeout`，需收敛口径 |
| 跨副本 | `HitlDecisionService.java:122-124` 三张 `ConcurrentMap` 唤醒句柄 | **进程内**，v1 请求打到非宿主副本会找不到等待者——最实质的改造点 |
| 产物 | `model/Artifact.java`、`service/ArtifactService.java:961-999`、`controller/ArtifactController.java` | 按 **uid + sessionId** 归属，签名 URL 1 小时（`ImageUrlSigner`）；表上无 runId；下载只验签名不验 uid |
| 出站 webhook | `service/webhook/AgentWebhookService.java`、`util/OutboundWebhook.java` | HMAC-SHA256 (`X-Wenqu-Signature`)、4 级退避、投递表 `c_ai_webhook_delivery` 齐全；但事件名 `agent.turn.finished`、幂等键是 `turnId/messageId`，**无 runId**、无唯一约束 |
| 插话 / 停止 | `ChatController.java:504/426`，`ChatRunRuntime.java:424-477 / 150-185` | 停止天然幂等（无在跑轮 → `stopped=false`）；插话先投递进活轮、框架收下才落库；按 `sessionId` 寻址 |

### 1.6 契约层约束

- v1 路径必须是 **`/api/ai/v1/`** 前缀（`openapi/OpenApiRegistry.java:42`），方案 HTML 里的 `/v1/...` 是简写。
- 每个 v1 方法都要 `@OpenApi(scope=..., summary=...)`（`openapi/OpenApi.java:19-32`）；
  未标注的 v1 路由启动期直接失败（`OpenApiRegistry.java:103-106`）。
- `OpenApiScopes.ALL`（`OpenApiScopes.java:13-21`）目前只有 5 档，**没有 runs 类**；
  新增 scope 必须同时被至少一个 `keyAccessible` 端点使用，否则启动失败（`:107-112`）。
- 限流**不是自动挂的**，要在控制器方法首行显式 `rateLimitService.checkRateLimit(bucket, uid)`
  （`OpenAiCompatController.java:130` 等）。
- 归属统一用 `RequestUser.uid()`；API Key 身份恒为签发人本人。产物签名 URL 与框架裁决通道
  （`FrameworkSessions.respond*`）**没有显式 uid 比对**，v1 要补。

### 1.7 总账

| v1 目标 | native 真源 | 判定 |
|---|---|---|
| `POST /v1/agents/{id}/runs` | `POST /api/ai/chat` → `ChatService.chat()` | 引擎已具备；需控制器 + 投影层 |
| `run.started` / `token` / `tool.status` / `artifact.created` | `turn_start` / `token` / `tool_status` / `artifact` | 已具备，payload 需 typed 化 |
| `plan.updated` | `plan` + `deep_plan_delta` + `deep_plan_approval` | 需多名合一映射 |
| `approval.required` | `approval_required` / `ask_user` / `deep_plan_approval` | 已具备；提交端点需补显式 uid |
| `run.done` / `run.error` | `done` / `error`（纯文本） | 已具备；需结构化 code |
| `GET /v1/runs/{id}/events` + Last-Event-ID | 内存 `ChatRunBus` + `/chat/resume?sessionId=` | **缺失最多**：无 `id:`、无回放、无 runId、跨重启丢 |
| `run.finished` webhook | `agent.turn.finished` + 投递表 | 机制已具备；换事件名/payload/幂等键 |

## 2. 六个设计判断

### J1 · runId 直接用 turnId，加一张轻量映射表，不新建状态机
> **实现已调整（见 §10.2）**：按 `CollectingSseEmitter` 接缝落地后，runId 实际是**对外独立
> 句柄**而非框架 turnId。下表是方案阶段的判断，保留作为决策记录；以实现与 V21 口径为准。

`turnId` 已经是消息、审批、事件账本、webhook 的共同幂等键。另造一个 UUID 会多一层映射且要和
框架 `executionRunId` 混淆。做法：

- 对外 `runId` = `turnId`（不换值，集成方拿到的就是平台内部同一个号）；
- 新增 `c_ai_open_run(run_id PK, session_id, uid, agent_id, status, created_at, finished_at)`，
  仅用于**快速归属与状态查询**（`GET /runs/{id}` 不必扫消息表），不承载执行状态机；
- **不动** `c_ai_message` / `c_ai_tool_approval` / `c_ai_artifact` 的归属键，避免与工作流 run 串线。
- 状态从现有信号投影：`running`（`TurnRegistry`/`ChatRunBus` 有活轮）、`succeeded`（`done`）、
  `failed`（`error`）、`stopped`（`chat/run` 的 stopped 标记）。进程重启后活轮消失 → 统一按 `failed/interrupted`
  收敛，不假装还在跑。

### J2 · 事件回放用 Redis 短 TTL 缓冲，不把 SSE 全量写 MySQL

方案 06 节允许「保留期外返回快照，SDK 自动降级重拉」，所以**不需要**永久事件日志。设计：

- 新增 `wenqu:run:events:{runId}`（Redis List，元素 = 已投影的 v1 帧 JSON），
  在投影单点追加，TTL 默认 **10 分钟**（可配 `runs.eventRetentionMinutes`）；
- SSE 帧同时写 `id: <seq>`，SDK 断线时带 `Last-Event-ID`；
- 请求 `GET /v1/runs/{id}/events` 时：缓冲命中 → 从 `id+1` 回放后接实时流；
  缓冲过期/不存在 → 返回 `snapshot` 帧（`running:false` 或当前快照）+ `run.error(resume_expired)`，
  由 SDK 降级重拉 `GET /runs/{id}`，**不静默当新流从头开始**；
- 逐字 `token` 全量进 Redis 会有体积与隐私成本（含模型输出），故**默认只回放稳态事件**
  （`run.started` / `tool.status` / `plan.updated` / `approval.required` / `artifact.created` / `run.done`），
  `token` 只保留最近 N 条用于拼接，其余靠 `snapshot` 的 `content` 补全文。

### J3 · 冻结 8 个对外事件 + 映射表，未知类型走兜底

对外事件名与 native 名分离但一一对应，映射表写进代码常量并进契约文档：

| v1 事件 | native 来源 | 投影规则 |
|---|---|---|
| `run.started` | `turn_start` | 补 `runId` / `agentId` / `sessionMode` / 工具清单摘要（从 `done` 的 `toolCalls` 摘要口径取） |
| `token` | `token` | **真增量** `delta`，不回吐全文 |
| `tool.status` | `tool_status` | 取 `name / label / status / elapsedMs / stepId`，丢弃 UI 字段（`hint/brief/preparing`） |
| `plan.updated` | `plan` + `deep_plan_delta` + `deep_plan_approval` | **只回最新版快照**，不做逐条 diff；审批卡另发 `approval.required` |
| `approval.required` | `approval_required` / `ask_user` / `deep_plan_approval` | 统一形状 `{approvalId, kind, options[], timeoutMs, payload}`，调用方回 `/approvals` |
| `artifact.created` | `artifact` | 回 `id / name / kind / size`，下载走 `/artifacts`，不回签名 URL |
| `run.done` | `done` | 与 `GET /runs/{id}` 同口径：`finalContent / usage / sources / artifacts / status` |
| `run.error` | `error` | 稳定 `code` + `message` + `request_id`，**不暴露堆栈** |

`thinking` **默认不对外**，由智能体配置显式开启才发（方案 06 节）。
新增 native 事件不升级 SDK：SDK 已有 `onEvent` 兜底派发（`native.ts:358-361`），契约只增不删。

### J4 · 新增 `runs.read` / `runs.write` 两个 scope，且**不进默认集**

- 读：`GET /runs/{id}`、`/runs/{id}/events`、`/runs/{id}/artifacts` → `runs.read`；
- 写：`POST /agents/{id}/runs`、`/runs/{id}/steer`、`/stop`、`/approvals` → `runs.write`；
- 同步改 `OpenApiScopes.ALL`、`ApiKeyService` 别名、`GET /api-key/scopes` 下发与前端勾选；
  两个 scope 各自都有端点使用，满足 `OpenApiRegistry` 启动校验；
- **不加入 `DEFAULT`**：存量 Key（`scopes=NULL` 落默认集）不应自动获得 run 能力，
  与 `kb.write` 同口径，必须显式勾选。这是最小权限，不是兼容层。

### J5 · 跨副本审批复用 `RunBusCluster` 转发，不新造一套

`POST /v1/runs/{id}/approvals` 可能落在非宿主副本。照 `ChatRunRuntime.forwardStop()`
（`:156-170` → `RunBusCluster.java:343-360`）的形态，在 `RunProjection` 里加一个
`forwardDecision(runId, decision)`：先查 `wenqu:run:{sessionId}` 的 `replica`，命中宿主则发
`wenqu:bus:cmd` 决策帧，宿主侧唤醒本地 `CompletableFuture`；未命中（卡已超时/轮已收尾）
直接返回终态 + `approval_timeout`，不静默丢弃。

### J6 · 与 `chat/completions` 边界写死

`chat/completions` 继续做「无状态、文本、收集型单块下发」的兼容面；逐 token 真增量、
长任务、人在回路**只承诺在 runs 上**。两条链路共用引擎但不共用承诺，文档与 SDK 都要标明，
避免集成方以为 OpenAI 兼容面的 stream 就是真增量。

## 3. 契约设计

### 3.1 端点（全路径 /api/ai/v1/...）

| 方法 | 路径 | scope | 要点 | 复用 |
|---|---|---|---|---|
| POST | `/agents/{agentId}/runs` | `runs.write` | `Idempotency-Key`；默认无状态，显式 `sessionId` 才持久（D2） | `ChatService.chat()` + `ChatCommand.agentId` |
| GET | `/runs/{id}` | `runs.read` | 状态 / 输出 / 用量 / 错误，与 `run.done` 同口径 | `c_ai_open_run` + `TurnDonePayload` |
| GET | `/runs/{id}/events` | `runs.read` | SSE，`Last-Event-ID`，`id:`=seq | `RunProjection` + Redis 缓冲 |
| POST | `/runs/{id}/steer` | `runs.write` | 运行中插话，沿用现有「框架收下才落库」 | `ChatRunRuntime.steerTurn()` |
| POST | `/runs/{id}/stop` | `runs.write` | 幂等；已结束返 200 + 终态 | `ChatRunRuntime.stopTurn()` |
| POST | `/runs/{id}/approvals` | `runs.write` | `decision` 统一枚举；超时收敛 `run.error(approval_timeout)` | `HitlDecisionService` + 跨副本转发 |
| GET | `/runs/{id}/artifacts` | `runs.read` | 只回可下载项（id/name/kind/size）+ 当场换发的 `downloadUrl`（1 小时）；不新增第 9 个端点 | `ArtifactService.toDto()` + `ImageUrlSigner` |
| HOOK | `run.finished` | — | HMAC + `runId` 幂等键，重投不产生第二条业务记录 | `AgentWebhookService` 投递表 |

`decision` 统一为 `approve | reject | revise | supersede | answer`（前四个沿用 `PlanDecision`，
`answer` 对应 askUser），入参带 `approvalId`；工具审批的 `{approved:bool}` 由投影层翻译，
**不改内部 Service**。

### 3.2 错误码（稳定，不暴露堆栈）

`invalid_request` / `authentication_error` / `permission_error`（缺 scope 点名缺哪项、去哪开） /
`not_found`（run 不存在或不属于该 Key 签发人，两者同码，避免探测） /
`rate_limit_error` / `approval_timeout` / `resume_expired` / `run_interrupted` / `internal_error`。
每个错误带 `request_id`（`RequestIdFilter` 已有）。

### 3.3 契约登记流程

新增端点 → 标 `@OpenApi` → `node scripts/check-openapi-contract.mjs --update` 更新
`contract/openapi.v1.json` 与 `CHANGELOG.md`（人工补「为什么改」）→ CI `--check` 守住只增不删。
事件 schema 以 `components.schemas` 形式进 `OpenApiRegistry.spec()`（当前 `spec()` 只生成路径与
`Error` schema，需扩展一处）。

## 4. 投影实现（不复制引擎）

### 4.1 单点订阅者

新增 `service/openrun/RunProjection`，**只挂一处**：`ChatRunBus.publish/publishRaw/publishToSession`
与 `ChatRunRuntime` 直写路径的汇合点。职责固定四件：

1. `turnId → runId` 查/写 `c_ai_open_run`；
2. native 事件名按 J3 映射表过滤 + payload typed 化；
3. `seq` 写成 SSE `id:`，帧追加到 `wenqu:run:events:{runId}`；
4. 终态（`done` / `error` / `stop`）更新 `c_ai_open_run.status` 并触发 `run.finished` webhook。

**不改**：`ChatService.chat()`、`RunChannel` / `SseRunEventChannel`、`AgentscopeChatEngine`、
`ChatRunRuntime` 的主体逻辑、`web/src/api.js` 的消费路径、`sdk/js/src/native.ts` 的既有回调。

### 4.2 新增文件（落点）

| 文件 | 职责 |
|---|---|
| `controller/OpenRunController.java` | 8 个 v1 端点（薄控制器，只做参数校验 + scope + 限流 + 委派） |

### 4.3 必须处理的 3 分钟宽限

`chat.detachGraceMs = 180000` 会在客户端断开 3 分钟后收束轮，与 5 分钟续传验收冲突。
两种做法，**建议后者**：

- 全局调大：影响网页端「关掉页面就别再烧模型」的既有语义，不可取；
- **按轮豁免**：`RunProjection` 在 `c_ai_open_run` 标记 `external=true`，`ChatRunBus.onGraceExpired`
  增加一条判据（外部 run 且回放缓冲未过期 → 续期），宽限上限取
  `max(chat.detachGraceMs, runs.eventRetentionMinutes)`。这是唯一需要**碰** `ChatRunBus` 的地方，
  且只加一个判据，不改扇出语义。

## 5. 续传、幂等、归属

- **续传**：`id:` = 全局单调递增 seq（与 `ChatRunBus.Run.seq` 同源）；客户端带 `Last-Event-ID: n`，
  服务端从 `n+1` 回放后接实时流；缓冲过期 → `snapshot` + `run.error(resume_expired)`，
  SDK 降级 `GET /runs/{id}` 重拉。验收「seq 连续、无重复、无丢失」在 5 分钟窗口内成立。
- **建 run 幂等**：`Idempotency-Key` 头 + `(uid, agentId, key)` 落 `c_ai_open_run` 唯一约束；
  重放返回同一 `runId` 与当时状态，不新起一轮。框架侧已有 `AgentSession.submit(idempotencyKey)`
  概念，但**没有 HTTP 头**，需在控制器层补。
- **webhook 幂等**：payload 加 `runId`，业务头加 `X-Wenqu-Run-Id`
  （工作流侧 `WorkflowService.java:1837` 已有先例）；接收方按 `runId` 去重。
  平台侧投递表当前无唯一约束，建议给 `(runId, event)` 加唯一键，避免 `sweepRetry` 重投多行。
- **归属**：所有端点用 `RequestUser.uid()`（Key 恒为签发人本人），先查 `c_ai_open_run.uid`
  再放行；审批/插话/停止按 `runId → sessionId` 反查后沿用现有 uid 比对；
  产物不在 `artifact.created` 事件里给签名 URL；由 `GET /runs/{id}/artifacts` 先按 runId 校验归属，
  再当场换发 1 小时 `downloadUrl`——避免持 URL 即可绕过归属（现有静态下载只验签名不验 uid）。

**A1 验收（逐条实测，不写「应该可以」）**：

1. 建 run → `token` 真增量 → `approval.required` → 提交审批 → `artifact.created` → `run.done`；
2. 运行中插话与停止各测一次，终态与 `GET /runs/{id}` 一致；
3. 杀客户端 5 分钟后带 `Last-Event-ID` 续传：seq 连续、无重复、无丢失；超保留期返回 `resume_expired` + 快照；

6. 非宿主副本提交审批能唤醒宿主（双副本验证栈）；
7. `POST /runs` 带同一 `Idempotency-Key` 重放不新起轮；

| 风险 | 等级 | 对策 |

## 10. 实现进展与选型调整（2026-11-15）

### 10.1 投影出口改用 `CollectingSseEmitter` 子类，不挂 `ChatRunBus`

§4.1 原写「在 `ChatRunBus.publish` 单点挂订阅者」。落地时改成
`service/openrun/OpenRunEmitter extends CollectingSseEmitter`，理由是代码事实而不是省事：

- `ChatService.chat():341` 用 `emitter instanceof CollectingSseEmitter` 判收集型通道：继承它即可
  **复用同一条问答流水线**，同时天然不登记运行总线、不挂 `TurnDeadline` 看门狗、
  不占网页端 `chat.detachGraceMs` 的无观众宽限。定时任务用的正是这条形态。
- 挂 bus 要同时覆盖两条写帧点（`ChatRunBus.java:427` 总线路径、`ChatRunRuntime.java:713` 直写路径），
  漏一条就丢事件；改核心扇出还会把回归面扩到网页问答。
- 运行总线是给「多个网页观众接同一轮」设计的；v1 run 由外部独立发起，本来不需要多观众。

**连带结果**：§4.3 的「3 分钟宽限 vs 5 分钟续传」冲突**消失**——外部 run 不进 bus，
不受 `detachGraceMs` 收束；续传完全由 `RunEventReplay` 的 Redis 短 TTL 缓冲保证（J2）。

为此给 `CollectingSseEmitter` 加了一个默认关闭的 `forwardAllFrames((type, raw) -> …)` 转发口：
定时任务 / MCP / 子智能体分支不注册，行为逐字节不变。

### 10.2 A1 第二批实现（已完成，与方案的四处差异）

**范围**：`POST /runs/{id}/approvals`、`GET /runs/{id}/artifacts`、`POST /runs/{id}/steer`、
`POST /runs/{id}/stop`、`run.finished` 出站回调、`run.error` 稳定错误码分级。
契约快照 18 → **22 端点**（只增不删），V21 给 `c_ai_webhook_delivery` 加 `run_id` 唯一键。

| # | 方案设想 | 实际做法与原因 |
|---|---|---|
| 1 | J1 `runId = turnId` | **不成立**。`OpenRunService.create` 生成 runId，`ChatService.chat` 另生成 turnId，`ChatCommand` 无 turnId 字段。要让两者相等得侵入引擎（改 ChatCommand + ChatService），回归面远大于收益。**不补映射列**：第二批四个端点全部走「runId → sessionId → 现有能力」；审批卡额外校验归属会话 + 产生时刻（避免复用会话时裁到上一轮）。V20 已执行不能改 checksum，口径更正写进 V21 头注释与 `OpenRun` 类注释。 |
| 2 | J5 照 `forwardStop()` 形态做跨副本审批转发 | **复用更贴合的既有通道**。`FrameworkSessions.respond/respondAsk/respondPlanApproval` 内部已有 `routeAnswerElsewhere` → `AgentxCluster.forwardAnswer`，是带 5s 回执的审批专用转投；而 stop 总线 `forwardCommand` 是 fire-and-forget 且只注册了 `"stop"` handler。照方案另造分支反而更差，故不新增总线 handler。 |
| 3 | 超时收敛 `run.error(approval_timeout)` | 实测超时后引擎仍会发 `done`（带超时尾标），提前 finish 会丢掉后续终态。改为新增 **`approval.timed_out` 过程事件**（只增不删），不收终态；终态仍由 done/error 决定。warn 帧按文案白名单过滤，`ask_user` 的「前台等待结束、本轮继续」不算超时。 |
| 4 | 停止后 `status=stopped` | 原生 `stopTurn` **不发 SSE 帧**，收尾仍是引擎的 done，直接投影会写成 succeeded。用 Redis 短标记 `wenqu:run:stop:{runId}`（TTL 同回放缓冲）把「停过」带到投影层，在 done 到达时改判 stopped，SSE 帧与 `c_ai_open_run.status` 一致。 |

**其余实现要点**：
- **审批**：统一 `decision` 枚举（approve/reject/revise/supersede/answer/ignore），按 `c_ai_tool_approval.tool_name`（`planApproval` / `askUser` / 其它）分派；照 `ChatController` 三段顺序「框架待办优先 → Hitl 回退 → CONTINUED 收尾」，归属两跳 `mustOwn` + `getApproval(uid)` + 会话/时刻校验。
  **实机挖出并修掉的一个真缺口**：`FrameworkSessions.respond*` 面对残留 PENDING 卡 / 卡片已终态 / 跨副本句柄丢失时，有时把 `IllegalArgumentException("No pending interaction: …")` 直接抛到外层（会话忙则是 `IllegalStateException`），原生端点因为卡都登记过所以碰不到；v1 端点不收口就会变成 400，旧通道明明能按 DB 行收尾却走不到。现在 `frameworkRespond` 只把这两种「没有待办 / 会话忙」信号当 false，其余异常照抛，重复提交如实落 409。
- **产物**：`ArtifactService.listBySession(uid, sessionId, run.createTime)` 只取本 run 之后的产物，`ImageUrlSigner.signUrl` 当场换发 1 小时 URL（事件帧里仍不给 URL，与方案一致）。
- **webhook**：不新建 service，在 `AgentWebhookService` 加 `EVENT_RUN_FINISHED` + `onRunFinished`，复用 `deliver/attempt/sweepRetry` 整套至少一次机制；幂等两层（应用层查 + `uk_wh_run_id` 唯一键）。`onTurnFinished` 按 `sourceName="open-run"` 跳过，**不双发**；挂点是 `OpenRunEmitter.finish` → `OpenRunService.finish` 这个唯一收敛点。业务头对 run 行改发 `X-Wenqu-Run-Id`。
- **错误码**：`OpenRunErrorCode` 定义稳定集合。`resume_expired` / `approval_timeout` 由 v1 自己产生，精确；native error 只有一句人话，按保守关键词分类，拿不准一律 `internal_error`，**契约保证码集合只增不删，不承诺精确归因**（已在类注释写明）。
