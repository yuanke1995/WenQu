快速开始

签一把 Key、跑一次自检、拿到第一个成功响应。三步，五分钟。

#三步走到第一个成功响应

  1. 签 Key —— 问渠「个人设置 → API 密钥」新建。选用途模板（问答 / 检索 / 工作流 / 全量）会自动预选 scope； 默认集里没有 runs.read、runs.write、kb.write，要跑 run 原语必须显式勾选。
  2. 自检 —— 拿 Key 打一次 GET /v1/me：能力范围、发问身份、限流、近 30 天用量一次看清。
  3. 首响 —— 复制下面的代码，只改 baseUrl 与 Key。

Key 恒以签发人本人身份发问，不存在机器号，也不能改绑别人。给哪个系统对接，就用那个系统归属的账号签发。

#1. 自检：这把 Key 能干什么

bash
curl __BASE__/api/ai/v1/me \
  -H "X-Api-Key: sk-你的Key"
json
{
  "key": "客服系统对接",
  "keyPrefix": "sk-3f8a…",
  "scopes": ["chat", "kb.read"],
  "actAs": "u_10086",
  "actAsBinding": "issuer",
  "limits": { "enabled": true, "windowSeconds": 60, "chatPerMinute": 10, "embeddingPerMinute": 60 },
  "usage30d": { "available": true, "calls": 128, "tokens": 96240 },
  "expiresAt": null,
  "contract": "/api/ai/v1/openapi.json"
}
  • actAs 恒为签发人（actAsBinding=issuer）；平台没有「代表账号」这一说。
  • limits 是平台按「桶 + 租户 + 账号/IP」分桶的当前配置，不是这把 Key 的独占配额。
  • usage30d.available=false 表示台账暂不可查，不等于 0 次调用。

接入选型

三层不是三条技术路线，差别只有一句话——谁持凭据、承诺到什么程度。

#三种形态，一种凭据边界

层谁持凭据形态承诺什么时候用
L0 零代码嵌入分享 token（浏览器不持 Key）wenqu-embed.js / iframe正式官网 / 帮助中心 / 客服台放一个问答入口
L1 前端深度集成业务后端代理，浏览器零凭据client.native 事件协议（A 期后走 run 事件）实验性自家前端要展示审批卡、产物、插话、计划
L2 后端集成API Key / 服务账号（只在服务端）v1 REST + webhook + MCP正式业务后端、自动化流程、批处理

凭据边界一句话：API Key 只在服务端，浏览器零凭据。L1 + L2 可以共用同一个业务后端，Key 仍然不进浏览器。

#选型问四句

  1. 只想在自己页面上放一个问答入口？ → L0（分享 token，零代码）
  2. 要嵌进自家前端，而且要展示审批、产物、计划过程？ → L1（业务后端代理，浏览器零凭据）
  3. 由业务系统后端调用，或要把结果通过回调送回业务？ → L2（API Key + webhook）
  4. 既要前端体验又要后端事件？ → L1 + L2，两者共用同一个后端，Key 仍然只在服务端。

#承诺分级

  • 正式 = 只增不删 + 变更日志 + 至少两个 minor 的废弃期。删端点、改 HTTP 方法、改 scope、 改 keyAccessible 都算破坏性变更，CI 会挡下来。
  • 实验性 = 字段可改，接口变更提前在本站公告。L1 先挂这个标签，run 契约冻结并稳定两周后转正。

为什么只正式承诺两层：三层全部正式会把维护面直接翻三倍，收益却在「少数要过程能力的前端」身上。

别把两种承诺混用：chat/completions 是无状态、文本、收集型单块下发的兼容面； 逐 token 真增量、长任务、人在回路只在 run 原语上承诺。

认证与安全

一把 Key 代表一个人。它能碰的面是固定的白名单，不是「这个账号在界面上能点什么」。

#地址拼法

后端 context-path 是 /ai，完整地址 = 服务地址 + /ai + 接口路径：

bash
# 本机实例
__BASE__/api/ai/v1/me

# 线上（同一台机器反代到 /ai）同形：
https://your-host/ai/api/ai/v1/me

#认证头

bash
X-Api-Key: sk-xxxxxxxx
  • Authorization: Bearer sk-… 等价（给 OpenAI SDK 用，Authorization 里必须是 sk- 开头）。
  • MCP 入口例外：它只认 Authorization: Bearer。
  • 分享 token 是另一条通道（L0 / 公开链接），不与 Key 混用。

#两类响应体

v1 命名空间（/api/ai/v1/**）：成功是裸对象或业务形状，错误统一 OpenAI 形状：

json
{
  "error": {
    "message": "该 API Key 未开通「runs.write」能力；请在问渠「个人设置 → API 密钥」编辑该 Key 的权限范围后重试",
    "type": "permission_error",
    "code": "permission_error",
    "request_id": "3f8a1c2e…"
  }
}

非 v1 的既有接口（如原生问答 /api/ai/chat）：走平台包络 {"success":true,"data":…} / {"success":false,"msg":"原因"}。两套形状的边界就在命名空间上，SDK 已各自抹平，手写 curl 时别按同一种解。

#scope：Key 的能力范围

每把 Key 一份 scope，签发时勾选、之后可在「个人设置 → API 密钥」编辑。只约束 Key 通道（登录态不受影响）， 收紧立即生效。

scope默认开通覆盖能力
chat是问答（/v1/chat/completions、/v1/responses）
embedding是向量化（/v1/embeddings）
kb.read是知识检索与知识库只读（/v1/retrieval、/v1/kbs 读侧）
workflow.run是触发已发布工作流（/v1/workflows）
kb.write否建库与上传文档（/v1/kbs 写侧）
runs.read否查 run 状态 / 事件流 / 产物
runs.write否建 run、插话、停止、提交审批

kb.write、runs.read、runs.write 不进默认集：存量 Key 不应因为平台升级就自动多出写库或跑长任务的权限。 缺哪个就 403 点名哪个，报错原文里写着去哪一列勾。

#Key 碰不到什么

Key 只开放问答链路。以下是硬性拒绝（HTTP 403，当场给出原因，不会静默落到别的鉴权层）：

端点前缀为什么不给
/api/ai/api-key/**Key 管理——否则泄露的 Key 能给自己签发续命、改绑定换身份
/api/ai/user/**改密 / 资料 / 偏好 / 个人设置——贴在配置文件里的密钥不该拥有账号自服务能力
/api/ai/auth/**登录鉴权（唯一例外 GET /auth/me，只读身份自检）
/api/ai/skill/**、/api/ai/mcp/**、/api/ai/market/**、/api/ai/scheduled/**、/api/ai/credential/**能力配置面：技能 / MCP / 市场 / 定时任务 / 工作流凭据
/api/ai/session-shares/**、DELETE /api/ai/session(s)…分享管理、删历史（保留审计线索）
/api/ai/agent/{id}/publish · /share智能体发布与分享配置

白名单之外的一切端点对 Key 一律 403——即使签发人在界面上是管理员。Key 的 API 面恒为问答白名单，不受角色影响。

#契约注册表：v1 只认登记过的端点

/api/ai/v1/** 的唯一真源是后端的开放契约注册表（@OpenApi 注解 + Spring 路由，启动期扫描）：

  • v1 命名空间里出现未标注的路由直接启动失败——新增端点必须显式声明它对集成方的可见性；
  • 未登记的 v1 路径对 Key 一律拒绝，错误文案会指向 GET /api/ai/v1/openapi.json；
  • 契约变更走 CI：删除端点 / 改 scope / 改可达性一律失败，新增必须先跑 --update 登记。

#集成方守则

  • 一把 Key 一个用途，别多系统共用；不用了先「停用」而不是删除——停用保留审计线索，删除记录即消失。
  • Key 等于签发人的问答身份与额度，按敏感凭据保管（配置文件 / 密钥管理服务），不进前端代码与日志。
  • 明文由服务端加密保管（列表点「眼睛」可回显）；怀疑泄露就停用重签。
  • 轮询注意限频，见错误码与限频。

#run 原语一行开跑

javascript
const run = await client.runs.create("agent-id", "帮我核对这份报销单", {
  idempotencyKey: "order-20261115-001",   // 重试不重复建 run
});

const summary = await client.runs.stream(run.runId, {
  onEvent: (ev) => {
    if (ev.event === "token") process.stdout.write(ev.data.delta);
    if (ev.event === "approval.required") {
      // 审批走同一个 run，不是另一个接口
      client.runs.approve(run.runId, ev.data.approvalId, "approve");
    }
  },
  onFallback: (detail) => console.log("回放已过期，已降级为拉取终态", detail.status),
});
console.log(summary.status);   // succeeded / failed / stopped
python
run = client.runs.create("agent-id", "帮我核对这份报销单", idempotency_key="order-20261115-001")

def on_event(ev):
    if ev.event == "token":
        print(ev.data["delta"], end="")
    elif ev.event == "approval.required":
        client.runs.approve(run["runId"], ev.data["approvalId"], "approve")

summary = client.runs.stream(run["runId"], on_event=on_event)
print(summary["status"])

事件名、字段与续传语义见事件契约；approve/steer/stop/artifacts/get 都是 runs 上的方法。

#自动续传做了什么

  • 记住每条事件的 id:（= seq），断线后带 Last-Event-ID 重连，最多 3 次退避重试；
  • 按 seq 去重，重连不会把已经处理过的事件再交一遍；
  • 回放缓冲已过期（resume_expired）时，自动降级为 GET /runs/{id} 拉终态，结果经 onFallback 交回，不抛异常、不留空。

#版本头

每个请求带 X-Wenqu-Sdk-Version。后端 debug 日志比对，提前发现「服务端已升级、客户端还是老版本」的错配。 四处版本号（JS 包清单 / JS 版本源 / Python 包清单 / Python 版本源）由 CI 闸门 scripts/check-sdk-version.mjs 对齐。

#错误类型

javascript
import { WenquAuthError, WenquRateLimitError, WenquApiError } from "@wenqu/sdk";

WenquAuthError（401/403，带 code 与 request_id）、WenquRateLimitError（429）、WenquApiError（其余）。 Python 侧统一 WenquError，字段 message / status_code / error_type / code / request_id。

事件契约（run 原语）

审批、产物、插话、停止、计划都在同一条 run 上。这是对外唯一的运行原语，不复制引擎。

#为什么要 run

chat/completions 是「无状态、文本、收集型单块下发」的兼容面。它没有任务身份、没有过程事件、 没有人在回路的入口。run 原语是把已有的站内运行过程投影成一条对外可订阅的链路：

  • 一条 run = 一次智能体运行，有稳定 id、有终态、有事件序列；
  • 审批 / 产物 / 插话 / 停止都挂在同一个 runId 上，不另开接口族；
  • 实现是投影（复用 native 会话与断线接流），引擎没变——所以站内看到的行为与对外一致。

#七个端点

方法路径scope要点
POST/v1/agents/{agentId}/runsruns.writeIdempotency-Key 去重；默认无状态，显式传 sessionId 才持久
GET/v1/runs/{id}runs.read状态 / 输出 / 错误，与 run.done 同口径
GET/v1/runs/{id}/eventsruns.readSSE，Last-Event-ID 续传，id: = seq
POST/v1/runs/{id}/approvalsruns.write统一 decision 枚举，按 approvalId 提交
GET/v1/runs/{id}/artifactsruns.read只回可下载项 + 当场换发的签名 URL（1 小时）
POST/v1/runs/{id}/steerruns.write运行中插话（纯文本），框架收下才落库
POST/v1/runs/{id}/stopruns.write幂等；已结束返 200 + 终态

  "createdAt": "2026-11-15T19:06:12"
}
  • question 必填；sessionId 不传就是一次性运行（D2：默认无状态）。
  • 同一 Idempotency-Key 重放直接回同一个 runId，返回体多一个 idempotent: true，不新起一轮。
  • 出站账号恒为 Key 签发人；智能体停用会当场 400（不能靠建新 run 绕开）。

#事件表

event: 行是下面 9 个名字之一，id: 是 seq（从 1 连续），data: 是带 runId 的扁平 JSON。

事件含义data 关键字段

tool.status工具执行进度native:{name,status,elapsedMs,stepId}

#审批：回同一条 run

text
event: approval.required
id: 12
data: {"runId":"9f2c…","approvalId":"ap_88","kind":"tool_approval","payload":{…}}
bash
curl -X POST __BASE__/api/ai/v1/runs/<runId>/approvals \
  -H "X-Api-Key: sk-你的Key" -H "Content-Type: application/json" \
  -d '{"approvalId":"ap_88","decision":"approve"}'

decision 统一为 approve | reject | revise | supersede | answer | ignore；kind 是 tool_approval / plan_approval / ask_user。answer 对应问答卡，其他按计划/工具审批处理。

  • 卡片已处理或已超时 → 409，文案是「已处理或已失效」。重新拉事件流取新的 approvalId， 不要拿旧 id 重试。
  • 审批卡不在本副本时由网关内部转发到宿主副本，调用方无感。
  • approvalId 是不透明字符串（形如 call_…，由产生这张卡的模型调用 id 派生成主键）， 不要解析、不要自己拼，只按事件里给的原样回传。

#超时：这一步被跳过，不是整轮失败

审批等待到达上限（chat.approvalTimeoutMs，默认 10 分钟）时，先到一帧 approval.timed_out（code=approval_timeout），工具/计划按「未批准」处理； 本轮仍会以 run.done 收口，finalContent 说明这一步没有执行。

所以判定要按事件、不要按状态：run.done(status=succeeded) 只表示「这一轮跑完了」， 不代表工具执行过。需要「超时即失败」的集成方，自己把 approval.timed_out 记成失败即可。 只有 run.error 才是整轮失败（code 见「错误码与限频」）。

#续传：Last-Event-ID + seq

bash
# 首次
curl -N __BASE__/api/ai/v1/runs/<runId>/events -H "X-Api-Key: sk-你的Key"

# 断线重连：把最后收到的 id 带回来
curl -N __BASE__/api/ai/v1/runs/<runId>/events \
  -H "X-Api-Key: sk-你的Key" -H "Last-Event-ID: 42"
  • id: 从 1 连续递增，没有空洞；客户端按 id 去重即可，不需要自己数帧。
  • 回放缓冲保留 10 分钟（Redis，短 TTL）。过期后流里回一帧 run.error(code=resume_expired)，提示「请重拉 GET /runs/{id}」——不会把过期伪装成一条新流从头开始。
  • 终止条件：收到 run.done / run.error 即结束；已结束的 run 再订阅，回放完直接关流。

#什么时候发

智能体运行结束（成功 / 失败 / 停止）后，问渠向该智能体配置的回调地址 POST 一条事件：

#请求头与验签

text
POST /your/callback
X-Wenqu-Event: run.finished
X-Wenqu-Run-Id: 9f2c…
X-Wenqu-Signature: sha256=<hex>
Content-Type: application/json

签名 = HMAC-SHA256(secret, 原始请求体)，十六进制，前缀 sha256=。secret 是智能体回调配置里的密钥。

javascript
// Express：必须用 raw body 验签，不能先用 express.json() 解析
import crypto from "node:crypto";

app.post("/callback", express.raw({ type: "application/json" }), (req, res) => {
  const expected = "sha256=" + crypto
    .createHmac("sha256", process.env.WENQU_WEBHOOK_SECRET)
    .update(req.body)                       // Buffer，字节级一致
    .digest("hex");

  const given = req.get("X-Wenqu-Signature") || "";
  const ok = given.length === expected.length &&
    crypto.timingSafeEqual(Buffer.from(given), Buffer.from(expected));
  if (!ok) return res.status(401).end("bad signature");

  const payload = JSON.parse(req.body.toString("utf8"));
  if (payload.event !== "run.finished") return res.status(204).end();

  // 幂等：runId 唯一。重投不产生第二条业务记录。
  if (db.seen(payload.runId)) return res.status(200).end();
  db.saveRun(payload);
  res.status(200).end();
});
python
# FastAPI：请求体用 bytes 拿，别用 Pydantic 模型先解析
import hmac, hashlib
from fastapi import FastAPI, Request, Response

@app.post("/callback")
async def callback(request: Request):
    raw = await request.body()
    expected = "sha256=" + hmac.new(SECRET.encode(), raw, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, request.headers.get("X-Wenqu-Signature", "")):
        return Response(status_code=401)
    payload = json.loads(raw)
    if not store.seen(payload["runId"]):
        store.save(payload)
    return Response(status_code=200)

验签三个坑：① 必须用原始字节（框架若先解析 JSON 再序列化，哈希就对不上）； ② 用恒时比较，别用 ==；③ 逐字节比较长度，缺失头直接拒绝。

#重试与幂等

  • 失败重试：60s → 5min → 30min → 2h 退避，耗尽后停止并留痕（不强投到天荒地老）。
  • 只认 2xx 为送达；3xx / 4xx / 5xx 都算失败。
  • 重投可能带相同 runId，所以幂等一定要做在 runId 上（不是消息体哈希）。
  • 建议：先落库（唯一键冲突即忽略）再触发副作用；不要「先发消息再存库」。

#回调地址的现实约束

  • 保存回调地址时过 SSRF 校验：127.0.0.1 / localhost / 内网段一律拒绝，生产必须公网可达。
  • 本地验证要绕开保存期校验（投递期不校验），samples/backend-node/README.md 给了具体做法——生产不要用。
  • 回调地址按智能体配置，不是按 Key。同一智能体的所有 run 都回同一个地址。

断线续传

SSE 断在长回答的中间是常态。契约给了序号和续传头，剩下的是客户端别把序号丢了。

#契约给了什么

  • 每帧带 id:，等于 seq，从 1 连续、无空洞；event: 是事件名，data: 是 JSON。
  • 重连时带 Last-Event-ID: <最后收到的 seq>，服务端从下一条开始补发。
  • 回放缓冲保留 10 分钟（Redis 短 TTL）。超出后回一帧 run.error(code=resume_expired)，让调用方改走 GET /runs/{id}。
bash
# 断线后从这里接着听
curl -N __BASE__/api/ai/v1/runs/<runId>/events \
  -H "X-Api-Key: sk-你的Key" \
  -H "Last-Event-ID: 42"

#手写客户端要点

javascript
let cursor = 0;
let retries = 0;

async function listen(runId) {
  while (retries < 3) {
    const res = await fetch(`${BASE}/api/ai/v1/runs/${runId}/events`, {
      headers: { "X-Api-Key": KEY, ...(cursor ? { "Last-Event-ID": String(cursor) } : {}) },
    });
    if (!res.ok) throw new Error("HTTP " + res.status);

    const reader = res.body.pipeThrough(new TextDecoderStream()).getReader();
    let buf = "";
    for (;;) {
      const { value, done } = await reader.read();
      if (done) break;
      buf += value;
      // 按空行切帧：解析 id: / event: / data:
      let at;
      while ((at = buf.indexOf("\n\n")) >= 0) {
        const frame = buf.slice(0, at);
        buf = buf.slice(at + 2);
        const ev = parseFrame(frame);            // {id, event, data}
        if (ev.id) cursor = Number(ev.id);       // 关键：先记住序号再处理
        if (ev.data?.code === "resume_expired") return fallback(runId);
        handle(ev);
        if (ev.event === "run.done" || ev.event === "run.error") return;
      }
    }
    retries++;                                  // 流被掐断：退避重连
    await sleep(500 * retries);
  }
}

async function fallback(runId) {
  // 缓冲过期：拉终态，不再假装能补齐过程事件
  const detail = await fetch(`${BASE}/api/ai/v1/runs/${runId}`, { headers: { "X-Api-Key": KEY } })
    .then(r => r.json());
  console.log("回放已过期，取终态：", detail.status, detail.output?.finalContent);
}
  • 先记 id 再处理事件：反过来的话，处理到一半崩了会重复消费。
  • 重连用退避（500ms 起，最多 3 次），别原地紧循环。
  • resume_expired 不是错误不是要重试，是一次降级信号：改用终态接口。

#SDK 里已经做了

javascript
const summary = await client.runs.stream(run.runId, {
  onEvent: (ev) => { /* 只会收到新事件，重连不会重复 */ },
  onReconnect: (attempt, cursor) => console.warn(`第 ${attempt} 次重连，从 ${cursor} 继续`),
  onFallback: (detail) => console.warn("回放过期，已取终态", detail.status),

SDK 记 id:、按 seq 去重、断线带 Last-Event-ID 重连 3 次、resume_expired 时自动 get(runId) 并回 summary.status = "resume_expired"（不抛异常、不留空）。Python 侧行为一致。

#什么时候必须自己处理

场景做法
客户端在浏览器，用户切后台被节流恢复时先 GET /runs/{id}：可能早就结束了，没必要重连
链路要跨进程接力（A 机断、B 机接）seq 存到共享存储，重连带 Last-Event-ID

续传只覆盖事件回放，不覆盖审批卡：卡片超时后会以 approval.timed_out 事件收口， 别指望重连后还能补交同一张卡。

#缺 scope 的文案到底写了什么

该 API Key 未开通「runs.write」能力；请在问渠「个人设置 → API 密钥」编辑该 Key 的权限范围后重试

该端点不在开放契约注册表内，默认拒绝；请从 GET /api/ai/v1/openapi.json 查已开放端点， 或让管理员把该能力登记进开放契约

该 API Key 只开放问答链路（问答 / 会话 / 反馈 / 引用溯源等）：这个端点不对 Key 开放

三类 403 的区别很重要：缺 scope 去勾选就能解决；未登记是平台没开放这个能力； 拒绝名单是结构性设计（Key 永远不该有账号自服务能力）。别把三者都当「权限不够，找管理员开」。

#问答：原生 SSE 链路

POST /api/ai/chat 是站内同款的原生流式接口——它不在 v1 注册表内（属于既有问答链路，按问答白名单放行）， 所以严格说不带「只增不删」承诺；但阶段事件比 chat/completions 丰富，L1 前端集成与内部代理用的就是它。

bash
curl -N -X POST __BASE__/api/ai/chat \
  -H "Content-Type: application/json" \
  -H "X-Api-Key: sk-你的Key" \
  -d '{"question":"如何创建评分组件？","agentId":"<智能体id>"}'

请求体主要字段：question（必填 ≤8000 字）、sessionId（续聊）、agentId、model、deepThink、 planMode、reasoningLevel、images（≤9 张 data URL）、attachments（fileId 来自 POST /api/ai/chat/attachment）、mentions（kb/doc/agent 三类 @ 引用）、historyRefs。

相关端点：POST /api/ai/session/new（建会话）、POST /api/ai/chat/stop、POST /api/ai/feedback、 GET /api/ai/session/{id}。

这条链路没有 run 身份、没有审批回传、没有续传序号。需要过程能力就上 run 原语。

#向量：OpenAI 兼容

bash
curl -X POST __BASE__/api/ai/v1/embeddings \
  -H "X-Api-Key: sk-你的Key" -H "Content-Type: application/json" \
  -d '{"input":["你好，世界"],"model":"<providerId>/<modelId>"}'
  • model 必填（问渠向量按知识库绑定，没有全局默认）；可用清单 GET /v1/models/embeddings。
  • input 单批 ≤256 条、单条 ≤8192 token；encoding_format 支持 float / base64；dimensions 可裁剪。
  • 响应是 OpenAI 标准形状，任何 OpenAI SDK 改 base_url 即可用；用量按 kind=embedding 单独记账。

#工作流：当 RPC 调

bash
curl -X POST __BASE__/api/ai/v1/workflows/<工作流id>/run \
  -H "X-Api-Key: sk-你的Key" -H "Content-Type: application/json" \
  -d '{"inputs":{"city":"杭州"}}'
  • inputs 对应开始节点入参，可整体省略。
  • 同步返回 run 全量：status / outputs / nodeTraces / durationMs。 outputs 是对象（结束节点出参，outputs.answer 直接取）、nodeTraces 是数组（节点级输入输出与耗时）， 不需要再 JSON.parse 一次。
  • 失败不抛 500：回 status=failed 的 run，看 error 与 nodeTraces 定位失败节点。
  • 约束：工作流对签发人可见才可触发（不可见一律 404，不泄露存在性）；未发布 → 400； 含人工审核节点 → 400（外部调用方没有审批交互面）。
  • 补查：GET /v1/workflows/{id}/run/{runId}。另有入站触发 POST /v1/workflows/webhook/{token}（令牌即凭据，不走 Key）。

#前端嵌入：分享 token，不碰 Key

两条路，凭据都是分享 token（智能体「公开发布」得到）：

html
<script src="https://your-host/wenqu-embed.js"></script>
<script>
  WenquChat.init({
    token: '<分享token>',        // 公开发布链接 /s/ 后面那段
    title: '在线咨询',
    color: '#3b82f6',
    placeholder: '问我任何问题',
    position: 'bottom-right'     // 或 bottom-left
  })
</script>
html
<iframe src="https://your-host/s/<分享token>?embed=1&color=%233b82f6"
        width="420" height="640" style="border:0;border-radius:12px"></iframe>
  • 加载器约 3KB、零依赖；浮动按钮点击才懒加载对话面板。
  • WenquChat.init() 返回 {open, close, toggle, destroy}。
  • iframe 参数（embed=1 时生效）：no-tool=1 / compact=1 / color=#rrggbb / placeholder=… / autoOpen=1。
  • 游客额度闸照常生效：每条分享有每日轮次与 token 上限，超限 429。
  • 嵌入脚本挂在前端站点，不在后端 API 实例上——本地起前后端两个进程时，src 要指向前端 5800，不是 8090。

#MCP 接入

平台级 MCP 入口把问渠能力暴露成标准 MCP Server（Streamable HTTP），凭据是 Authorization: Bearer：

json
{
  "mcpServers": {
    "wenqu": { "url": "__BASE__/mcp", "headers": { "Authorization": "Bearer sk-你的Key" } }
  }
}

固定元工具集：wenqu_ask、wenqu_search_knowledge、wenqu_list_knowledge_bases、wenqu_list_agents。

启用条件（缺一不可）：① 该 Key 在个人设置里打开了「MCP」开关；② 管理员在「系统设置 → MCP 服务（双向）」 开启「对外提供 MCP 端点」；③ 对外域名访问时，前端域名要进「允许的 Origin」（Claude / Cursor 这类本地进程不带 Origin，不受影响）。可见范围与签发人在网页上看到的完全一致。

想让某一个智能体单独对外，用它的「公开发布 → MCP 端点」__BASE__/mcp/{token}——凭据是分享 token，不是 Key。

#2026-11-15

  • 新增 GET /api/ai/v1/runs/{id}/artifacts（scope: runs.read）：列出本次运行的可下载产物（含签名 URL）
  • 新增 POST /api/ai/v1/runs/{id}/approvals（scope: runs.write）：提交审批卡（approve/reject/revise/supersede/answer/ignore）

为什么改：A 期 A1 第二批——补齐 run 控制面（审批 / 产物 / 插话 / 停止），让长任务与人在回路能走正式 v1 契约；同时收口 run.finished 出站回调，新增 approval.timed_out 过程事件。详见 design/plans/对外开放运行原语A1实现方案.md §10.2。

#2026-11-15

  • 修正（不改端点、不改 scope）：POST /api/ai/v1/workflows/{id}/run 与 GET …/run/{runId} 的响应里 inputs / outputs / nodeTraces 由「JSON 字符串」改为真正的 JSON（对象 / 数组）。

为什么改：这三个字段在库里是 String（存的是序列化后的 JSON），实体直接序列化就成了「字符串套 JSON」—— res.data.outputs.answer 取不到值，而 SDK 的类型声明（WorkflowRun.outputs: Record<string, unknown>） 与本仓文档写的都是对象。实测同步触发与补查都把出参回成了 "{\"answer\":\"…\"}"。 对外端点改为解析后返回，内部管理端点 /api/ai/workflow/** 形状不变（前端那里按字符串 JSON.parse）。 解析失败原样回字符串，不因形状问题把 run 变成 500。
