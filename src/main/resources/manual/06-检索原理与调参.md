# 检索原理与调参

问渠的问答质量由「检索 → 重排 → 上下文组装」三级决定，调参前先理解两条链路。

## 混合检索

一次检索并行跑两路：

- **向量路**：问题向量化后在 Redis 向量索引里召回语义近邻（per-KB 独立索引，按库绑定模型）
- **关键词路**：关键词引擎召回（默认 MySQL LIKE 零依赖；可切 Meilisearch 获得 jieba 中文分词与相关度打分）

两路结果按权重融合（向量权重/关键词权重设置页可调），语义与关键词双命中叠加加分，另有标题命中奖励。向量分经归一化后参与融合。

> 注意：融合分因权重与阈值设定会**放大**词面重叠——只字面撞词的无关块融合分也可能不低，这就是为什么需要重排。

## 重排与两道相关分门

重排（Rerank）用交叉编码器对「问题-块」逐对精算相关分，是过滤语义无关块的关键一环。**融合分与重排分是两个分值域**，阈值不能混用：

- `retrieval.minContextScore`（设置页名「最低相关分」，默认 0.6）：卡**重排分**——真相关块通常 0.5+，无关块趋近 0
- `retrieval.minFusionScore`（设置页名「融合分门（未重排）」，默认 0.5）：卡**融合分**，仅在重排未启用/失败时兜底
- 单侧约束：本轮重排实际执行过时，未重排的候选不得借融合门入场，防止弱相关块混进引用

**重排有两个窗口旋钮**（系统设置 → 检索设置，改完即生效）：

- **少于几条不重排**（默认 6）：候选太少时重排省不了什么，直接按融合分序走
- **重排窗口**（默认 15）：候选多于这个数，只重排头部这么多条，其余保持融合分序。配合上面那条单侧约束，**窗口外的候选进不了上下文**——所以「明明检索命中上百条、上下文却只有一两块」时，先用检索调试面板看分数分布，再决定是调窗口还是这道门本来就该只放这么几条。窗口调大更准但每次多花时间（本地 CPU 重排服务逐条吃时间）

凡把命中块送进上下文、引用面板、工具结果、工作流节点结果的路径，都先重排再卡门——看到「没引用但回答里像有资料」多半是这两道门拦了弱相关内容，属预期行为。**联网搜索结果与智能体咨询交回的资料同样按本轮问题过这两道门**（服务商自带的相关度分没有相关性含义，不参与判定），被滤掉的内容不进引用面板、不交给模型，滤掉多少会如实写进给模型的说明里。

## 其他增强

- **词面召回**：问句按中文分词切成检索词（jieba），与向量召回并行发起后再融合排序；多轮指代由对话上下文本身承担
- **GraphRAG 图谱扩展**（库级开关，默认关）：解析时抽「主体-关系-客体」三元组入库；检索命中后，用命中块内容匹配实体 → 取一跳三元组 → 反查真实知识块，按衰减分（×0.9）并入结果，条数由 `graphrag.expandTopK` 封顶。抽取模型归知识库绑定，未绑定回落库主个人默认聊天模型，两者皆空则不抽取并告警
- **父子分块**：超长块切子块做检索索引，命中子块返回父块完整正文
- **问答对增强**：解析时对每块生成 QA 并按问法向量化，用不同问法也能召回

## 上下文组装

预算 = 模型窗口 × 安全系数(0.7) − 最大输出（窗口/最大输出按模型在模型供应商里声明）。命中块按相关度价值驱动填充，块内按命中位置截取片段（带 ±150 字窗口），信息增益去冗余，历史对话按轮裁剪。token 计数用 tiktoken（jtokkit cl100k BPE）。

## 怎么调

1. **先看分域**：调阈值前先确认它作用在哪个分值域（重排分/融合分），两域分布不同
2. **用检索调试**：`POST /api/ai/debug/retrieval` 分步展示检索词元/关键词/向量/合并/重排/最终结果；问答页的检索状态行可直视命中情况
3. **用检索评估**：评估页从历史问答引用回放生成评估集，多参数组对比 recall@k / MRR / 命中率，一键体检、一键应用最优组
4. **手册类资料放宽阈值保召回**，法律/制度类提高阈值保精度——这正是库级参数稀疏覆盖的用途
5. 切换关键词引擎（mysql ↔ meilisearch）后需全量重建一次索引，写索引随解析/编辑/删除增量同步
