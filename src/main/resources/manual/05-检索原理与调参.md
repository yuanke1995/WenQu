# 检索原理与调参

问渠的问答质量由「检索 → 重排 → 上下文组装」三级决定，调参前先理解两条链路。

## 混合检索

一次检索并行跑两路：

- **向量路**：问题向量化后在 Redis 向量索引里召回语义近邻（per-KB 独立索引，按库绑定模型）
- **关键词路**：关键词引擎召回（默认 MySQL LIKE 零依赖；可切 Meilisearch 获得 jieba 中文分词与相关度打分）

两路结果按权重融合（向量权重/关键词权重设置页可调），语义与关键词双命中叠加加分，另有标题命中奖励。向量分经归一化后参与融合。

> 注意：融合分因权重与阈值设定会**放大**词面重叠——只字面撞词的无关块融合分也可能不低，这就是为什么需要重排。

## 重排与两道相关分门

重排（Rerank）用交叉编码器对「问题-块」逐对精算相关分，是过滤语义无关块的关键一环。**融合分与重排分是两个分值域**，阈值不能混用：

- `retrieval.minContextScore`（默认 0.6）：卡**重排分**——真相关块通常 0.5+，无关块趋近 0
- `retrieval.minFusionScore`（默认 0.25）：卡**融合分**，仅在重排未启用/失败时兜底
- 单侧约束：本轮重排实际执行过时，未重排的候选不得借融合门入场，防止弱相关块混进引用

凡把命中块送进上下文、引用面板、工具结果、工作流节点结果的路径，都先重排再卡门——看到「没引用但回答里像有资料」多半是这两道门拦了弱相关内容，属预期行为。

## 其他增强

- **查询改写**（默认开）：LLM 把问句改写为检索关键词；多轮对话自动补全指代（追问「那删除呢？」会带上文）
- **意图分类**：问候/闲聊类问题跳过检索直接对话，省时省钱
- **知识块关联检索**：解析时识别块间交叉引用建边；检索命中 A 时 1-hop 扩散带出关联块，并沿章节路径带出父章节摘要；扩散块走独立配额
- **父子分块**：超长块切子块做检索索引，命中子块返回父块完整正文
- **问答对增强**：解析时对每块生成 QA 并按问法向量化，用不同问法也能召回
- **语义缓存**：相似问题直接复用历史回答，知识库变动整体失效

## 上下文组装

预算 = 模型窗口 × 安全系数(0.7) − 最大输出（窗口/最大输出按模型在模型管理中声明）。命中块按相关度价值驱动填充，块内按命中位置截取片段（带 ±150 字窗口），信息增益去冗余，历史对话按轮裁剪。token 计数用 tiktoken（jtokkit cl100k BPE）。

## 怎么调

1. **先看分域**：调阈值前先确认它作用在哪个分值域（重排分/融合分），两域分布不同
2. **用检索调试**：`POST /api/ai/debug/retrieval` 分步展示检索词元/关键词/向量/合并/重排/最终结果；问答页的检索状态行可直视命中情况
3. **用检索评估**：评估页从历史问答引用回放生成评估集，多参数组对比 recall@k / MRR / 命中率，一键体检、一键应用最优组
4. **手册类资料放宽阈值保召回**，法律/制度类提高阈值保精度——这正是库级参数稀疏覆盖的用途
5. 切换关键词引擎（mysql ↔ meilisearch）后需全量重建一次索引，写索引随解析/编辑/删除增量同步
